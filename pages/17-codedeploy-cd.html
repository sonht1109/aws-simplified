Project: CD with CodeDeploy

Finish the pipeline from the previous lesson. After CodeBuild pushes a new Docker image, CodeDeploy automatically pulls it onto an EC2 server and runs it. By the end, one git commit takes your code all the way to a running app.

This continues Lesson 16: CI with CodeBuild. Do that first: CD isn't much use without a CI pipeline that produces something to deploy.

The complete CI/CD picture

CodePipeline stays the orchestrator. It now has three stages: Source (GitHub) → Build (CodeBuild) → Deploy (CodeDeploy). CodeDeploy doesn't copy a Docker image itself. It tells a small program on the server (the CodeDeploy agent) to run your scripts, and those scripts pull and start the image.

CodeDeploy's building blocks

CodeDeploy is AWS's managed deployment service. It can deploy to EC2 (and on-premises servers), ECS, or Lambda. This project uses EC2. Five terms to know:

Application

A named container for one thing you deploy. Usually one per microservice: payments, login, and so on. It's like a folder. On its own it doesn't know where or how to deploy.

Deployment group

The where: the set of servers to deploy to, picked by tags. Similar to a load balancer's target group.

Deployment

One actual rollout of one version (a revision) of your code, taken from GitHub or S3, to a deployment group.

appspec.yml

The how: a file in your repo listing which scripts to run at each step of the deployment. It's CodeDeploy's version of buildspec.yml.

CodeDeploy agent

A small program installed on each target server. It checks in with CodeDeploy, downloads the revision and runs your scripts. Like a Jenkins agent or a GitHub Actions runner.

Step 1: Create the application

Open CodeDeploy → Applications → Create application. Give it a name (e.g. sample-python-flask-app) and choose compute platform EC2/On-premises. In a company with 200 microservices you'd repeat this 200 times, which is why teams script it with the CLI once they understand the steps in the console.

Step 2: Launch and tag the EC2 instance

Launch an Ubuntu t2.micro in the default VPC with a public IP and your key pair (Lesson 4 covers this). The new part is the tag.

A tag is a key/value label you attach to an AWS resource, such as Name = sample-python or project = payments. CodeDeploy uses tags to find its targets. There could be many instances called "example.com" in an account, but a deployment group that says "every instance tagged Name = sample-python" is clear. This also scales: tag 10 more servers the same way and they automatically become deployment targets.

Tags also matter for tracking cost and ownership across teams. Tagging best practices are covered in Lesson 36: Reducing Your AWS Bill.

Step 3: Install the CodeDeploy agent

SSH into the instance (Lesson 5) and follow these steps exactly. Skipped steps here cause most CodeDeploy problems. The agent is written in Ruby, so install Ruby first. The download bucket must match your instance's region; for us-east-1 it looks like this:

sudo apt update
sudo apt install -y ruby-full wget
cd /home/ubuntu

# bucket name + region must match where your instance runs
wget https://aws-codedeploy-us-east-1.s3.us-east-1.amazonaws.com/latest/install
chmod +x ./install
sudo ./install auto

# check it's running; start it if it says "No AWS CodeDeploy agent running"
sudo service codedeploy-agent status
sudo service codedeploy-agent start

While you're there, install Docker too, since your deploy scripts will need it:

sudo apt install -y docker.io
Watch outForgetting Docker on the server is a classic first failure. The deployment reaches your start script and fails with docker: command not found.

Step 4: Give the instance and CodeDeploy their roles

Two things need AWS permissions, and both get them from IAM roles (roles are for services, users are for people, as covered in Lesson 3):

  • The EC2 instance, so the agent on it can talk to CodeDeploy and fetch revisions. Create a role with EC2 as the trusted service, then attach it: instance → Actions → Security → Modify IAM role.
  • CodeDeploy itself, so it can look up your instances and tags. Create a role with CodeDeploy as the trusted service (it suggests the AWSCodeDeployRole policy). You'll pick this as the deployment group's service role.

For a quick demo, one role with broad EC2 + CodeDeploy permissions works. In real projects, keep them separate and give each one only the permissions it needs.

TipAfter you attach or change the instance's IAM role, restart the agent (sudo service codedeploy-agent restart) and check its status again. Otherwise the agent may keep using its old (missing) credentials and never connect.

Step 5: Create the deployment group

  1. Open your application → Create deployment group. Name it and choose the CodeDeploy service role.
  2. Deployment type: choose In-place (update the existing servers). Blue/green creates a second set of servers and switches traffic over through a load balancer. It's safer, but more setup than we need here.
  3. Environment configuration: Amazon EC2 instances, tag Name = sample-python. The console immediately says "1 unique matched instance". Type a wrong value and it drops to 0, which is a handy check.
  4. Agent install: skip it (you already installed it). Load balancer: untick. Create.

Step 6: Write appspec.yml and the scripts

When the source is GitHub, appspec.yml must sit at the root of the repository and have exactly that name. (CodeBuild let you put the buildspec anywhere; CodeDeploy doesn't.) For this project it runs two scripts:

version: 0.0
os: linux
hooks:
  ApplicationStop:
    - location: scripts/stop_container.sh
      timeout: 300
      runas: root
  AfterInstall:
    - location: scripts/start_container.sh
      timeout: 300
      runas: root

scripts/start_container.sh pulls the image CI just pushed and runs it. The app listens on port 5000 (that's what the Dockerfile exposes), so map host 5000 to container 5000:

#!/bin/bash
set -e
docker pull <your-dockerhub-user>/simple-python-flask-app:latest
docker run -d -p 5000:5000 <your-dockerhub-user>/simple-python-flask-app:latest

scripts/stop_container.sh removes the container from the previous deployment. Without it, the next deployment fails because port 5000 is already in use:

#!/bin/bash
# Remove any running containers so port 5000 is free
container_ids=$(docker ps -q)
if [ -n "$container_ids" ]; then
  docker rm -f $container_ids
fi
NoteYou'll often see this written as docker ps | awk '{print $1}' to grab the container ID from the first column. That works if you skip the header row. docker ps -q prints just the IDs, so you don't need to deal with the header.

The lifecycle hooks

A deployment on EC2 moves through fixed steps called lifecycle events. You attach scripts to the ones you care about, which are called hooks. In order:

EventWhat happensYour script?
ApplicationStopStop the old version. Runs the stop script from the previous revision, so it does nothing on the very first deployment.Yes
DownloadBundleAgent downloads the revision (your repo at that commit).No (agent)
BeforeInstallPrep work, e.g. backups, before files are copied.Optional
InstallAgent copies files to their destination.No (agent)
AfterInstallConfigure or start things after the copy. We start the container here.Yes
ApplicationStartStart services (a common alternative place to start the app).Optional
ValidateServiceCheck the new version works, e.g. curl a health endpoint.Optional
Try it: run a CodeDeploy deployment

Set up the situation, then deploy. Watch each lifecycle event the way you would in the console's View events page. Try a second deployment with the old container still running and the stop script left as a placeholder.

    Step 7: Test a deployment by hand

    Before connecting it to the pipeline, check that CD works by itself. In your application → Create deployment: pick the deployment group, revision type "My application is stored in GitHub", connect your GitHub account, enter user/repo and a commit ID (copy it from the repo's commit history). Leave the rest at defaults and create.

    If something fails, open the deployment → View events. It shows which lifecycle event failed and the script's error output. These are the failures you'll most likely see:

    • Fails right after downloading → no appspec.yml at the repo root.
    • AfterInstall fails with docker: command not found → install docker.io on the instance.
    • AfterInstall fails with "port is already allocated" → an old container still holds port 5000. Fix stop_container.sh (or remove it once by hand with sudo docker rm -f <id>).

    When it succeeds, sudo docker ps on the instance shows the container running. To open the app in a browser at http://<public-ip>:5000, allow inbound port 5000 in the instance's security group.

    Step 8: Add the Deploy stage to CodePipeline

    1. Open the pipeline from the CI lesson → Edit → Add stage after Build (name it e.g. Deploy).
    2. Add action group: action provider AWS CodeDeploy, input artifact SourceArtifact (the repo, which contains appspec.yml and the scripts), then your application name and deployment group.
    3. Save. Commit a small change, or click Release change, and watch Source → Build → Deploy all turn green.

    That's full CI/CD on AWS: a commit triggers the pipeline, CodeBuild builds and pushes a new image, and CodeDeploy pulls it onto the server and restarts the container.

    Tip: tag your imagesThis project uses the latest tag everywhere for simplicity. In real pipelines, push each image with a unique tag (a version number, a date/time stamp, or the commit ID) and have the deploy script pull that same tag. The rule: whatever tag CI pushes, CD must pull. Unique tags also let you see exactly which version is running and roll back to an earlier one.
    Interview angle"How does CodeDeploy know which servers to deploy to?" Through the deployment group, which selects instances by tags (or an Auto Scaling group). And each instance needs the CodeDeploy agent running, plus an IAM role that lets it talk to CodeDeploy.

    Check yourself

    Your app's source is on GitHub. Where must appspec.yml be?
    For GitHub revisions, CodeDeploy looks for appspec.yml at the root of the revision. Unlike CodeBuild's buildspec, its location can't be changed.
    The second deployment fails in AfterInstall with "port is already allocated". The cleanest fix is…
    The old container still holds port 5000. A proper stop script frees it before the new container starts. Changing ports just moves the problem to the next deployment.
    You just attached an IAM role to the EC2 instance. What should you do next?
    Restart the agent so it picks up the new credentials. Otherwise it may not be able to reach CodeDeploy.

    Key takeaways

    • CodeDeploy = application (what) + deployment group (where, chosen by tags) + appspec.yml (how) + an agent on every target server.
    • Install the agent (Ruby + region-specific installer), give the instance an IAM role, and restart the agent after role changes.
    • appspec.yml lives at the repo root and attaches scripts to lifecycle hooks like ApplicationStop and AfterInstall.
    • Always write a real stop script. Otherwise the second deployment hits "port already allocated".
    • Add CodeDeploy as the Deploy stage in CodePipeline to get one-commit-to-production CI/CD. Use matching, unique image tags in CI and CD.
