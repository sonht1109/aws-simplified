Project: Production-style VPC

Time to build the setup AWS recommends for running apps securely: servers hidden in private subnets across two Availability Zones, a load balancer in front, NAT gateways for outbound traffic, and a bastion host for admin access. Along the way you'll meet Auto Scaling Groups, launch templates, bastion hosts and Elastic IPs.

This project uses ideas from Lesson 6: VPC (subnets, route tables, NAT) and Lesson 7: Security Groups. Review them if anything below feels unfamiliar.

What we're building

  • A VPC with a public and a private subnet in each of two Availability Zones.
  • In the public subnets: an Application Load Balancer, one NAT gateway per AZ, and a bastion host.
  • In the private subnets: app servers launched by an Auto Scaling Group.
  • Users reach the app only through the load balancer. Servers reach the internet only through the NAT gateways.

New building blocks

Two Availability Zones

In the theory lessons we drew one public and one private subnet. In production you repeat them in two (or more) Availability Zones. If one AZ — one group of AWS data centers — has a problem, the other keeps serving users. That's high availability.

Auto Scaling Group (ASG) and launch template

Instead of launching each EC2 instance by hand, you tell an Auto Scaling Group: "Always keep at least 2 copies of this server running, spread across these subnets."

  • Desired capacity — how many to run now (e.g. 2).
  • Minimum / maximum — the floor and ceiling. On a festival sale day, when CPU climbs to 80–90%, a scaling policy can grow the group up to the maximum (say 4), then shrink it back later.
  • If an instance dies, the ASG replaces it automatically.

An ASG needs a launch template — a saved recipe for the instances it creates: AMI, instance type, key pair, security group, network. It's the same form as launching an EC2 instance, saved for reuse. One template can be shared by several ASGs and acts as a record of exactly what your servers look like.

Bastion host (jump server)

Servers in private subnets have no public IP, so you can't SSH to them from your laptop. A bastion host is a small, tightly-guarded EC2 instance in the public subnet. You SSH into the bastion first, then "jump" from it to the private servers.

  • Only one door to guard instead of many.
  • One place to log and audit who logged in and what commands they ran.
  • You can apply extra rules there (allowed source IPs, MFA, scripts).
  • Linux servers are reached over SSH; Windows servers over RDP.
Think of it like…The reception desk of an office building. Visitors can't walk straight to the server room; they sign in at reception, and only from there are they escorted inside.

NAT gateway per AZ and Elastic IPs

Each private subnet sends its internet traffic to the NAT gateway in the same AZ. One NAT per AZ means losing an AZ doesn't cut the other AZ's servers off from the internet.

Each NAT gateway needs an Elastic IP: a public IP address that belongs to your account and stays the same (a static IP). Normal public IPs can change when an instance stops and starts; an Elastic IP doesn't.

Load balancer and target group (just enough)

The load balancer spreads requests across servers — 100 requests might go 50/50, or 60/40. It sends traffic to a target group (a list of servers plus a port), and only to targets that pass their health check. Full details in Lesson 28.

Build it step by step

Step 1 — Create the VPC

  1. Open the VPC console → Create VPC → choose VPC and more. AWS draws a preview of everything it will create.
  2. Name: aws-prod-example. Keep the IPv4 CIDR 10.0.0.0/16 (65,536 IPs is plenty). No IPv6.
  3. Availability Zones: 2. Public subnets: 2. Private subnets: 2.
  4. NAT gateways: 1 per AZ. VPC endpoints: None (not needed here).
  5. Click Create VPC. AWS creates the subnets, route tables (public → internet gateway, each private → its NAT gateway), the internet gateway, Elastic IPs and NAT gateways. NAT gateways take a few minutes to become active.
Watch outIf creation fails with "maximum number of addresses has been reached", your account has hit its Elastic IP limit (5 per region by default). Release unused Elastic IPs in EC2 → Elastic IPs, then click Retry.

Step 2 — Launch template

  1. EC2 console → Auto Scaling Groups → Create Auto Scaling group → Create a launch template.
  2. Name it, pick the Ubuntu AMI, a free-tier instance type (t2.micro) and your key pair.
  3. Create a new security group in your new VPC with inbound rules: SSH 22 and Custom TCP 8000 (the app port). Open only the ports you need.

Step 3 — Auto Scaling Group

  1. Name the ASG and select your launch template.
  2. Network: choose your VPC and the two private subnets.
  3. Load balancing: No load balancer for now — we'll create and attach one separately.
  4. Group size: desired 2, min 1–2, max 3–4. Scaling policy: none for this demo. Skip notifications.
  5. Create. After a minute, EC2 → Instances shows two instances: one in us-east-1a, one in us-east-1b, both without public IPs.

Step 4 — Bastion host

  1. Launch a normal EC2 instance named bastion-host (Ubuntu, t2.micro, same key pair).
  2. Network settings → Edit: choose the same VPC, a public subnet, and enable auto-assign public IP. Security group must allow SSH (22).

Step 5 — Jump into a private server and start the app

The bastion needs the key to log into the private servers. The simple (demo) way is to copy the .pem file to it with scp (secure copy):

# from your laptop: copy the key to the bastion
scp -i aws_login.pem aws_login.pem ubuntu@<bastion-public-ip>:/home/ubuntu

# log into the bastion
ssh -i aws_login.pem ubuntu@<bastion-public-ip>

# from the bastion: hop to a private server using its PRIVATE IP
chmod 400 aws_login.pem
ssh -i aws_login.pem ubuntu@10.0.140.109
TipCopying private keys onto servers is fine for learning, but avoid it in real life. Use an SSH agent and ProxyJump instead, so the key never leaves your laptop: 
ssh-add aws_login.pem
ssh -J ubuntu@<bastion-public-ip> ubuntu@10.0.140.109
Also restrict the bastion's SSH rule to your IP rather than 0.0.0.0/0. (SSH basics are in Lesson 5.)

On one of the private servers, create a page and serve it:

cat > index.html <<'EOF'
<!DOCTYPE html>
<html><body>
<h1>My first AWS project</h1>
<p>Demo of an app in a private subnet</p>
</body></html>
EOF
python3 -m http.server 8000

We deliberately leave the second server without the app, to watch the load balancer's health checks at work.

Step 6 — Target group

  1. EC2 → Target groups → Create. Target type: Instances. Protocol HTTP, port 8000 (the port your app listens on — getting this wrong is a common mistake), your VPC.
  2. Select both ASG instances → Include as pending below → Create target group.

Step 7 — Application Load Balancer

  1. EC2 → Load balancers → Create → Application Load Balancer (works with HTTP/HTTPS — "layer 7").
  2. Scheme: Internet-facing. VPC: yours. Mappings: both AZs, each with its public subnet.
  3. Security group: one that allows HTTP port 80 from anywhere.
  4. Listener: HTTP :80 → forward to your target group. Create, and wait for state Active.
Watch outIf the console warns "security groups for your load balancer don't allow traffic on the listener port", the ALB's security group is missing an inbound rule for port 80. Add HTTP · 80 · Anywhere and wait a moment.

Step 8 — Test it

Copy the load balancer's DNS name into your browser. You'll see "My first AWS project", served from a server that has no public IP. Traffic went: Internet gateway → ALB in the public subnet → target group → EC2 in the private subnet.

Refresh many times — you always land on the same server. Why? The target group's health check marks the server without the app as unhealthy, so the ALB only sends traffic to the healthy one.

Your assignmentDeploy the page on the second server too, with a different heading ("My second AWS project"). Once both targets are healthy, refreshing should alternate between the two pages — load balancing in action.

Clean up

NAT gateways and Elastic IPs cost money every hour. When you're done, delete in this order: Auto Scaling Group (otherwise it recreates instances), load balancer, target group, bastion, NAT gateways, then release the Elastic IPs and delete the VPC.

Interview angle"Have you built a public/private subnet architecture? How does traffic reach the app?" Describe this project: two AZs for availability, ASG for scaling and self-healing, ALB in public subnets, apps in private subnets, NAT per AZ for outbound, bastion for admin access, and security groups opening only needed ports.

Check yourself

Why can't you SSH from your laptop directly to the app servers in this project?
Private-subnet servers have no route from the internet. The bastion in the public subnet is the controlled entry point.
What does an Auto Scaling Group need before you can create it?
The launch template is the recipe (AMI, type, key pair, security group). A load balancer is optional.
Only one of two servers runs the app. The ALB keeps sending you to that one. Why?
Load balancers route only to healthy targets. Deploy the app on both and traffic will be shared.

Key takeaways

  • Production layout: public subnets (ALB, NAT, bastion) and private subnets (apps) in two AZs.
  • An Auto Scaling Group keeps the right number of instances running, using a launch template as its recipe.
  • A bastion host is the single, auditable door for SSH into private servers.
  • One NAT gateway per AZ, each with a static Elastic IP, gives private servers safe outbound access.
  • The ALB forwards to a target group and only to healthy targets. Remember to open port 80 on its security group.
  • Clean up NAT gateways and Elastic IPs after practice — they bill by the hour.
