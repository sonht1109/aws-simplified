Security Groups vs NACLs

AWS gives you two firewalls inside a VPC: security groups guard each server, and network ACLs guard each subnet. You'll learn how each works, how their rules are evaluated, what "stateful vs stateless" means, and you'll replay a hands-on experiment that blocks and unblocks a real app.

This lesson builds on Lesson 6: VPC — subnets, internet gateways and route tables are explained there.

Security is a shared job

Before a company moves to the cloud, its first question is "Is it secure?" AWS's answer is that security is a shared responsibility (see Lesson 2): AWS secures the data centers and gives you tools, and you must configure those tools well.

A request from a user travels a long way inside your VPC — internet gateway, load balancer, route tables. The last two checkpoints before it reaches your app are:

  • NACL (Network Access Control List) — at the subnet edge. It protects every server in that subnet.
  • Security group — at the instance (EC2) level. It protects one server (or a group of servers you attach it to).

Because they're the last line of defense, a mistake here usually means your app is exposed.

Security groups: the guard at each server

A security group is a virtual firewall attached to an EC2 instance (more precisely, to its network interface). It has two lists of rules:

Inbound rules

Traffic coming into your instance — e.g. a user opening your website. Default: nothing is allowed. You add rules like "TCP port 8000 from anywhere".

Outbound rules

Traffic going out of your instance — e.g. your shop app calling a payment provider. Default: everything is allowed. You can tighten it if needed.

This is why, back in Lesson 4, Jenkins on port 8080 couldn't be reached until you added an inbound rule. When you launch an instance from the console, the wizard creates a security group that allows only SSH on port 22 — otherwise you couldn't even log in.

  • Security group rules can only allow. There is no "deny" rule — anything not allowed is blocked.
  • A rule names a protocol (TCP/UDP), a port or range, and a source (an IP range like 203.0.113.0/24, 0.0.0.0/0 for "anywhere", or another security group).
  • All rules are checked together — there is no rule order.
  • Changes apply right away to every instance using that security group.
Watch outOpening "All traffic from 0.0.0.0/0" to make things work quickly is a common mistake. Every unused open port is a door for attackers or junk traffic. Open only the ports your app actually needs.
NoteAWS restricts outbound traffic on port 25 (email/SMTP) from EC2 by default, to stop spammers from abusing its IP addresses. You can ask AWS to lift this if you really run a mail server.

NACLs: the gate of each subnet

Now imagine a team that, to save time, opens all traffic from everywhere on its 50 instances. As the DevOps or network admin, you can't police every instance. A Network ACL gives you a second layer you control at the subnet level:

  • One NACL applies to every instance in the subnet automatically — 50 or 10,000 of them.
  • NACLs support both ALLOW and DENY rules. If you deny something here, opening it in a security group won't help.
  • You can block by port ("deny port 8000") or by IP range ("deny 3.4.0.0/16").
  • The default NACL that comes with a VPC allows all inbound and outbound traffic, so by default it doesn't get in the way.

Rule order matters

Each NACL rule has a rule number. AWS checks rules from the lowest number up and stops at the first match. The last rule, shown as *, denies everything that didn't match anything else — you can't delete it.

Rule #TypePortSourceAction
100All trafficAll0.0.0.0/0ALLOW
200Custom TCP80000.0.0.0/0DENY
*All trafficAll0.0.0.0/0DENY

Is port 8000 blocked here? No! Rule 100 (allow all) matches first, so rule 200 is never reached. To block 8000, its deny rule needs a lower number than the allow-all rule, e.g. 110 deny and 200 allow.

TipNumber your rules in steps of 10 or 100 (100, 110, 200…) so you can slot new rules in between later.

Stateful vs stateless

This is the most-asked difference in interviews. Every connection has two directions: the request and the response.

Security group = stateful

It remembers connections. If a request was allowed in, the response is automatically allowed out — no outbound rule needed. Same the other way: if your app calls google.com, the reply is let back in automatically.

NACL = stateless

It has no memory. Every packet is checked against the rules on its own. So a response needs its own rule in the other direction — for example an outbound rule allowing the return traffic.

Think of it like…A security group is a guard who remembers faces: "You came in a minute ago, go ahead and leave." A NACL is a turnstile that checks your ticket both ways — entering and leaving.

Responses go back to the client on a random high "ephemeral" port (typically 1024–65535). With the default NACL that's fine, because it allows everything. If you write a custom NACL, remember an outbound rule for those ports, or replies will be silently dropped.

Using both is called defense in depth: if one layer is misconfigured, the other can still protect you. That's how most organizations run.

Hands-on: block and unblock an app

Here's the experiment you can repeat in your own account.

  1. Create a VPC. In the VPC console choose Create VPC → VPC and more. Name it demo-vpc and keep the defaults. AWS creates public and private subnets in two Availability Zones, route tables and an internet gateway for you. The Resource map tab shows a diagram of it all.
  2. Launch an EC2 instance (Ubuntu, t2.micro, your key pair). Under Network settings → Edit, pick demo-vpc, choose a public subnet (only for this demo — real apps go in private subnets), and enable Auto-assign public IP. Let it create a new security group.
  3. Start a tiny web app after you SSH in: 
    sudo apt update
python3 -m http.server 8000
  4. Try http://<public-ip>:8000 in a browser. It times out. The NACL allows everything, but the security group only allows port 22.
  5. Security group → Edit inbound rules → Add rule: Custom TCP, port 8000, source Anywhere-IPv4. Refresh — you see the directory listing (HTTP 200).
  6. NACL → Edit inbound rules: replace the allow-all rule with 100 · Custom TCP · 8000 · DENY. Refresh — blocked again, even though the security group allows it.
  7. Reorder: set 100 ALLOW all and 200 DENY 8000. It works (rule 100 matches first). Change the deny to 110 and the allow to 200, and it's blocked (rule 110 matches first).

Notice how an app owner who "did everything right" in the security group can still be blocked by the subnet's NACL. That's the power the NACL gives the network team.

Mention stateful vs stateless and rule order.

    Check yourself

    A NACL has rule 100 ALLOW all traffic and rule 200 DENY TCP 8000. A request arrives on port 8000. What happens?
    NACL rules are checked from the lowest number up and the first match wins. Rule 100 allows everything, so rule 200 is never reached.
    You allow inbound port 443 in a security group but have removed every outbound rule. Can users still get responses?
    Security groups remember allowed connections, so return traffic is let through. A NACL, being stateless, would need an outbound rule.
    You need to block one country's IP range for every server in a subnet. Which tool fits best?
    Security groups can't deny. A NACL deny rule applies to the whole subnet at once.

    Key takeaways

    • Security groups protect instances; NACLs protect subnets. Traffic passes the NACL first, then the security group.
    • Security groups only allow; new ones block all inbound and allow all outbound.
    • NACLs allow and deny, checked by rule number from lowest up — first match wins, * denies the rest.
    • Security groups are stateful (replies automatic); NACLs are stateless (replies need a rule).
    • Open only the ports you need, and use both layers for defense in depth.
