EKS Auto Mode

Running Kubernetes is easy to start and hard to keep running well: sizing nodes, scaling, patching, upgrades and cost. EKS Auto Mode hands most of that work to AWS. You'll learn which problems it solves, how it uses Karpenter to add and remove nodes, and exactly what you still manage yourself.

This lesson assumes you know what an EKS cluster, nodes and pods are. If not, start with Lesson 24: EKS, and for why orchestration exists, Lesson 23.

The problems with running Kubernetes yourself

Problems show up in two phases. Day 1 is setting the cluster up. Day 2 is everything after that, which never ends.

Day 1: creating the cluster

  • Capacity planning: how many worker nodes (the EC2 machines that run your pods): 3, 6, 10? And how big should each one be (16 CPU / 16 GB, or more)? Teams new to Kubernetes have no data to base this on.
  • Instance type: EC2 has many families (general, memory-optimized, GPU…). The wrong choice hurts app performance. AI/ML workloads make this harder because you also have to pick GPU instances and use them efficiently.
  • Setup effort: by hand, that means a VPC with subnets, route tables, internet and NAT gateways, and then EKS, with every step checked for mistakes. With IaC such as Terraform, you also have to manage state files, locking, and many .tf files.

Day 2: keeping it healthy

  • Node management: picture an online shop with 3 nodes on weekdays, 5 at weekends and 8 during a sale. Every scale-up means adding nodes, joining them to the cluster and spreading pods onto them. Every scale-down means cordoning and draining nodes (moving pods off safely) before removing them. Some teams do this every day and every night.
  • Security fixes: the node operating systems need patches for vulnerabilities, all the time.
  • Version upgrades: Kubernetes releases patch versions often (1.33.0 → 1.33.1 → …) and new minor versions regularly. You can't stay on one version forever.
  • Add-on compatibility: after each upgrade, core components such as the CNI (pod networking), CoreDNS (in-cluster DNS) and CSI drivers (storage) must still be compatible.
  • Cost: teams over-provision "just in case", and rarely go back to scale down or rebalance when usage drops.

How EKS Auto Mode solves them

One-click, ready-to-use cluster

Choose Quick configuration and click create. Networking, storage drivers, a load-balancing controller, DNS and metrics come built in.

Automatic nodes with Karpenter

No node groups to size. Auto Mode launches the right number and type of nodes for your pods, and removes them when they're no longer needed.

Patched, upgraded nodes

Nodes run Bottlerocket-based AMIs (a minimal, container-focused OS) that AWS patches, tests and rolls out. Nodes are replaced regularly (never older than 21 days), so you never patch nodes by hand.

Compatible core components

Pod networking, DNS, storage (EBS) and load-balancer integration are built in and kept compatible by AWS when you upgrade.

Karpenter in one minute

Karpenter is an open-source node autoscaler. AWS built it and donated it to the Kubernetes/CNCF community. Instead of scaling fixed node groups, it looks at pending pods (pods that can't be scheduled because no node has room), works out what they need, and launches the cheapest EC2 instance that fits. It also keeps checking for consolidation: if pods could fit on fewer or cheaper nodes, it moves them and removes the extra nodes. In Auto Mode, Karpenter is already running and managed by AWS, so you don't install or upgrade it.

Who manages what?

Compare the three ways to run EKS worker nodes. Self-managed nodes are EC2 instances you build and join to the cluster yourself. Managed node groups are groups of EC2 nodes that EKS creates for you, but you still choose and size them. Auto Mode is described above.

Try it: who manages what?

Pick a node option and see who's responsible for each job.

NoteEven with Auto Mode, you still own your applications: deployments, sensible CPU/memory requests (Karpenter sizes nodes from these), IAM permissions, and choosing when to upgrade the cluster's Kubernetes version. Auto Mode also charges a management fee per node on top of the normal EC2 price.

Hands-on: create a cluster and watch it scale

1. Create the cluster

  1. Console → Elastic Kubernetes Service → Create cluster → Quick configuration (with EKS Auto Mode).
  2. First time only: create a cluster IAM role and a node IAM role using Create recommended role. The wizard pre-selects EKS / EKS Auto Cluster and the right policies. You can reuse both roles for future Auto Mode clusters. (Roles are explained in Lesson 3.)
  3. Click Create. After a few minutes the status is Active and the API server endpoint is shown.

Look around in the console. The Resources tab shows system pods already running on a node that Auto Mode launched (its compute shows as auto mode). Default services such as kubernetes and the metrics service are present, and storage drivers for EBS/EFS are listed. The cluster is ready to use.

2. Point kubectl at it and watch the nodes

aws eks update-kubeconfig --name <cluster-name> --region ap-south-1

# in a second terminal: live view of nodes, pods, CPU use and cost
eks-node-viewer

eks-node-viewer is a small open-source tool from AWS Labs. It shows each node with its instance type, price, CPU use, and running and pending pods. It's the easiest way to watch Karpenter work.

3. Deploy a lot of microservices

The OpenTelemetry demo installs 20+ microservices, which is enough to make the cluster grow:

helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm install my-otel-demo open-telemetry/opentelemetry-demo
kubectl get pods        # most pods Pending at first…

What happened:

  • 24 pods were Pending (only the 2 existing system pods were running).
  • Karpenter launched a new node and chose m6a.large as the best fit for those pods, with about 73% of its CPU used. It chose the instance type itself.
  • A minute or two later, kubectl get pods showed them Running.

4. Remove them and watch the cost go away

helm uninstall my-otel-demo

CPU use dropped to 0 and no pods were left on that node. After a few minutes the node moved to Deleting, and shortly afterwards it was gone. That's what makes Auto Mode cost-effective: you don't keep paying for an empty node.

TipDelete the cluster when you're done practicing. The EKS control plane is billed per hour even with no nodes (see Lesson 36).
Interview angle"Managed node groups vs Karpenter vs Auto Mode?" Node groups: AWS runs the node lifecycle, but you size them and install autoscaling and add-ons. Karpenter (self-installed): flexible, cost-aware autoscaling, but you operate it. Auto Mode: AWS runs Karpenter, patched Bottlerocket nodes and core add-ons for you, at the cost of less low-level control and a per-node fee.

Check yourself

In EKS Auto Mode, what decides that a new m6a.large node should be launched?
Karpenter watches for pods that can't be scheduled and launches the cheapest instance type that fits them.
Who patches the worker node operating system in Auto Mode?
AWS continuously patches, tests and rolls out the node AMIs, and nodes are replaced regularly.
After helm uninstall, the node stays "Ready" for a minute and then shows "Deleting". What is this?
Once a node is empty (or its pods fit elsewhere), Karpenter consolidates it away.

Key takeaways

  • Running Kubernetes means Day-1 work (sizing, instance types, setup) and Day-2 work (scaling, patching, upgrades, add-on compatibility, cost).
  • EKS Auto Mode gives a ready-to-use cluster in one click, with networking, DNS, storage and load-balancer integration built in.
  • It uses Karpenter to launch the cheapest instance that fits pending pods and to consolidate nodes that aren't needed.
  • Nodes use AWS-patched Bottlerocket AMIs and are replaced regularly, so there's no manual node patching.
  • You still own your apps, pod resource requests, IAM, and when to upgrade. Managed node groups leave sizing, autoscaling and add-ons to you.
