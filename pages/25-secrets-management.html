Secrets Management

"How do you handle secrets?" comes up in nearly every DevOps interview. This lesson explains why secrets need special care, the three common options on AWS (Parameter Store, Secrets Manager and HashiCorp Vault), and how to choose between them with a confident, cost-aware answer.

What counts as a secret?

A secret is any piece of information that would let someone do damage if it leaked. As a DevOps engineer you handle them all the time:

  • CI/CD: container registry username, password and URL, used to push images. Leaked: someone deletes your images or pushes a malicious one.
  • Databases: DB usernames and passwords. Leaked: someone reads or deletes your data.
  • Automation tools: Ansible or Terraform need AWS credentials. Leaked: someone controls your cloud account.
  • Apps: third-party API tokens, certificates and private keys.

Secrets management means storing these values in one protected place, encrypting them, controlling exactly who and what can read them, auditing access, and changing them regularly. That way they never need to sit in code, Git repos, or plain-text config files. A single leak can hurt the whole organisation, which is why this is a core DevOps responsibility.

Watch outThe classic mistake is hard-coding a password in a script or committing a .env file to Git. Even if you delete it later, it stays in the Git history. Treat any leaked secret as compromised and change it.

The three options

SSM Parameter Store

Part of AWS Systems Manager. A simple, hierarchical key-value store for configuration and secrets. Values can be encrypted with KMS. Standard parameters are free.

AWS Secrets Manager

A dedicated AWS secrets service. Its headline feature is automatic rotation. Costs more, per secret per month.

HashiCorp Vault

Not an AWS service. A specialised, cloud-agnostic secrets platform you install and run yourself (or buy as HashiCorp's managed cloud service). Works across AWS, Azure, GCP and on-premises.

Systems Manager Parameter Store

Parameter Store holds values under path-like names such as /myapp/prod/docker/username. Each parameter has a type:

  • String: plain text, e.g. a registry URL.
  • StringList: comma-separated values.
  • SecureString: encrypted with an AWS KMS key. Use this for anything sensitive.
# store values
aws ssm put-parameter --name /myapp/docker/registry-url --type String \
  --value "docker.io"
aws ssm put-parameter --name /myapp/docker/username --type String \
  --value "myuser"

# read a SecureString (decrypted)
aws ssm get-parameter --name /myapp/db/password --with-decryption \
  --query Parameter.Value --output text

Access is controlled by IAM: give the service that needs the value (CodeBuild, EC2, Lambda…) an IAM role allowed to read those parameter paths. In Lesson 16, CodeBuild reads Docker credentials from Parameter Store exactly this way. It's easy to use and easy to integrate.

AWS Secrets Manager

If Parameter Store can hold encrypted values, why does Secrets Manager exist? Mainly for rotation.

What is rotation?

Rotation means automatically replacing a secret with a new one on a schedule, say every 90 days. Even if an old password or certificate leaks, it stops working soon after, so the window of risk shrinks.

Think of it like…A hotel that re-codes every room key card at checkout. If a guest keeps their card, it's useless the next day. Rotation does the same for passwords.
  • Built-in rotation for supported databases such as Amazon RDS, Aurora and Redshift: Secrets Manager changes the password in the database and in the secret together.
  • Custom rotation for anything else (API tokens, other systems): you supply a Lambda function with your own rotation logic, and Secrets Manager runs it on schedule.
  • Apps always fetch the current value at runtime, so they keep working after rotation.
  • Extra features: cross-region replication of secrets, resource policies, and fine-grained auditing through CloudTrail.
# create a secret (JSON is common for DB credentials)
aws secretsmanager create-secret --name prod/db/credentials \
  --secret-string '{"username":"admin","password":"S3cure!Pass"}'

# read it
aws secretsmanager get-secret-value --secret-id prod/db/credentials \
  --query SecretString --output text

# rotate every 90 days using a rotation Lambda
aws secretsmanager rotate-secret --secret-id prod/db/credentials \
  --rotation-lambda-arn arn:aws:lambda:us-east-1:123456789012:function:my-rotator \
  --rotation-rules AutomaticallyAfterDays=90

The trade-off is price. Secrets Manager charges per secret per month (around $0.40) plus API calls. Standard Parameter Store parameters cost nothing to store. A few secrets cost very little either way, but organisations have thousands. Check the AWS pricing page for current numbers.

The smart combo: use both

You don't have to pick one. A cost-aware strategy is to sort secrets by how sensitive they are:

  • Important but not highly sensitive (useless on their own): usernames, registry URLs, config. Use Parameter Store.
  • Highly sensitive or needs rotation: passwords, DB credentials, API tokens. Use Secrets Manager.

Example: a CodePipeline/CodeBuild job pushes images to a container registry. It needs a username, password and registry URL. A leaked username alone can't do anything without the password.

In a CodeBuild buildspec.yml, both stores plug straight into environment variables:

version: 0.2
env:
  parameter-store:
    REGISTRY_URL: /ci/registry-url
    DOCKER_USERNAME: /ci/username
  secrets-manager:
    DOCKER_PASSWORD: ci/registry:password   # secret-id:json-key
phases:
  build:
    commands:
      - echo "$DOCKER_PASSWORD" | docker login -u "$DOCKER_USERNAME" --password-stdin "$REGISTRY_URL"

The CodeBuild service role needs ssm:GetParameters for the parameters and secretsmanager:GetSecretValue for the secret (plus kms:Decrypt if you use a customer-managed key).

Why would anyone use HashiCorp Vault?

If AWS offers two services, why add a third-party tool? Because AWS-managed services tie you to AWS.

  • Multi-cloud and hybrid: if your company runs on AWS and Azure, or on-prem too, or might migrate later, secrets locked in AWS services become a migration headache. Vault is one central store that works everywhere.
  • Specialist features: Vault has been a dedicated secrets tool for years. It offers things like dynamic secrets (it creates short-lived DB credentials on demand), encryption-as-a-service and many authentication methods.
  • Large community: it grew up as an open-source project with broad community use and integrations. (HashiCorp moved Vault to a source-available licence in 2023, and the community fork OpenBao stays fully open source.)
  • The cost: if you self-host it, you install, secure, back up, upgrade and keep it highly available. That's real operational work.

Check yourself

Which feature is the main reason to choose Secrets Manager over Parameter Store?
Secrets Manager can rotate secrets on a schedule (built-in for RDS and similar, or via a custom Lambda). Neither AWS service works outside AWS.
Your company runs apps on AWS and Azure and wants one place for all secrets. What fits best?
Vault is cloud-agnostic, so one central store serves every platform. AWS's services only work inside AWS.
A pipeline needs a registry username, a registry URL and a password. What's the cost-aware split?
Low-sensitivity values go in cheap Parameter Store. The password, which actually grants access, gets Secrets Manager's extra protection and rotation. Never hard-code secrets.

Key takeaways

  • Secrets (passwords, tokens, keys, credentials) must never live in code or Git. Store them centrally and control access with IAM.
  • Parameter Store: simple, cheap (standard tier free), SecureString for encryption. Great for config and low-sensitivity values.
  • Secrets Manager: built for highly sensitive secrets, with automatic rotation (RDS built-in, Lambda for custom). Costs more.
  • Use both together, split by sensitivity, to balance security and cost.
  • HashiCorp Vault is for multi-cloud or hybrid setups and advanced features, but you operate it yourself.
