Project: Kubernetes on EKS

Kubernetes is the most requested skill in DevOps job posts. In this project you'll learn what EKS manages for you, the core Kubernetes objects (pods, deployments, services, ingress), and then deploy the 2048 game on an EKS cluster with Fargate, exposed to the internet through an Application Load Balancer created by the AWS Load Balancer Controller.

Why orchestrate containers at all, and how ECS compares with EKS, is covered in Lesson 23: ECS. Container images and ECR are in Lesson 22.

Kubernetes in two halves

Every Kubernetes cluster has two parts:

  • Control plane (the "master nodes", the brain). Its parts: the API server (the front door, which every kubectl command talks to), etcd (the database holding cluster state), the scheduler (decides which node runs each pod), the controller manager (keeps reality matching what you asked for), and the cloud controller manager (talks to the cloud provider).
  • Data plane (the "worker nodes", the muscle). This is where your apps actually run. Each node runs kubelet (starts and watches pods), kube-proxy (networking rules), a container runtime, plus a network plugin (CNI) and cluster DNS.

For high availability, production clusters usually run three control-plane nodes.

The pain of doing it yourself

On plain EC2 you'd launch, say, six instances (three masters, three workers), install all the control-plane parts with kubeadm, install a CNI, container runtime, DNS and kube-proxy on the workers, then join them to the cluster. Tools like kops automate the setup, but day-2 problems are still yours:

  • A master node dies, or the API server becomes slow or unresponsive.
  • etcd crashes, and you need backups and restores.
  • Certificates expire and must be renewed and re-attached.
  • Now multiply that by tens or hundreds of clusters.

What EKS does for you

Amazon EKS (Elastic Kubernetes Service) is a managed control plane. You ask for a cluster, and AWS runs a highly available control plane you never see: no master nodes to patch, no etcd to babysit, no certificates to renew. It's backed by an AWS service level agreement (SLA).

EKS manages the control plane, not fully the data plane. For worker capacity you choose:

EC2 node groups

Your own instances, joined to the cluster. Use these when you need a specific OS (e.g. RHEL), instance type or configuration. You handle auto scaling, health and patching (managed node groups help).

Fargate

AWS's serverless compute for containers. Each pod runs on capacity AWS provides, so there are no nodes to manage. Combined with EKS, AWS runs both the control plane and the compute.

Interview angle"Why EKS instead of self-managed Kubernetes?" Because the control plane is the hardest part to operate: etcd, API server health, upgrades, certificates. EKS makes that AWS's job (with an SLA), so the team focuses on applications. Ways to run Kubernetes on AWS: DIY on EC2 (kubeadm/kops), or EKS. On-premises you'd install it on your own data-centre servers.

Core Kubernetes objects you'll use

ObjectWhat it does
PodThe smallest deployable unit: one (or a few tightly coupled) containers with their resources and settings, described in YAML.
DeploymentManages a set of identical pods: keeps replicas: 5 running, replaces failed ones, rolls out new versions.
ServiceA stable name/IP in front of changing pods. It finds pods using labels and selectors.
IngressRules for HTTP traffic from outside: "requests for example.com/abc go to service X".
Ingress controllerThe program that reads Ingress rules and configures a real load balancer to follow them.
NamespaceA folder-like boundary to group resources, e.g. game-2048, kube-system.
Service accountAn identity for pods. On EKS it can be linked to an IAM role.

Getting traffic in: the three Service types

A pod on its own only has a cluster-internal IP. Users outside can't reach it. A Service offers three modes:

TypeWho can reach the appCatch
ClusterIP (default)Only things inside the clusterNot reachable from outside
NodePortAnyone who can reach a node's IP on a high portNodes sit in private subnets, so only things inside the VPC can reach them
LoadBalancerThe internet, via a cloud load balancerOne load balancer per service. With hundreds of microservices, that's a big bill.

The better pattern is Ingress: keep services as ClusterIP/NodePort, write an Ingress per app, and let one ingress controller manage the load balancer(s) for all of them.

Ingress vs ingress controller

An Ingress resource by itself does nothing. It's just rules written down. Someone has to read them and act. That's the ingress controller: NGINX, F5 and many others each have one, usually installed with a Helm chart. On AWS we use the AWS Load Balancer Controller: it watches for Ingress resources and creates and configures an Application Load Balancer (listeners, target groups, rules, security groups) to match them.

Think of it like…The Ingress is a written seating plan for a wedding. The ingress controller is the usher who reads the plan and actually walks guests to their tables. A plan with no usher seats nobody.
NoteIf you run several controllers (say NGINX and ALB) in one cluster, the ingressClassName field says which one should handle each Ingress.
What an Application Load Balancer is, and how it differs from NLB, is explained in Lesson 28: Load Balancers.

IAM for pods: OIDC and service accounts

On EC2, when an app needs S3 access you attach an IAM role to the instance. Pods need the same, at the pod level. The ALB controller, for instance, is just a pod that must call AWS APIs to create load balancers.

  • Every EKS cluster has an OpenID Connect (OIDC) provider URL. OIDC is a standard way to trust identities from another system, like "Log in with Google" on a website.
  • You associate that OIDC provider with IAM, so IAM trusts identities issued by your cluster.
  • Then you link an IAM role to a Kubernetes service account. Any pod using that service account gets the role's permissions. This is called IRSA (IAM Roles for Service Accounts).

In real teams, developers say "my service needs RDS access", and the DevOps engineer creates a service account bound to a role with exactly those permissions.

Fargate profiles

With Fargate there are no nodes, so how does EKS know which pods to run on Fargate? A Fargate profile lists namespaces (and optionally labels). Pods created in those namespaces run on Fargate. A new cluster made with --fargate gets a profile for default and kube-system. To deploy into another namespace, you add a profile for it. Pods in a namespace with no profile stay Pending.

Hands-on: deploy the 2048 game

Watch out: costEKS charges per cluster per hour, and the ALB, NAT gateway and Fargate pods cost extra. Run the cleanup step as soon as you finish. The demo uses a root account for simplicity. At work, use an IAM user/role with the needed permissions.

Prerequisites

  • kubectl: the Kubernetes command line (install from the Kubernetes docs).
  • eksctl: a command-line tool for creating and managing EKS clusters (on macOS: brew install eksctl).
  • AWS CLI, configured with aws configure (see Lesson 12).
  • helm: the Kubernetes package manager, used to install the controller.

1. Create the cluster

eksctl create cluster --name demo-cluster --region us-east-1 --fargate

You could click through the console, but it asks for IAM roles, VPC, subnets and more. In companies, eksctl (or IaC tools) is preferred. Behind the scenes it uses CloudFormation to create a new VPC with public and private subnets, the control plane and a Fargate profile. Expect 10–20 minutes.

When it's done, the console shows the cluster. The Resources tab lets you browse pods, deployments and more without kubectl. The Overview shows the API server endpoint and the OIDC provider URL.

2. Point kubectl at the cluster

aws eks update-kubeconfig --name demo-cluster --region us-east-1

This writes the cluster's connection details into your ~/.kube/config.

3. Add a Fargate profile for the app's namespace

eksctl create fargateprofile \
  --cluster demo-cluster --region us-east-1 \
  --name alb-sample-app --namespace game-2048

4. Deploy the app: namespace, deployment, service, ingress

kubectl apply -f https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.5.4/docs/examples/2048/2048_full.yaml

This one file (from the official AWS example) creates the game-2048 namespace, a Deployment with 5 replicas, a Service and an Ingress. The key parts:

# Service: finds pods by label, forwards port 80 to the container's port 80
apiVersion: v1
kind: Service
metadata:
  namespace: game-2048
  name: service-2048
spec:
  type: NodePort
  selector:
    app.kubernetes.io/name: app-2048   # must match the pod labels
  ports:
    - port: 80
      targetPort: 80                   # the container port
      protocol: TCP
---
# Ingress: "send all HTTP traffic to service-2048"
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  namespace: game-2048
  name: ingress-2048
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb                # handled by the AWS LB Controller
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: service-2048
                port:
                  number: 80

Check what got created:

kubectl get pods -n game-2048        # 5 pods, Pending → Running
kubectl get svc -n game-2048         # NodePort with a cluster IP, no external IP
kubectl get ingress -n game-2048     # class "alb", but ADDRESS is empty!

The empty ADDRESS proves the point: there's no ingress controller yet, so nothing has acted on the Ingress.

Tiptarget-type: ip tells the ALB to send traffic straight to pod IPs. It's required on Fargate, because there are no EC2 nodes to send NodePort traffic to.

5. Connect IAM to the cluster (OIDC)

eksctl utils associate-iam-oidc-provider --cluster demo-cluster --approve

This is the same as Authentication → Associate identity provider in the console. Without it, the next steps fail.

6. Create the IAM policy and service account for the controller

curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.5.4/docs/install/iam_policy.json

aws iam create-policy \
  --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

eksctl create iamserviceaccount \
  --cluster=demo-cluster \
  --namespace=kube-system \
  --name=aws-load-balancer-controller \
  --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn=arn:aws:iam::<YOUR_ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

The policy JSON comes from the controller's official docs, so you don't write it yourself. The last command creates an IAM role and a Kubernetes service account linked to it (IRSA). Replace the account ID with yours.

7. Install the AWS Load Balancer Controller with Helm

helm repo add eks https://aws.github.io/eks-charts
helm repo update eks

helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system \
  --set clusterName=demo-cluster \
  --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=us-east-1 \
  --set vpcId=<YOUR_VPC_ID>

Find the VPC ID on the cluster's Networking tab. serviceAccount.create=false tells Helm to reuse the IAM-linked service account from step 6. Then verify:

kubectl get deployment -n kube-system aws-load-balancer-controller
# wait until READY shows 2/2 (two replicas for availability)

8. Play

kubectl get ingress -n game-2048
# ADDRESS: k8s-game2048-ingress2-xxxxxxxx.us-east-1.elb.amazonaws.com

The controller saw the Ingress and created an ALB named like k8s-game2048-… (see EC2 → Load Balancers). Wait until its state is Active (2–4 minutes), then open the address with http:// in your browser. The 2048 game appears.

Troubleshooting: controller stuck at 0/2 ready

Run kubectl describe deploy aws-load-balancer-controller -n kube-system (or look at the status in kubectl edit deploy …). A common error is "error looking up service account kube-system/aws-load-balancer-controller". That means step 6 didn't really create the service account, often because a leftover CloudFormation stack from an earlier attempt exists.

  • Delete the old eksctl-…-iamserviceaccount-… stack in CloudFormation, then rerun step 6 (adding --override-existing-serviceaccounts if needed).
  • If Helm says "cannot reuse a name that is still in use", run helm uninstall aws-load-balancer-controller -n kube-system and install again.
  • If helm install complains about unexpected arguments, check for stray spaces after the \ line breaks.

9. Clean up

kubectl delete -f https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.5.4/docs/examples/2048/2048_full.yaml
eksctl delete cluster --name demo-cluster --region us-east-1

Delete the app first so the controller removes the ALB it created. Otherwise the leftover ALB can block VPC deletion and keep costing money.

What you just built

This is how it works in organisations: for each microservice, the DevOps engineer writes deployment.yaml, service.yaml and ingress.yaml. Installing the ingress controller is a one-time job per cluster, and from then on it creates and updates load balancers automatically. On EKS the only extra wiring is IAM (OIDC + service account). On a self-managed cluster you'd give the controller permissions through Kubernetes RBAC instead.

Check yourself

You applied an Ingress, but kubectl get ingress shows no ADDRESS. What's the most likely cause?
An Ingress is just rules. Without a controller (like the AWS Load Balancer Controller), no load balancer gets created, so there's no address.
What does EKS manage for you?
EKS is a managed, highly available control plane. Worker capacity comes from EC2 node groups or Fargate, and your app manifests are still yours.
Why do we associate an IAM OIDC provider before installing the ALB controller?
OIDC lets IAM trust the cluster's service accounts (IRSA). The controller needs AWS permissions to create load balancers and target groups.

Key takeaways

  • EKS = AWS runs the Kubernetes control plane. You choose EC2 node groups or Fargate for the data plane.
  • Pod → Deployment (replicas) → Service (stable address via labels/selectors) → Ingress (HTTP routing rules).
  • An Ingress needs an ingress controller. On AWS, the AWS Load Balancer Controller turns Ingress rules into an ALB.
  • Pods get AWS permissions through IAM OIDC + service accounts (IRSA). Fargate needs a Fargate profile per namespace.
  • Tooling: eksctl to create clusters, aws eks update-kubeconfig, kubectl, and helm. Always delete demo clusters.
