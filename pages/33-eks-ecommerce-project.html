Project: E-Commerce App on EKS

Deploy Robot Shop, a demo online store made of many microservices and several databases, onto Amazon EKS. You'll see how a three-tier app maps to Kubernetes, why microservices exist, and which extra AWS plumbing a real cluster needs.

This is a hands-on project. The three-tier idea is explained in Lesson 32, and Kubernetes objects (pods, deployments, services, ingress), OIDC and the AWS Load Balancer Controller are covered in Lesson 24: EKS. This page focuses on what's new.

The project: Robot Shop

Robot Shop is an open-source demo store (originally built by IBM's Instana team to show off monitoring) that sells robots and AI products. It behaves like a real shop: register, log in, browse a catalogue, see ratings, add to cart, calculate shipping, pay, and get an order ID.

It's a great learning project because:

  • It's split into many small services, each written in a different language (Node.js, Java, Python, PHP, Go). You get to see a Dockerfile for each kind of app.
  • It uses several data stores: MongoDB, MySQL, Redis and RabbitMQ.
  • The flow (catalogue → cart → shipping → payment) is the same one Amazon or Flipkart uses, so the high-level design carries over to real shops.

Its three tiers: the presentation tier is the web UI (AngularJS served by Nginx), the logic tier is the set of microservices, and the data tier is the databases.

Monolith vs microservices

Catalogue, ratings, cart, payment and shipping all need their own code. Developers can package it in two ways:

Monolith

All features in one application / one binary. Simple at first, but a change to the catalogue can break payments, so QA has to re-test everything (regression testing) on every release.

Microservices

Each feature is a separate service with its own API, deployed on its own. The catalogue team changes and tests only the catalogue. Large companies run hundreds or thousands of these.

Each microservice can use the language that suits it best. A company might write 998 services in Go and two in Python. Robot Shop uses many languages on purpose, for teaching. In a real company each service would usually live in its own Git repository; Robot Shop keeps them in one repo because it's small.

Think of it like…A food court instead of one giant kitchen. Each stall (service) has its own staff and menu. If the pizza stall changes its recipe, the noodle stall keeps cooking unaffected.

That adds up to 12 components: web, 7 microservices, 2 databases, Redis and RabbitMQ. Each one gets its own Kubernetes Deployment (or StatefulSet) and Service.

  • Why Redis for the cart? If you add an item, log out and come back days later, the item should still be there. Keeping the cart only in the app's own memory would lose it whenever the pod restarts. Redis is an in-memory data store: very fast, and it can save its data to disk. Run it as a StatefulSet with a persistent volume and the cart survives restarts. (Caching in general: Lesson 39.)
  • Why two databases? MongoDB (document DB) and MySQL (relational DB) are both used so you can practise deploying each kind on Kubernetes. A real app could use just one.
  • Why RabbitMQ? It's a message queue. When you pay, the payment service drops the order into a queue and returns right away. The dispatch service picks orders up in the background. If dispatch is slow or down, orders wait in the queue instead of being lost.

Why EC2 nodes instead of Fargate? Two reasons. The Redis pod is given the extra Linux privilege NET_ADMIN, which Fargate doesn't allow, and Fargate pods can't mount EBS volumes. Stateful workloads like this need EC2 nodes.

Persistent storage: StatefulSet → PVC → EBS

A normal pod loses its files when it's replaced. Redis needs its data to survive, so it runs as a StatefulSet, a Kubernetes object for stateful apps that gives each pod a stable name and its own disk. The pieces:

  • PersistentVolumeClaim (PVC): the pod's request: "I need 1 GiB of disk."
  • StorageClass: describes how to make that disk (on AWS: an EBS volume of type gp2/gp3).
  • EBS CSI driver: the add-on that actually calls AWS to create the EBS volume and attach it to the node. Without it, the PVC stays Pending forever.

Helm in one minute

Helm is a package manager for Kubernetes. A Helm chart is a folder with:

  • Chart.yaml: the chart's name and version.
  • values.yaml: settings you might change, such as the image repository and tag.
  • templates/: the Kubernetes YAML files (a Deployment + Service per component), with placeholders filled in from values.yaml.

Why bother? Robot Shop has 12+ manifests that all pull images from the same repository. To switch every image to a new repo or version, you change one line in values.yaml instead of editing 12 files. One helm install deploys everything.

Step-by-step deployment

Prerequisites: kubectl, eksctl, helm and the AWS CLI installed and configured. Start the cluster first, because it takes 15–20 minutes.

  1. Create the cluster (EC2 nodes). 
    eksctl create cluster --name demo-cluster-robot-shop --region us-east-1
    If the default region of your AWS CLI differs from the cluster's region, later commands fail with confusing "not found" errors. Run aws configure and set the same region, or pass --region everywhere.
  2. Connect the cluster to IAM (OIDC provider). This lets Kubernetes service accounts use IAM roles, so pods like the load balancer controller and the EBS CSI driver can call AWS APIs. 
    export cluster_name=demo-cluster-robot-shop
oidc_id=$(aws eks describe-cluster --name $cluster_name \
  --query "cluster.identity.oidc.issuer" --output text | cut -d '/' -f 5)
aws iam list-open-id-connect-providers | grep $oidc_id   # empty = not created yet
eksctl utils associate-iam-oidc-provider --cluster $cluster_name --approve
  3. Install the AWS Load Balancer Controller. It watches Ingress objects and creates ALBs for them. Create the IAM policy, a service account linked to an IAM role, then install with Helm: 
    curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.5.4/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
  --policy-document file://iam_policy.json

eksctl create iamserviceaccount --cluster=$cluster_name --namespace=kube-system \
  --name=aws-load-balancer-controller --role-name AmazonEKSLoadBalancerControllerRole \
  --attach-policy-arn=arn:aws:iam::<ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
  --approve

helm repo add eks https://aws.github.io/eks-charts
helm repo update eks
helm install aws-load-balancer-controller eks/aws-load-balancer-controller -n kube-system \
  --set clusterName=$cluster_name --set serviceAccount.create=false \
  --set serviceAccount.name=aws-load-balancer-controller \
  --set region=us-east-1 --set vpcId=<VPC_ID>

kubectl get deployment -n kube-system aws-load-balancer-controller
    Find the VPC ID under your cluster's Networking tab. Wait until the controller pods are running before moving on. It installs in kube-system because one controller watches all namespaces.
  4. Install the EBS CSI driver add-on, so Redis (and the databases) can get EBS volumes: 
    eksctl create iamserviceaccount --name ebs-csi-controller-sa --namespace kube-system \
  --cluster $cluster_name --role-name AmazonEKS_EBS_CSI_DriverRole --role-only \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve

eksctl create addon --name aws-ebs-csi-driver --cluster $cluster_name \
  --service-account-role-arn arn:aws:iam::<ACCOUNT_ID>:role/AmazonEKS_EBS_CSI_DriverRole --force
  5. Deploy Robot Shop with Helm. From the project's EKS/helm folder: 
    kubectl create ns robot-shop
helm install robot-shop --namespace robot-shop .
kubectl get pods -n robot-shop      # wait until all pods are Running (can take 5–10 min)
  6. Expose the web UI with an Ingress. The web Service listens on port 8080; the Ingress tells the controller to put an internet-facing ALB in front of it: 
    apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: robot-shop
  namespace: robot-shop
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing
    alb.ingress.kubernetes.io/target-type: ip
spec:
  ingressClassName: alb
  rules:
    - http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: web
                port:
                  number: 8080
    kubectl apply -f ingress.yaml
kubectl get ingress -n robot-shop
    In the EC2 console under Load Balancers, wait for the new ALB to change from Provisioning to Active, then open its DNS name in the browser.
  7. Test every workflow: register, log in, browse, rate, add to cart, ship, pay, get an order ID.
  8. Clean up. EC2 nodes, EBS volumes and ALBs cost money: 
    eksctl delete cluster --name $cluster_name --region us-east-1
Watch outeksctl create iamserviceaccount works through a CloudFormation stack. If it fails, a retry will keep failing until you delete the failed stack in the CloudFormation console. Also, commands copied from Markdown sometimes get "smart" dashes; if a flag is rejected, retype the --.
TipA Service of type LoadBalancer also exposes an app, but you get one load balancer per service. Ingress + ALB controller is the more common approach: one ALB can route to many services by path or host.

What about CI/CD?

Once you understand the architecture and the Dockerfiles, a pipeline is straightforward. The key rule: one CI/CD pipeline per microservice. Robot Shop would need about 12. One pipeline for everything defeats the purpose of deploying independently. Likewise, a real setup would usually have a Helm chart per service rather than one big chart. Practise by building one pipeline, for example for the Go dispatch or Python payment service. (CI/CD concepts)

Interview angle"Why is Redis a StatefulSet, and how does it get storage on EKS?" Answer: a StatefulSet gives stable identity and a dedicated volume. The PVC is fulfilled by a StorageClass backed by the EBS CSI driver, which uses an IAM role (via OIDC/IRSA) to create and attach the EBS volume.

Check yourself

Why did this project use EC2 worker nodes instead of Fargate?
Fargate pods can't mount EBS volumes or get extra privileges like NET_ADMIN. Ingress works fine with Fargate; Lesson 24 used it.
A PVC for Redis stays in Pending forever. What's the most likely missing piece?
Without the EBS CSI driver, nothing creates the EBS volume the StorageClass asks for, so the claim is never fulfilled.
What is the main benefit of microservices over a monolith?
Independent deployment is the point. Services can share a language or not; that's up to the team.

Key takeaways

  • Robot Shop = web UI (presentation) + 7 microservices (logic) + MongoDB, MySQL, Redis, RabbitMQ (data): a realistic three-tier e-commerce app.
  • Microservices are deployed independently, so a change to one feature doesn't force re-testing the whole app.
  • Stateful pods need EC2 nodes, a StatefulSet, and the EBS CSI driver to turn PVCs into EBS volumes.
  • Setup order: cluster → OIDC → ALB controller → EBS CSI driver → helm install → Ingress → test → delete the cluster.
  • Helm keeps shared settings (image repo, versions) in values.yaml. In production, use one pipeline (and usually one chart) per microservice.
