VPC: Your Private Network

A VPC (Virtual Private Cloud) is your own fenced-off network inside AWS. In this lesson you'll learn why it exists, what its parts are (IP ranges, subnets, internet gateway, route tables, NAT gateway), and how a request from the internet finds its way to your server.

Why do we need a VPC?

Picture a big piece of land in a village. A clever builder buys it and offers a deal to people who don't want to build or maintain their own homes: "Tell me what you need, pay me, and I'll build and look after the house for you."

Business is good — but to save money the builder puts all the houses right next to each other with no walls between them. If a burglar gets into one house, it's easy to walk into the next one. The careful customers complain, so the builder invents something better: a gated community.

  • Each group of houses gets its own fenced property.
  • There is a single gate where visitors come in.
  • Inside, signposts tell visitors which path leads to which house.
  • At each house a guard checks: "Are you really allowed to see this person?"
Think of it like…AWS is the builder. Its data centers are the land. In the early days, servers from many different companies could sit side by side with weak separation, so one hacked customer was a risk to others. The VPC is the gated community: a logically isolated network that belongs only to you. The gate is the internet gateway, the signposts are route tables, and the guards are security groups.

Unlike the builder story, AWS doesn't design your community for you. AWS gives you the building blocks and documentation; DevOps engineers are the ones who create and configure the VPC for their project.

NoteEvery AWS account comes with a default VPC in each region so you can launch an EC2 instance straight away (that's what happened in Lesson 4). Real companies almost always build their own custom VPCs so they control every setting.

Sizing a VPC: IP ranges and CIDR

Land is measured in acres. A VPC is measured in IP addresses — every server, load balancer and database inside it needs one. When you create a VPC, AWS asks for an IP address range, written in CIDR notation (Classless Inter-Domain Routing), for example 10.0.0.0/16.

  • An IPv4 address has 32 bits, written as four numbers (10.0.0.0).
  • The number after the slash says how many of those bits are fixed. The rest can change, and each combination is one address.
  • So /16 leaves 16 free bits → 216 = 65,536 addresses. /24 leaves 8 free bits → 28 = 256 addresses.
  • Smaller number after the slash = bigger network.

AWS lets a VPC (and a subnet) be anywhere from /16 (largest) to /28 (16 addresses, smallest). Inside every subnet AWS keeps 5 addresses for itself (the network address, the VPC router, DNS, one reserved for future use, and the broadcast address), so a /24 subnet gives you 251 usable IPs.

TipPick a size with room to grow. You can add extra ranges to a VPC later, but it's extra work. Private ranges such as 10.x.x.x, 172.16–31.x.x and 192.168.x.x are the usual choices.

Subnets: splitting the VPC

One project usually has several smaller parts — say payments, transactions and reporting. Instead of throwing everything into one big pool, you split the VPC's range into smaller ranges called subnets (short for sub-networks). For example, inside 172.16.0.0/16:

SubnetRangeAddresses
Payments172.16.1.0/24256
Transactions172.16.2.0/24256
Reporting172.16.3.0/24256

Each subnet lives in a single Availability Zone, and you launch EC2 instances into a subnet. Subnets come in two flavours:

Public subnet

Reachable from the internet. Its route table sends internet traffic to the internet gateway. This is where you put things the outside world should talk to first: load balancers and NAT gateways.

Private subnet

No direct route from the internet. Your application servers and databases live here, so nobody outside can reach them directly. Best practice: apps go in private subnets.

The main building blocks

Internet gateway (IGW)

The gate of the gated community. An internet gateway is attached to the VPC and is the only way traffic can move between your VPC and the public internet. No IGW = nobody from outside can get in, and nothing inside can reach out directly.

Route tables

The signposts. A route table is a list of rules that says "traffic going to this destination, send it there". At home your Wi-Fi router does the same job, and on the internet your request hops through many routers. In AWS each subnet is associated with a route table.

  • Every route table has a local route for the VPC's own range, so subnets in the same VPC can talk to each other.
  • A public subnet's table adds 0.0.0.0/0 → igw-… ("anything else, send to the internet gateway").
  • A private subnet's table has no route to the IGW (it may have 0.0.0.0/0 → nat-…, see below).
NoteA subnet isn't "public" because of a checkbox. It's public because its route table points to an internet gateway. Remove that route and it becomes private.

Load balancer

Users don't hit your servers directly. A load balancer sits in the public subnet, receives every request and passes it to a healthy server in the private subnet. You tell it which servers to use with a target group. Load balancers get a full lesson later in Lesson 28.

Security groups (and NACLs)

The guard at the door. Even after a request reaches the right subnet, the server's security group can still refuse it — for example "only allow port 8080". There is also a second guard at the subnet level called a NACL.

Security groups, NACLs, and how they differ are covered in Lesson 7: Security Groups vs NACLs.

In short, an incoming request goes:

  1. Internet gateway — the request enters the VPC.
  2. Public subnet — its route table connects it to the IGW, so the request reaches the load balancer.
  3. Route table — the local route lets the load balancer reach the private subnet.
  4. Security group — checks the port and source IP. If allowed…
  5. EC2 instance — the application finally gets the request.

NAT gateway: going out without being seen

So far traffic came in. But servers in a private subnet often need to go out — to download a package, apply security updates or call another company's API. They have no route to the IGW, so how?

Also, it's bad practice to reveal your private servers' IP addresses to the outside world. If the website you call is ever compromised, an attacker would learn where your servers are.

The answer is a NAT gateway (Network Address Translation):

  • It lives in the public subnet and has its own public IP (an Elastic IP).
  • The private subnet's route table says 0.0.0.0/0 → nat-….
  • When a private server sends a request, the NAT gateway swaps the private source IP for its own public IP (this is "IP masking"), sends it out through the IGW and passes the reply back.
  • It only allows connections that start inside. Nobody on the internet can start a connection to your private server through it.
Think of it like…A company mailroom. Employees hand letters to the mailroom, which sends them out with the company's return address. Replies come back to the mailroom and get delivered inside. Outsiders never learn which desk the letter came from.

VPC flow logs

When something doesn't work ("why can't users reach my app?"), you want to see the traffic. VPC flow logs record information about the IP traffic going to and from network interfaces in your VPC: who talked to whom, on which port, and whether it was accepted or rejected. They are great for debugging and security audits. Note that flow logs (and NAT gateways) cost money, while the VPC itself, subnets, route tables and the internet gateway are free.

Key takeaways

  • A VPC is your own isolated network in AWS — the "gated community" for your servers.
  • Its size is a CIDR range: /16 = 65,536 IPs, /24 = 256. AWS reserves 5 IPs per subnet.
  • Subnets split the range. Public subnets hold load balancers and NAT gateways; private subnets hold your apps.
  • The internet gateway is the door; route tables are the signposts; security groups are the guards.
  • A NAT gateway lets private servers reach the internet while hiding their IPs.
  • VPC flow logs record traffic so you can debug and audit.
