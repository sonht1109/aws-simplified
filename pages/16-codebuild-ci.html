Project: CI with CodeBuild

Build a real continuous integration pipeline: every commit to GitHub automatically builds a Docker image of a Python app and pushes it to Docker Hub, using AWS CodeBuild and CodePipeline. You'll also see the errors you're likely to hit, and how to fix each one.

This is a hands-on project. What CI/CD means is covered in Lesson 14, and how CodePipeline coordinates other services is in Lesson 15. This lesson does only the CI half. The deploy (CD) half comes next in Lesson 17.

What we're building

The goal: a developer pushes code, and with no manual steps a fresh, tested Docker image ends up in a registry, ready to deploy. Four pieces work together:

  • GitHub holds the source code. GitHub is used here instead of CodeCommit because it's what most teams use, and it needs a bit of extra setup.
  • CodePipeline is the orchestrator. It notices the commit and tells the other services to run, in order.
  • CodeBuild does the actual work: installs dependencies, builds the Docker image, pushes it.
  • Systems Manager Parameter Store keeps the Docker Hub username and password out of the code.

The sample application

The app is a tiny Python Flask "hello world" web app. The steps are exactly the same for a big app. The repo folder contains:

  • app.py: the Flask code.
  • requirements.txt: Python dependencies (just flask).
  • Dockerfile: starts from a Python base image, copies requirements.txt, installs it, copies the code, exposes port 5000 and starts Flask.
New to Docker images and registries? The quick primer is in Lesson 22: ECR. Here we push to Docker Hub; ECR is AWS's own registry.

Step 1: Create the CodeBuild project

CodeBuild is a fully managed build service. You don't run any build servers. When a build starts, AWS spins up a fresh build machine, runs your commands, then throws it away. You pay per build minute.

  1. Name and description. In the console, open CodeBuild → Create build project. Give it a clear name (e.g. sample-python-flask-service). In a company you'd name it after the real service, like payments-service. You can leave the concurrent build limit off.
  2. Source. Pick GitHub. CodeBuild supports GitHub, GitHub Enterprise, Bitbucket, CodeCommit and S3. For anything else (e.g. GitLab), you mirror the repo to a supported source, meaning you keep a copy that's updated automatically. Click Connect to GitHub, choose OAuth, and confirm in the pop-up. Then enter your repository.
  3. Environment. This is the machine your build runs on. Choose a managed image, operating system Ubuntu, runtime Standard, and the latest image. In Jenkins you'd have to create and maintain these worker nodes yourself; here AWS provides them ready-made.
  4. Service role. CodeBuild needs permission to call other AWS services. Services get permissions through an IAM role, not an IAM user (users are for people). Let the console create a new service role, or create one in IAM → Roles → Create role → trusted service CodeBuild. You'll add permissions to it later.
  5. Buildspec. Choose Insert build commands → Switch to editor to write the build file in the console (next section). You could also keep buildspec.yml in your repo, which is the more common choice in real teams.
Roles vs users, and why services use roles, are explained in Lesson 3: IAM.

Step 2: Write the buildspec.yml

The buildspec is a YAML file that tells CodeBuild what to run. It's CodeBuild's version of a Jenkinsfile or a GitHub Actions workflow. The editor gives you a commented-out template, so you mostly uncomment what you need.

Your commands go into four phases, which always run in this order:

PhaseWhat goes hereIn this project
installPick language runtimes, install toolsPython 3.11
pre_buildThings needed before building: dependencies, loginspip install -r requirements.txt
buildThe main work: compile, test, build the imagedocker login, build, push
post_buildWrap-up: notifications, extra pushesPrint "build is successful"

You don't need a "checkout" step. CodeBuild clones the source repo for you before install starts.

version: 0.2

env:
  parameter-store:
    DOCKER_REGISTRY_USERNAME: /myapp/docker-credentials/username
    DOCKER_REGISTRY_PASSWORD: /myapp/docker-credentials/password
    DOCKER_REGISTRY_URL: /myapp/docker-registry/url

phases:
  install:
    runtime-versions:
      python: 3.11
  pre_build:
    commands:
      - echo "Installing dependencies..."
      - pip install -r simple-python-app/requirements.txt
  build:
    commands:
      - cd simple-python-app
      - echo "Building Docker image..."
      - echo "$DOCKER_REGISTRY_PASSWORD" | docker login -u "$DOCKER_REGISTRY_USERNAME" --password-stdin "$DOCKER_REGISTRY_URL"
      - docker build -t "$DOCKER_REGISTRY_URL/$DOCKER_REGISTRY_USERNAME/simple-python-flask-app:latest" .
      - docker push "$DOCKER_REGISTRY_URL/$DOCKER_REGISTRY_USERNAME/simple-python-flask-app:latest"
  post_build:
    commands:
      - echo "Build is successful"

A few things to notice:

  • Paths are relative to the repo root. The app lives in a sub-folder (simple-python-app/), so the pip install path and the cd must include it. If your code is at the repo root, drop the folder part.
  • Runtime matches your app. Python app → python. A Java app would use java, a Go app golang.
  • No secrets in the file. The username, password and registry URL are environment variables filled in from Parameter Store at build time.
  • The image tag looks like docker.io/<username>/simple-python-flask-app:latest. That's registry / user / image name : tag.

Step 3: Store credentials in Parameter Store

If you write your Docker Hub password in the buildspec, anyone who can read the file can use your account. Instead, store it in AWS Systems Manager Parameter Store. It plays the same role as Jenkins' credential store or GitHub Actions secrets.

  1. Open Systems Manager → Parameter Store → Create parameter.
  2. Name it with a clear, consistent pattern, for example /myapp/docker-credentials/username. The pattern is app → kind of credential → field. Once you have hundreds of secrets for many services, a naming standard is what lets you find the right one.
  3. Choose type SecureString (encrypted) and keep the default encryption key.
  4. Enter the value. Create three parameters: username, password, and registry URL (docker.io).

In the buildspec's env: parameter-store: block, the left side is the variable name your commands use (you choose it). The right side must match the parameter name exactly, because that's where the value comes from.

When to use Parameter Store, Secrets Manager or Vault (and how rotation works) is covered in Lesson 25: Secrets Management.

Step 4: Run the build and fix the errors

Click Start build. Your first build will very likely fail, and that's normal. Reading the build log and fixing one error at a time is the real skill here. These are the errors you're most likely to see, in roughly the order they show up:

Error in the logWhyFix
Access denied reading the parameters (ssm:GetParameters)The CodeBuild service role isn't allowed to read Parameter Store.IAM → Roles → your CodeBuild role → Add permissions → attach an SSM policy (read-only access is enough; full access is fine only for a throwaway demo).
Could not open requirements file: No such file or directoryThe path in the buildspec doesn't match the repo (e.g. a typo in the folder name).Edit the buildspec with the exact path.
"docker build" requires exactly 1 argumentThe . at the end of docker build is missing. The dot is the build context: "use the Dockerfile and files in this folder".Add the trailing .
Cannot connect to the Docker daemonBy default, CodeBuild build machines aren't allowed to run Docker builds.Edit project → Environment → Override image → tick Privileged.
denied: requested access to the resource is denied on pushThe credentials were loaded but nobody logged in to the registry.Add the docker login line before build/push.
TipRead the build logs even when builds pass. They show exactly what CodeBuild does in each phase, and that makes the next failure much faster to debug.

Once the build succeeds, open Docker Hub, go to your user's repositories and you'll see simple-python-flask-app with a latest tag updated a minute ago.

Step 5: Automate it with CodePipeline

Right now you have to press Start build yourself. To make it real CI, let CodePipeline start CodeBuild whenever someone commits:

  1. CodePipeline → Create pipeline. Give it a name and let it create a new service role.
  2. Source stage: provider GitHub (Version 2). Click Connect to GitHub, name the connection and approve it. This connection is how GitHub tells the pipeline "something changed". Pick the repository and branch main.
  3. Build stage: provider AWS CodeBuild, choose the project you just made, single build.
  4. Deploy stage: skip it for now. It gets added in the CD lesson.
  5. Review and Create pipeline. It runs once straight away.

Now test it: commit any small change to the repo. The pipeline's Source stage turns "In progress", then Build. Click Details to watch the CodeBuild job, and a minute or two later Docker Hub shows the image as "pushed a few seconds ago". No one pressed a button.

Check yourself

Your CodeBuild log says "Cannot connect to the Docker daemon". What do you change?
CodeBuild build machines can't run Docker builds unless the environment is in privileged mode.
Why is the Docker password stored in Parameter Store instead of the buildspec?
The buildspec is usually readable by the whole team, or even public. A SecureString parameter keeps the secret encrypted, and only roles with permission can read it.
In this setup, what does CodePipeline do?
CodePipeline is the orchestrator. CodeBuild does the building, and Docker Hub stores the image.

Key takeaways

  • CodeBuild is a managed build service: AWS provides the build machine, you provide a buildspec.yml.
  • Buildspec phases run in order: install → pre_build → build → post_build. The source checkout happens automatically.
  • Keep secrets in Parameter Store (SecureString) and load them with env: parameter-store:. The CodeBuild service role needs permission to read them.
  • Docker builds in CodeBuild need Privileged mode, a docker login, and the trailing . on docker build.
  • CodePipeline with a GitHub connection makes it real CI: every commit triggers a build automatically.
