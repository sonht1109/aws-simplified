CloudFront: Content Delivery Network

Learn what a CDN is, why every big website uses one, and how to put CloudFront in front of a private S3 bucket so users worldwide get your content fast without ever touching the bucket directly.

The problem: far away means slow

Picture a photo-sharing app. Someone in Australia uploads a photo, and the app stores it in one central place, say a storage system in North Virginia (US). Now a friend in India opens the app to see it.

Without any help, the friend's request has to cross the world and back:

  • The request jumps through many routers on the internet. Each jump is called a hop.
  • More hops and more distance mean more latency, which is the waiting time before data arrives.
  • People near Virginia get photos instantly. People in India, Europe or South America see spinners and buffering.

For apps like Instagram, YouTube or Amazon.com, that slow experience is not acceptable. The fix is a CDN.

What is a CDN?

A CDN (Content Delivery Network) is a worldwide network of servers that keep copies of your content close to your users. You use CDNs every day: every time a reel, product photo or video loads quickly, a CDN is probably serving it.

  • Origin: the "real" home of your content. It could be an S3 bucket, a load balancer, API Gateway, or any web server.
  • Edge location: a CDN data center in a city near your users (Mumbai, Frankfurt, Toronto…). AWS has hundreds of them, many more than it has regions.
  • Cache: the stored copy at the edge. When the edge already has the file, it can answer immediately.

Amazon CloudFront is AWS's managed CDN service. You tell it where your origin is, and it handles the worldwide edge network for you.

Think of it like…A popular book with one copy in a central library. Instead of everyone travelling to that library, the publisher puts copies in every neighbourhood bookshop. The first reader in a neighbourhood may have to wait while a copy is shipped in, but everyone after that picks it up around the corner.

How CloudFront serves a request

  1. A user opens your site. DNS sends them to the nearest edge location (not to your bucket).
  2. The edge checks its cache. If it has a fresh copy, that is a cache hit: it replies right away.
  3. If not, that is a cache miss: the edge fetches the file from the origin, sends it to the user, and keeps a copy.
  4. The next user near that edge (say, someone in Montreal after someone in Toronto) gets a fast cache hit.

Caching and TTL

A cached copy doesn't live forever. Each object has a TTL (Time To Live): how long the edge may keep serving it before checking the origin again. CloudFront's default is 24 hours, and you can change it in the cache settings or from the origin with Cache-Control headers.

  • Long TTL = fewer trips to the origin, faster and cheaper, but users may see an old version for longer.
  • Short TTL = changes appear sooner, but more requests go back to the origin.

If you deploy a new version and can't wait for TTLs to expire, you can create an invalidation to tell every edge to drop its copy:

aws cloudfront create-invalidation \
  --distribution-id E1ABCDEXAMPLE \
  --paths "/index.html" "/css/*"

Using "/*" clears everything. A limited number of invalidation paths each month are free; beyond that, they cost a little.

Why put CloudFront in front of S3?

You can serve a website straight from an S3 bucket by making it public, but that isn't best practice. CloudFront fixes three things at once:

Lower latency

Content is served from the edge closest to each user, no matter which region the bucket lives in.

Better security

The bucket stays private. Users only ever talk to CloudFront, and you can add HTTPS and a web application firewall (AWS WAF) at the edge.

Lower cost at scale

Most requests are answered from cache, so far fewer requests and less data transfer hit S3. For a busy site, this usually costs less than serving everything from S3.

A common setup: an e-commerce app runs on EC2 or Kubernetes, while its images, CSS and JavaScript sit in S3 behind CloudFront. A fully static website can live entirely in S3 + CloudFront.

Origin access: keeping the bucket private

If the bucket blocks all public access, how does CloudFront read from it? You give CloudFront its own identity and allow only that identity in the bucket policy.

  • Origin Access Control (OAC) is the current, recommended way. The bucket policy allows the CloudFront service, but only for your specific distribution.
  • Origin Access Identity (OAI) is the older ("legacy") way. Think of it as a special virtual user, like a functional ID on a Linux server, that is allowed to read the bucket. You'll still see it in older setups and tutorials.

When you choose OAC in the console, CloudFront gives you a policy to paste into the bucket. It looks like this:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipal",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::www.example.com/*",
    "Condition": {
      "StringEquals": {
        "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/E1ABCDEXAMPLE"
      }
    }
  }]
}

In plain words: "Let CloudFront GetObject (read files) from this bucket, but only when the request comes from my distribution."

Hands-on: S3 + CloudFront step by step

Watch out: costCloudFront and WAF are not entirely free. If you practise this, delete the distribution and bucket when you're done. To avoid any cost, you can just read along, or stick to plain S3 static hosting.
  1. Create an S3 bucket. If you plan to use a custom domain, people often name it after the domain (e.g. www.example.com); any unique name works for this demo. Keep Block all public access turned on. Enabling versioning is optional but lets you recover deleted files.
  2. Upload your site files, e.g. index.html and a CSS file. If you open the bucket's own URL now, you get 403 Forbidden. That is what we want.
  3. Create a CloudFront distribution. For Origin domain, pick your bucket from the list. (Load balancers, API Gateway and custom servers can also be origins.)
  4. Origin access: choose Origin access control settings, create a new OAC, and apply the bucket policy CloudFront gives you (as above). Never choose "Public".
  5. Viewer settings: set Redirect HTTP to HTTPS. Leave the default cache policy for now.
  6. WAF: optional extra protection against common web attacks. It costs extra, so you can disable it for a demo.
  7. Price class: "Use all edge locations" if your users are worldwide, or a cheaper class (e.g. North America and Europe) if your customers are only there.
  8. Alternate domain name + SSL certificate (optional): to serve from www.example.com instead of the CloudFront URL, add the name and an HTTPS certificate from AWS Certificate Manager. CloudFront needs that certificate to be created in us-east-1.
  9. Default root object: enter index.html so visiting the bare URL shows your home page.
  10. Create and wait 5–10 minutes while it deploys to the edges. Then open the distribution domain, e.g. https://d111111abcdef8.cloudfront.net. Your site loads. The S3 URL still says 403.
TipWith OAC you don't need S3's "static website hosting" feature: CloudFront reads the files through the normal S3 endpoint, and the default root object handles index.html. If you pick the S3 website endpoint as the origin instead, OAC can't be used and the bucket would have to be public.
NoteTo point your own domain at the distribution, create a Route 53 alias record. DNS records are covered in Lesson 8: Route 53.

Cleanup: a distribution must be disabled first, then deleted once it has finished disabling. Then empty and delete the bucket.

Interview angle"How would you serve static assets globally and securely?" Good answer: private S3 bucket as origin, CloudFront in front with OAC, HTTPS redirect, a sensible TTL plus invalidations on deploy, optional WAF, and a price class that matches where the users are.

Check yourself

A user in Toronto requests an image that someone else in Toronto loaded five minutes ago (TTL is 24 hours). What happens?
The nearby edge already holds a fresh copy, so it answers directly without contacting the origin.
You want the S3 bucket to stay private but still be readable by CloudFront. What do you use?
OAC gives CloudFront an identity, and the bucket policy allows only that distribution to read objects. The bucket stays blocked for everyone else.
You deployed a new index.html, but users still see the old one. What is the quickest fix?
An invalidation tells the edges to drop their cached copy so the next request fetches the new file from the origin.

Key takeaways

  • A CDN keeps copies of your content in edge locations near users, which cuts latency.
  • CloudFront is AWS's CDN. The origin (S3, ALB, API Gateway, any web server) is where the real content lives.
  • Cache hit = served from the edge. Cache miss = fetched from the origin once, then cached for its TTL.
  • Keep the S3 bucket private and let CloudFront in with Origin Access Control (OAI is the legacy way).
  • Use invalidations after deploys, choose a price class for your audience, and delete demo distributions to avoid charges.
