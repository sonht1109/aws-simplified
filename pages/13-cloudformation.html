Infrastructure as Code with CloudFormation

Instead of clicking resources together, you describe them in a YAML file, and AWS CloudFormation builds them for you, the same way every time. You'll learn what Infrastructure as Code means, how a template is laid out, how stacks work, how to catch manual changes with drift detection, and when to choose Terraform instead.

What is Infrastructure as Code?

Developers write code to build apps. Infrastructure as Code (IaC) applies the same idea to servers, networks and storage: you write code (a template) that describes infrastructure, and a tool creates it.

You might say the AWS CLI also uses code. It does, but it doesn't follow the IaC principles. An IaC tool:

  1. Acts as a middleman between you and one or more cloud providers. You hand it a template, and it turns that into the provider's API calls.
  2. Works from templates that are declarative: you describe the end result, not the steps.
  3. Works from templates that are versioned: they live in Git or S3, so you can see what changed 5 or 10 days ago, review changes and audit them.

Imperative (step by step)

"Create a bucket. Now enable versioning. Now add a tag." You give commands in order, like a CLI script. If you run it twice, you may get errors or duplicates.

Declarative (end state)

"There should be one bucket, with versioning on, tagged app1." The tool works out what to create or change. In short: what you see is what you get. Reading the template tells you what exists in AWS.

Think of it like…An architect's blueprint versus shouting instructions at builders. The blueprint can be reviewed, copied and reused for the next house, and anyone can read it to see what the house should look like.

Which tools are IaC?

  • AWS CloudFormation (CFT): AWS only.
  • Azure Resource Manager: Azure only.
  • Terraform, Crossplane: work with many cloud providers.

How CloudFormation works

  • Template: your YAML or JSON file describing resources.
  • Stack: what you get when you submit a template. CloudFormation builds every resource in it and tracks them as one unit. Delete the stack and its resources are deleted too.
  • Update: edit the template and update the stack. CloudFormation works out what changed. A change set lets you preview those changes before applying them.

YAML or JSON?

CloudFormation accepts both. Choose YAML unless your team already has a lot of JSON:

  • YAML supports comments (# this creates the web server), which matters when a team shares templates. JSON has no comments.
  • YAML uses indentation (like Python) instead of nested braces, so it's easier to read.
  • YAML is everywhere in DevOps: Kubernetes, Ansible, CI pipelines.
Watch outIn YAML, indentation is the structure. Pick 2 spaces and stick to it, and never mix tabs and spaces.

Anatomy of a template

A template can have up to ten top-level sections, but only Resources is required. Everything else adds reuse, validation and documentation, which matters when many people share templates.

SectionWhat it's for
AWSTemplateFormatVersionFormat version. The only valid value is "2010-09-09", unchanged since 2010.
DescriptionPlain-text summary so you (in 20 days) and teammates know what this template does.
MetadataExtra info, e.g. owner, team, project.
ParametersInputs supplied when the stack is created, so the same template works for many teams (e.g. instance type, environment).
RulesValidate parameter values before anything is created, e.g. "in prod, the instance type must be one of these".
MappingsFixed lookup tables, e.g. region → AMI ID, read with !FindInMap.
ConditionsTrue/false checks (usually based on parameters) that decide whether a resource or setting is created.
TransformMacros that expand the template, mainly AWS::Serverless (SAM) for serverless apps (Lesson 19).
Resources (required)The actual AWS resources: buckets, instances, VPCs…
OutputsValues to show after creation, e.g. an instance's public IP or a bucket name.
TipInside Resources, the first key (e.g. MyBucket) is just a logical name you choose. You could call it abhishek1. What defines the resource is its Type, e.g. AWS::S3::Bucket or AWS::EC2::Instance. A template can hold hundreds of resources, each with its own logical name.

Hands-on: create a stack from a template

  
    
    
  1. Write the template. Start from the docs: search "CloudFormation template reference", open Resource and property reference, find your service (e.g. Amazon S3 → AWS::S3::Bucket) and copy only the properties you need. Every property has YAML and JSON examples.
    2. 
    
  2. Open CloudFormation in the console → Create stack. You'll see three choices: Template is ready (upload a file or give an S3 URL), Use a sample template, or build one in the visual designer (drag and drop a resource and it generates YAML or JSON; in today's console this is Infrastructure Composer).
    3. 
    
  3. Upload your template.yaml, give the stack a name (e.g. s3-bucket), fill in any parameters, optionally choose an IAM role for CloudFormation to use, and click Submit.
    4. 
    
  4. Watch the Events tab: CREATE_IN_PROGRESS changes to CREATE_COMPLETE. Check S3 and your bucket is there. You'll also see a cf-templates-… bucket that CloudFormation created automatically to store the templates you upload.
    5. 
  


# template.yaml — the smallest useful template
AWSTemplateFormatVersion: "2010-09-09"
Description: Demo bucket with versioning
Resources:
  S3Bucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: demo-aws-abhi-example.com   # must be globally unique
      VersioningConfiguration:
        Status: Enabled

  
You can do the same from the terminal:


aws cloudformation deploy --template-file template.yaml --stack-name s3-bucket
aws cloudformation delete-stack --stack-name s3-bucket

  
NoteFor one bucket, a stack is overkill; the CLI or console is faster. CloudFormation pays off when you create a VPC, subnets, EC2 instances and S3 buckets together and want to manage them as one unit.


  
Drift detection: catch manual changes

  
You created a bucket with versioning enabled through CloudFormation. A week later, a teammate goes into the console and suspends versioning. Now reality no longer matches the template. That gap is called drift.

  
In the stack, choose Stack actions → Detect drift, then View drift results. CloudFormation compares every resource with the template and reports:

  
    
    
  • IN_SYNC: matches the template.
    • 
    
  • MODIFIED: a property changed. View drift details shows expected vs actual side by side, e.g. Status: Enabled → Suspended.
    • 
    
  • DELETED: someone removed the resource completely.
    • 
  

  
With hundreds of resources, you can't check each one by hand. Drift detection tells you that someone changed something. Then you fix it, and use bucket access logs or CloudTrail to find out who, so you can tighten their permissions. Drift detection only runs when you ask for it, so teams often schedule it (e.g. a cron job or scheduled Lambda calling aws cloudformation detect-stack-drift).

Tips for writing templates faster

  
    
    
  • Start small. Just Resources and one resource. Add parameters and conditions once you're comfortable.
    • 
    
  • Use the documentation. Nobody memorizes hundreds of properties. The template reference has an example for every resource.
    • 
    
  • VS Code extensions: YAML (by Red Hat) flags indentation and syntax errors, and AWS Toolkit autocompletes CloudFormation. Type AWS::EC2:: and pick Instance, then add ImageId, InstanceType, KeyName, SecurityGroupIds.
    • 
    
  • The visual designer and AI assistants are fine for a first draft, but always read and understand the result.
    • 
  

  
PracticeWrite a template that creates one EC2 instance (image ID, instance type, key pair, security group) and deploy it as a stack. Then delete the stack to clean up.


  
CloudFormation vs Terraform

  

    
CloudFormationTerraform

    
      
CloudsAWS onlyAWS, Azure, GCP, on-prem and more

      
LanguageYAML / JSONHCL

      
Who runs itA managed AWS service; state is tracked for youA tool you run; you manage the state file

      
Pick it whenYour company is all-in on AWSMulti-cloud or hybrid, or you want one tool everywhere

    
  

  
If you can learn only one, Terraform is more widely asked for, because companies often run workloads on more than one cloud. Terraform is covered in Lesson 26.

  
Interview angle"Why CloudFormation and not Terraform?" A good answer: "Our organization runs only on AWS and has no plans to move clouds, so a native, AWS-managed IaC service with built-in drift detection was the simplest choice." If multi-cloud comes up, that's the case for Terraform.

Key takeaways

    
    
      
  • IaC = describing infrastructure in declarative, versioned templates that a tool turns into API calls.
    • 
      
  • CloudFormation takes YAML/JSON templates (prefer YAML) and creates a stack: resources managed as one unit.
    • 
      
  • Only Resources is required. Each resource has a logical name, a Type and Properties. Parameters, Mappings, Conditions and Outputs add reuse.
    • 
      
  • Drift detection reveals manual changes (MODIFIED / DELETED) by comparing reality with the template.
    • 
      
  • Use the CLI for quick tasks and CloudFormation for full stacks. Choose Terraform when you need more than one cloud.
