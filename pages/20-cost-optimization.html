Cloud Cost Optimization Project

Forgotten AWS resources quietly add to the bill every month. In this project you build a Lambda function that finds stale EBS snapshots and deletes them automatically on a schedule. It's a real task DevOps engineers do, and a solid project to put on your résumé.

This project builds on Lesson 19: Lambda (functions, handler, execution role, triggers). For reading the bill, Cost Explorer, budgets and tagging, see Lesson 36: Reducing Your AWS Bill.

Why cost optimization matters

Companies, especially startups and mid-size firms, move to the cloud for two main reasons:

  1. Less overhead. No data centre to build, no servers to buy, no team needed just to keep hardware running.
  2. Lower cost. Pay only for what you use instead of buying servers up front.

The second promise only holds if the cloud is used efficiently. Anyone with the right IAM permissions can create resources in seconds, and people forget to delete them. If nobody watches, the bill goes up after the move to cloud, which is the opposite of what the company wanted. Keeping it under control is one of a DevOps engineer's core responsibilities.

Stale resources

A stale resource is something someone created, stopped using, and forgot to delete, while AWS keeps charging for it. Common examples:

  • EBS volumes not attached to any instance.
  • EBS snapshots of volumes that no longer exist.
  • S3 buckets full of data nobody reads any more.
  • An EKS cluster left running after a test.
  • An old EC2 instance still holding an Elastic IP.

Large accounts use hundreds of resource types across many teams. Checking them by hand isn't realistic, so you automate it.

A typical story

First, two quick definitions:

  • An EBS volume is the virtual hard disk attached to an EC2 instance.
  • A snapshot is a point-in-time backup copy of a volume. You can create a new volume from it later.

Now the story. A developer launches an instance and stores important data on its volume, so every day they take a snapshot "just in case". Months later the feature is dropped. They terminate the instance, and its root volume is deleted with it. But the hundreds of snapshots stay behind, and AWS bills for their storage every month.

When a DevOps engineer finds stale resources, there are two options:

Notify

Send an alert ("you have 120 snapshots of a deleted volume, please clean up") using an SNS topic, as covered in CloudWatch & SNS.

Delete

If your team has the permission and the policy allows it, remove them automatically. This project builds the delete option.

The architecture

Build it step by step

  1. Create test resources. Launch a small Ubuntu instance (it gets a root volume automatically). Go to EC2 → Volumes, find its volume, then EC2 → Snapshots → Create snapshot from that volume.
  2. Create the function. Lambda → Create function → author from scratch, name cost-optimization-ebs-snapshot, runtime Python, default execution role.
  3. Add the code (below), click Deploy, then create a test event (any name; you're invoking it by hand) and click Test.
  4. Raise the timeout. The first test likely fails. The default timeout is 3 seconds, which is too short for API calls across the account. Configuration → General configuration → set about 10 seconds. Keep it as low as works, because run time is part of what you pay.
  5. Grant permissions. The next error is UnauthorizedOperation … DescribeSnapshots. The function's execution role can only write logs. Open Configuration → Permissions → the role, then Add permissions → Create inline policy (searching the managed policies for "snapshot" finds nothing useful). Allow exactly what the code needs: 
    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "ec2:DescribeSnapshots",
      "ec2:DescribeVolumes",
      "ec2:DeleteSnapshot"
    ],
    "Resource": "*"
  }]
}
    Granting AmazonEC2FullAccess would be quicker, but it breaks least privilege. If your version of the code also looks up instances, add ec2:DescribeInstances. A missing permission shows up as another Unauthorized error naming the exact action, so just add it. New permissions can take a moment to apply; wait and test again.
  6. Test: nothing should be deleted. The snapshot's volume still exists and is attached to a running instance.
  7. Make it stale. Terminate the instance; its root volume is deleted with it. Test again: the log says the snapshot was deleted because its volume no longer exists. Then try a second case: create a 1 GB volume, don't attach it, snapshot it, and test. The snapshot is deleted, but the volume stays, because this function only cleans snapshots.

The code

import os
from datetime import datetime, timezone, timedelta

import boto3
from botocore.exceptions import ClientError

ec2 = boto3.client('ec2')
DRY_RUN = os.environ.get('DRY_RUN', 'true').lower() == 'true'
MIN_AGE = timedelta(days=int(os.environ.get('MIN_AGE_DAYS', '0')))


def delete(snapshot_id, reason):
    if DRY_RUN:
        print(f"[dry run] would delete {snapshot_id}: {reason}")
        return
    try:
        ec2.delete_snapshot(SnapshotId=snapshot_id)
        print(f"Deleted {snapshot_id}: {reason}")
    except ClientError as e:
        # e.g. InvalidSnapshot.InUse when an AMI still uses the snapshot
        print(f"Could not delete {snapshot_id}: {e.response['Error']['Code']}")


def lambda_handler(event, context):
    # 1. Every EBS snapshot owned by this account (paginated for big accounts)
    paginator = ec2.get_paginator('describe_snapshots')
    for page in paginator.paginate(OwnerIds=['self']):
        for snapshot in page['Snapshots']:
            snapshot_id = snapshot['SnapshotId']
            volume_id = snapshot.get('VolumeId')

            # Optional safety: leave recent snapshots alone
            if datetime.now(timezone.utc) - snapshot['StartTime'] < MIN_AGE:
                continue

            # 2. No source volume recorded -> stale
            if not volume_id:
                delete(snapshot_id, "no source volume")
                continue

            # 3. Is the source volume still there?
            try:
                volume = ec2.describe_volumes(VolumeIds=[volume_id])['Volumes'][0]
            except ClientError as e:
                if e.response['Error']['Code'] == 'InvalidVolume.NotFound':
                    delete(snapshot_id, f"volume {volume_id} no longer exists")
                    continue
                raise

            # 4. Volume exists but isn't attached to any instance -> stale
            if not volume['Attachments']:
                delete(snapshot_id, f"volume {volume_id} is not attached to any instance")

How it works:

  • boto3.client('ec2') creates a client that talks to the EC2 API. The function's role supplies the credentials, so there are no keys in the code.
  • describe_snapshots(OwnerIds=['self']) returns JSON describing your snapshots. Without self you'd also get public snapshots shared by others. The code loops over it and reads SnapshotId and VolumeId.
  • When a volume has been deleted, describe_volumes raises an InvalidVolume.NotFound error. The try/except turns that error into "this snapshot is stale".
  • A volume's Attachments list is empty when it isn't connected to any instance.
  • Environment variables control behaviour without code changes. It starts with DRY_RUN=true (only print). Set it to false once you trust the output. MIN_AGE_DAYS=30 adds the age buffer.
Watch outDeleting a snapshot is permanent. Before running this in a real account: run with dry run first and read the log; agree the rules with the teams (some keep snapshots of deleted volumes on purpose as backups); add an age limit like "older than 30 days"; and consider skipping snapshots tagged e.g. keep=true. Snapshots used by an AMI can't be deleted until the AMI is deregistered.
TipDeleting isn't the only option. Some organisations move old snapshots to the much cheaper EBS Snapshots Archive tier, or only notify owners through SNS. Pick what matches your company's policy.

Run it automatically

Lambda is event-driven, so the last step is a trigger. Create a schedule with Amazon EventBridge (in the console you'll find it under EventBridge → Schedules, or via CloudWatch → Events → Rules, which now opens EventBridge):

  • Schedule type: recurring, e.g. rate(1 day) or the cron expression cron(0 10 * * ? *) (10:00 UTC daily).
  • Target: AWS Lambda → your function.

From then on the cleanup runs every day without anyone remembering to do it. Each run's output lands in the function's CloudWatch log group.

Clean up after the labDelete the test instance, volumes, snapshots, and the schedule (or disable it). Leftover lab resources are exactly the kind of waste this project is meant to catch.

Going further

Real teams write one small function per resource type instead of one giant script: unattached EBS volumes, unused Elastic IPs, idle RDS instances, old S3 data, forgotten EKS clusters. They all follow the same pattern: list → filter by a rule → notify or delete → run on a schedule.

Check yourself

An instance was terminated and its root volume deleted, but its daily snapshots remain. What happens on your bill?
Snapshots are billed separately from volumes and stay until someone deletes them. That's exactly what makes them stale.
The function fails with "UnauthorizedOperation … ec2:DescribeVolumes". What's the right fix?
Grant exactly the missing action to the execution role (least privilege). Never embed access keys in Lambda code.
What's the best way to make the cleanup run every day?
A scheduled EventBridge rule is the event that triggers the function. (Lambda timeouts max out at 15 minutes anyway.)

Key takeaways

  • The cloud only saves money if it's used efficiently. Finding stale resources is a core DevOps responsibility.
  • Snapshots of deleted or unattached volumes are classic waste: AWS keeps billing until they're deleted.
  • The pattern: EventBridge schedule → Lambda (Python + boto3) → describe → filter → delete or notify.
  • Give the execution role only the actions it needs, and raise the 3-second default timeout.
  • Be careful with deletes: dry run first, add an age buffer, respect tags and team policies, and clean up lab resources.
