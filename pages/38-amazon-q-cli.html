Amazon Q Developer CLI

An AI assistant that lives in your terminal, where DevOps work actually happens. You'll learn what makes it different from a chat window (agents, context, hooks, trusted tools), how to install it for free, and how it handled two real tasks: writing Terraform for a secure S3 bucket and fixing a broken Kubernetes pod.

What it is, and why the terminal?

Amazon Q Developer CLI is an agentic AI assistant for your command line. "Agentic" means it doesn't just answer. With your permission it can also do things: run shell commands, read and write files, call AWS, or run kubectl. Typical uses:

  • Creating infrastructure (a Kubernetes cluster, Terraform for AWS resources).
  • Getting unstuck: "why is this deployment failing?"
  • Understanding large codebases (application code, IaC, maintenance scripts). This is useful when you have to troubleshoot a build or deployment for code you didn't write.

Many AI assistants live inside an IDE (code editor). DevOps engineers, though, spend most of their day in the terminal: editing YAML manifests, running shell and Git commands, troubleshooting dev or production, and calling AWS with the CLI. Q Developer CLI brings the assistant to that terminal.

The features that make it useful

Multiple agents

Create a specialist for each job, such as a Terraform agent, a Kubernetes agent or a Git agent. Each one has its own instructions, context and allowed tools.

Context management

Give the AI your rules so its output fits your setup instead of generic boilerplate. Context can be set at three levels (below).

Agent hooks

Run shell commands automatically at set moments (e.g. when the agent starts, or each time you send a prompt) and feed their output in as context.

Strong models

It runs on Anthropic Claude models. Claude Sonnet 4 was the default when this was written. Good reasoning matters for multi-step DevOps tasks.

Three levels of context

LevelHow long it lastsExample
Agent resourcesEvery session that uses that agentFiles listed in the agent's config, e.g. AmazonQ.md, README.md, rule files under .amazonq/rules/
Session contextOnly the current chat/context add instructions.md
Knowledge baseAcross sessions; built for big codebasesIndex a large repo so the agent can search it

Rule files are also how you set guardrails, for example "never touch these directories" or "only run these commands".

Install and sign in (free)

You don't need a paid AWS account. Sign in with a free AWS Builder ID (a personal AWS developer profile, separate from any AWS account).

  1. Go to the Amazon Q Developer "Get started" page → Command line. Download the installer for your OS (a .dmg on macOS; Linux packages are also available).
  2. Install it, then sign in with your Builder ID (q login, or follow the prompt on first launch).
  3. Run q chat. The banner tells you which model you're chatting with.
# interactive chat
q chat
> generate linux command to list files

# one-shot, non-interactive (handy in scripts)
q chat --no-interactive "generate linux command to list files"
NoteQ doesn't need your AWS keys separately. When it runs AWS or Terraform commands, they use whatever you already set up with aws configure (~/.aws/credentials). See Lesson 12: AWS CLI.

Working with agents and context

# inside q chat
/agent help                                # list, create, edit, set a default…
/agent create --name demo-terraform-agent  # starts from a default config
/agent list

# start a new chat using that agent
q chat --agent demo-terraform-agent

# add a file to this session's context
/context add instructions.md

The instructions.md in the example was short:

- Always use the us-east-1 region.
- Always add tags to resources, e.g. Name = <resource-name>.

Hooks are set in the agent's JSON config. For example, a hook can run git status when the agent starts so it always knows what's changed:

"hooks": {
  "agentSpawn":       [ { "command": "git status" } ],
  "userPromptSubmit": [ { "command": "kubectl get pods -A" } ]
}

Trust: the safety switch

Whenever the agent wants to use a tool, such as writing a file or running a command, it asks first:

  • y: allow it this one time.
  • t: trust this tool for the rest of the session, so it won't ask again.
  • n: deny.
Watch outTrust carefully, especially when your terminal is pointed at a real AWS account or production cluster. Read what the agent is about to run. "Trust always" is convenient for reading files but risky for commands that delete or change things.

Real task 1: Terraform for a secure S3 bucket

With demo-terraform-agent and the instructions file in context, the prompt was: "generate terraform code to create S3 bucket with all the best practices". The agent asked to write a file (allowed with t) and produced something like this:

provider "aws" {
  region = "us-east-1"                      # from instructions.md
}

resource "random_id" "suffix" {
  byte_length = 4
}

resource "aws_s3_bucket" "secure" {
  bucket = "my-secure-bucket-${random_id.suffix.hex}"
  tags   = { Name = "my-secure-bucket" }    # tag format from instructions.md
}

resource "aws_s3_bucket_versioning" "secure" {
  bucket = aws_s3_bucket.secure.id
  versioning_configuration { status = "Enabled" }
}

resource "aws_s3_bucket_server_side_encryption_configuration" "secure" {
  bucket = aws_s3_bucket.secure.id
  rule {
    apply_server_side_encryption_by_default { sse_algorithm = "AES256" }
  }
}

resource "aws_s3_bucket_public_access_block" "secure" {
  bucket                  = aws_s3_bucket.secure.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

Then the usual terraform init → plan → apply (see Lesson 26). In the S3 console, the bucket had the requested tag, was in us-east-1, and had versioning, encryption and Block Public Access turned on (these settings are explained in Lesson 11). The agent followed the context file instead of guessing.

Real task 2: troubleshooting a broken pod

A local kind cluster (Kubernetes running in Docker on your laptop) was given a deployment with an image tag that doesn't exist:

kind create cluster --name demo-cluster-q
kubectl create deployment nginx --image=nginx:doesnotexist
kubectl get pods        # STATUS: ErrImagePull / ImagePullBackOff

A k8s-agent was created with session context saying "act as a Kubernetes troubleshooting engineer and provide solutions". Asked "what is the issue with this pod?", it ran kubectl (after a trust prompt), found the invalid image tag, and suggested a fix:

kubectl set image deployment/nginx nginx=nginx:latest
kubectl get pods        # STATUS: Running
New to pods and deployments? See Lesson 24: EKS.
TipAI suggestions are a starting point. In the demo, the human ran the fix command. Keep it that way for production systems, and keep your IaC and cluster changes in Git.

Check yourself

You want every chat with your Terraform agent to remember "always tag resources". Which is the best place for that rule?
Agent resources persist across sessions. /context add lasts only for the current session.
The agent asks to run a command and you press t. What happens?
y = once, t = trust for the session, n = deny.
How does Q CLI get permission to create AWS resources through Terraform?
Commands it runs use your existing local AWS credentials. The Builder ID only signs you in to Q itself.

Key takeaways

  • Amazon Q Developer CLI is an agentic AI assistant in the terminal. It can explain, generate, and (with permission) run commands.
  • Create separate agents per job (Terraform, Kubernetes, Git), each with its own instructions and tools.
  • Context comes in three levels: agent resources (persistent), session (/context add), and knowledge base (large codebases). Hooks add command output automatically.
  • It's free to start with an AWS Builder ID. Run q chat, or q chat --no-interactive "…" for one-shot use.
  • Use trust (y / t / n) carefully, and review what it generates before applying it to real environments.
