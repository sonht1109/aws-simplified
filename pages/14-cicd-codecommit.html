CI/CD Basics & CodeCommit

CI/CD is how code gets from a developer's laptop to real users, automatically and safely. This lesson explains continuous integration and delivery, the Git basics you need, the AWS "Code" services that make up a pipeline on AWS, and AWS's own Git hosting service, CodeCommit, including why many teams still pick GitHub.

The problem: shipping code by hand

Without automation, every release looks like this: someone pulls the latest code, builds it on their machine, runs some tests (if they remember), copies files to a server and restarts the app. It's slow, every person does it a little differently, and bugs slip through. CI/CD turns those steps into an automatic pipeline that runs on every code change.

CI, CD and CD

Continuous Integration (CI)

Developers merge small changes into a shared repository often. Every change is automatically built and tested. Problems show up within minutes, while the change is still fresh.

Continuous Delivery (CD)

Every change that passes CI is automatically packaged and deployed to test/staging, so it's always ready to release. Going to production needs one manual approval.

Continuous Deployment (CD)

Same as delivery, but with no manual gate: if every check passes, the change goes straight to production.

Pipeline

The ordered list of automatic steps (stages) a change goes through: checkout → build → test → scan → package → deploy.

Typical CI stages

The exact stages differ between companies and between web, mobile and ML apps, but a common set is:

  1. Code checkout: fetch the commit that triggered the pipeline.
  2. Build and unit tests: compile (e.g. Maven for Java) and run fast automated tests.
  3. Static code analysis (SAST): scan code for bugs and security issues with tools like SonarQube.
  4. Image build, scan and push: package the app as a Docker image, scan it for vulnerabilities and push it to a registry (Lesson 22).

The CD part then deploys that package to servers (EC2), containers (ECS/Kubernetes) or serverless functions.

Try it: run a pipeline

Push a commit and watch it move through the stages. Then try pushing a bug, or adding a manual approval gate to see the difference between continuous delivery and continuous deployment.

A classic open-source setup uses four kinds of tools. AWS offers a managed service for each role:

Git basics you'll need

Git is a version control system: it records every change to your files so you can see who changed what, go back in time, and work in parallel. Services like GitHub and CodeCommit host Git repositories.

  • Repository (repo): a project folder plus its full history.
  • Commit: a saved snapshot with a message ("fix login bug").
  • Branch: a separate line of work. Pull request: a request to merge a branch, where teammates review the code.
  • Clone / push / pull: copy a remote repo to your machine / send your commits up / bring others' commits down.
git --version                              # check Git is installed
git clone <repo-url>                       # copy the repo locally
cd demo-repo-cc
git config --global user.name  "Your Name" # one-time identity setup
git config --global user.email "you@example.com"
echo "hello" > test.txt
git add test.txt                           # stage the change
git commit -m "Add test file"              # snapshot it
git push                                   # send it to the remote repo

What is AWS CodeCommit?

CodeCommit is AWS's managed, private Git hosting, similar to GitHub or GitLab, but running inside your AWS account.

Why would anyone use it?

Inside companies, code is rarely in public repos. Teams use private GitHub repos, GitHub Enterprise, or run self-hosted GitLab on their own servers. Self-hosting means someone must add servers as repos and teams grow, patch them, secure them and keep them up. CodeCommit removes that work, just as EC2 took over compute and S3 took over storage:

  • Managed: no Git servers to install, patch or back up.
  • Scales automatically: 1 repo or 10,000, and you pay for what you use.
  • Reliable: run by AWS with a service-level agreement (SLA).
  • Always private: repos can't be made public. Access is controlled with IAM.
  • Native AWS integration with CodePipeline, CloudWatch, SNS and so on.
Think of it like…Renting a managed safe-deposit vault for your code inside your own AWS building, instead of buying, guarding and maintaining your own safes.

Hands-on: create and use a repository

  1. In the console, search for CodeCommit and click Create repository. Name it (e.g. demo-repo-cc) and add a description. You can leave CodeGuru Reviewer off; it's an optional code reviewer limited to Java and Python.
  2. The repo page has what you'd expect: a clone URL, files, commits, branches and pull requests. You can upload or edit files in the browser, but only one file at a time. For real work you'll use Git from a terminal or VS Code.
  3. Create an IAM user (don't use root: SSH access doesn't work with the root user, and AWS warns against it). Attach the managed policy AWSCodeCommitPowerUser, which covers everything short of deleting repos, including notification integrations.
  4. For that user, go to IAM → Users → Security credentials → HTTPS Git credentials for AWS CodeCommit → Generate. This gives a special Git username and password. (Alternatives: SSH keys, or the git-remote-codecommit helper.)
  5. Sign in as the IAM user (account ID + username + password) and make sure you're in the same region as the repo. Repos are regional, so a different region shows an empty list.
  6. Copy the HTTPS clone URL and clone it. Git asks for the credentials from step 4. Then add, commit and push a file and watch it appear in the console.
git clone https://git-codecommit.us-east-1.amazonaws.com/v1/repos/demo-repo-cc
TipAuthentication fails even with correct credentials? Your machine may be sending other saved Git credentials (e.g. for GitHub) from its credential manager. Clear the stored entry for git-codecommit.*.amazonaws.com and try again.

The catch: why many teams skip CodeCommit

Pros

  • Fully managed, scales on its own
  • Private by default, IAM-based access
  • Smooth integration with other AWS services
  • AWS reliability and support

Cons

  • Far fewer features than GitHub/GitLab: no Copilot-style AI help, no built-in CI like Actions or Auto DevOps, no in-browser VS Code
  • Integrations mostly limited to AWS services, with few third-party ones
  • Plainer user interface
  • Ties your code hosting to AWS

Because of this, even companies that run everything else on AWS often keep their code in GitHub, GitLab or Bitbucket. That's why the following lessons connect CodePipeline to GitHub. It's the more common real-world setup, and more useful to talk about in interviews.

Status noteCodeCommit stopped accepting new customers in June 2024, then AWS reversed that decision and returned it to general availability on 24 November 2025. New accounts can create repositories again.
Interview angle"CodeCommit or GitHub?" Show you know the trade-off: CodeCommit removes the work of self-hosting Git and keeps code private inside AWS, but GitHub/GitLab have a much richer feature set and ecosystem, so most teams use them and connect them to CodePipeline.

Check yourself

What is the difference between continuous delivery and continuous deployment?
Both automate build, test and release prep. Only continuous deployment pushes to production with no human gate.
Which AWS service plays the role of the "pipeline orchestrator", like Jenkins?
CodePipeline orchestrates the stages. CodeCommit hosts code, CodeBuild builds/tests, CodeDeploy deploys.
Why is CodeCommit used less than GitHub, even by AWS-only companies?
CodeCommit is real Git and always private, but its feature set and ecosystem are much thinner than GitHub's or GitLab's.

Key takeaways

  • CI = every change is automatically built and tested. Continuous delivery = always release-ready, with a manual prod gate. Continuous deployment = no gate.
  • A pipeline is a chain of stages (checkout → build → test → scan → package → deploy) triggered by a Git push.
  • AWS's CI/CD services: CodeCommit (code), CodePipeline (orchestration), CodeBuild (build/test), CodeDeploy (deploy).
  • CodeCommit is managed, private, scalable Git. Use an IAM user with AWSCodeCommitPowerUser and HTTPS Git credentials, not root.
  • Its weak spot is features and integrations, so many teams pair GitHub/GitLab with the other AWS Code services.
