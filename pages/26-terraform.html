Terraform with AWS

Learn the Terraform basics (providers, resources, variables, state, plan and apply), then use them to build a real project: a VPC with two public subnets, two web servers, an S3 bucket and an Application Load Balancer, all from code.

New to Infrastructure as Code? The idea, and how declarative tools compare, is explained in Lesson 13: CloudFormation. This lesson is about Terraform itself.

What is Terraform?

Terraform is an Infrastructure as Code tool made by HashiCorp. You describe the resources you want in text files ending in .tf, and Terraform creates, changes or deletes real cloud resources until they match your files.

  • The files are written in HCL (HashiCorp Configuration Language). It reads a lot like JSON or YAML: blocks, names and key = value pairs.
  • It works with many platforms (AWS, Azure, Google Cloud, OpenStack, Alibaba Cloud…), not only AWS.
  • It is fast and repeatable. Building a setup 100 times by clicking in the console takes hours; with Terraform it's one command each time. If everything is lost, you can run the code again and get it back.
Learn the console firstTerraform only writes down what you would otherwise click. If you don't know that a subnet needs a route table association, or that a load balancer needs a target group and a listener, Terraform won't tell you. Build the setup by hand once (see Lesson 9), then automate it. Keep the AWS console and the Terraform docs open side by side while you write code.

Before you start

  1. Install Terraform and the AWS CLI. Check with terraform -version and aws --version.
  2. Create access keys for an IAM user (IAM → your user → Security credentials → Create access key). Terraform talks to AWS through its API, so it needs keys, not a console password. Never share them.
  3. Run aws configure and paste the keys and a region (for example us-east-1). Terraform's AWS provider reads these saved credentials automatically. Details in Lesson 12: AWS CLI.
  4. Check permissions. Terraform can only do what the IAM user is allowed to do. If the user has no EC2 or VPC permissions, apply fails. See Lesson 3: IAM.
  5. Optional: install the official HashiCorp Terraform extension in VS Code for autocomplete and syntax highlighting.
Watch outThe provider docs let you put access_key and secret_key directly in the provider block, but they also warn against it. Hard-coded keys end up in Git. Use aws configure, environment variables or a role instead.

The building blocks

Provider

The plugin that lets Terraform talk to a platform's API. provider "aws" means "build things on AWS". You find every provider and its versions in the Terraform Registry.

Resource

One thing to create, for example resource "aws_vpc" "myvpc". The first label is the type (fixed by the provider), the second is a local name that only Terraform uses. It's not the name you see in the console.

Variable

An input value kept in one place (usually variables.tf) and used as var.name. Change it once, and every place that uses it follows.

Output

A value Terraform prints after apply, for example the load balancer's DNS name. Handy when you don't have console access.

State

The file terraform.tfstate, where Terraform remembers what it already created. It compares your code with the state to work out what to change. Don't edit it by hand, and never push it to GitHub: it can contain secrets.

Data source

A read-only lookup of something that already exists, for example "find the latest Ubuntu AMI". Declared with a data block instead of resource.

The Terraform workflow

CommandWhat it does
terraform initPrepares the folder and downloads the provider plugins. Run it first, and again after adding a provider.
terraform fmtFormats your code neatly (aligns the = signs, fixes indentation).
terraform validateChecks syntax and references, and tells you the file and line of any mistake.
terraform planA dry run: shows what would be created, changed or destroyed. Nothing is touched.
terraform applyShows the plan again, asks you to type yes, then makes the changes. -auto-approve skips the question.
terraform destroyDeletes everything this configuration created. Use it when you finish practising so you don't get billed.

In the plan output, + means create, ~ means change in place, - means destroy, and -/+ means destroy and re-create (needed when a setting can't be changed on a live resource). The summary line reads like Plan: 7 to add, 0 to change, 0 to destroy.

Try it: plan & apply simulator

The checkboxes are your .tf code. The "state" column is what Terraform remembers creating. Edit the code, press Plan to see the diff, then Apply to make the state match. Try unticking the VPC while subnets still use it, or changing the VPC CIDR after it exists.

Press "terraform plan" to start. The state is empty, so everything in the code will be created.

The project we'll build

This is the same setup as the production-style VPC project, now written as code. To keep it simple, both web servers sit in public subnets.

Step 1: provider and variables

Copy the provider block from the Terraform Registry (click Use provider on the AWS provider page). The terraform block pins the provider version. It's also where you would later set a remote backend to keep state in S3.

# provider.tf
terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

# variables.tf
variable "cidr" {
  default = "10.0.0.0/16"
}

Now run terraform init. It creates a hidden .terraform folder and a lock file. Leave those alone; you only edit the .tf files.

Step 2: networking

Splitting code across files (provider.tf, variables.tf, main.tf…) is good practice; Terraform reads every .tf file in the folder together.

# main.tf
resource "aws_vpc" "myvpc" {
  cidr_block = var.cidr
}

resource "aws_subnet" "sub1" {
  vpc_id                  = aws_vpc.myvpc.id
  cidr_block              = "10.0.0.0/24"
  availability_zone       = "us-east-1a"
  map_public_ip_on_launch = true
}

resource "aws_subnet" "sub2" {
  vpc_id                  = aws_vpc.myvpc.id
  cidr_block              = "10.0.1.0/24"
  availability_zone       = "us-east-1b"
  map_public_ip_on_launch = true
}

resource "aws_internet_gateway" "igw" {
  vpc_id = aws_vpc.myvpc.id
}

resource "aws_route_table" "rt" {
  vpc_id = aws_vpc.myvpc.id
  route {
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.igw.id
  }
}

resource "aws_route_table_association" "rta1" {
  subnet_id      = aws_subnet.sub1.id
  route_table_id = aws_route_table.rt.id
}

resource "aws_route_table_association" "rta2" {
  subnet_id      = aws_subnet.sub2.id
  route_table_id = aws_route_table.rt.id
}
Think of it like…Writing aws_vpc.myvpc.id is like writing "the ID of the VPC I named myvpc, whatever it turns out to be". The ID doesn't exist yet, so Terraform learns it must create the VPC first. These references are how Terraform works out the build order on its own.

Read the docs to see what each argument expects. Most want .id, but some (like target groups and listeners) want .arn. Some take a single string, others a list in [ ].

Run terraform validate, then terraform plan. It should say 7 to add: the VPC, two subnets, the internet gateway, the route table and two associations. Then run terraform apply and type yes.

Step 3: security group, S3 bucket and web servers

resource "aws_security_group" "webSg" {
  name   = "web"
  vpc_id = aws_vpc.myvpc.id

  ingress {
    description = "HTTP from anywhere"
    from_port   = 80
    to_port     = 80
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  ingress {
    description = "SSH"
    from_port   = 22
    to_port     = 22
    protocol    = "tcp"
    cidr_blocks = ["0.0.0.0/0"]
  }
  egress {
    from_port   = 0
    to_port     = 0
    protocol    = "-1"
    cidr_blocks = ["0.0.0.0/0"]
  }
}

resource "aws_s3_bucket" "example" {
  bucket = "my-unique-terraform-project-bucket-2023"   # must be globally unique
}

resource "aws_instance" "webserver1" {
  ami                    = "ami-xxxxxxxxxxxxxxxxx"   # Ubuntu AMI id from YOUR region
  instance_type          = "t2.micro"
  vpc_security_group_ids = [aws_security_group.webSg.id]
  subnet_id              = aws_subnet.sub1.id
  user_data              = base64encode(file("userdata.sh"))
}

resource "aws_instance" "webserver2" {
  ami                    = "ami-xxxxxxxxxxxxxxxxx"
  instance_type          = "t2.micro"
  vpc_security_group_ids = [aws_security_group.webSg.id]
  subnet_id              = aws_subnet.sub2.id
  user_data              = base64encode(file("userdata1.sh"))
}
  • Ingress = inbound rules, egress = outbound. protocol = "-1" means all protocols.
  • AMI IDs differ per region. Copy one from the EC2 launch page in your region, or look it up with a data "aws_ami" block.
  • User data is a start-up script that runs on first boot. Keeping it in its own .sh file keeps main.tf short. file() reads the file; base64encode() encodes it the way the user-data field expects.

Each script installs Apache and writes a small page. The two scripts print different text, so you can see the load balancer switching between servers later:

#!/bin/bash
apt update
apt install -y apache2
# Ask the instance metadata service for this server's ID
INSTANCE_ID=$(curl -s http://169.254.169.254/latest/meta-data/instance-id)
cat <<EOF > /var/www/html/index.html
<h1>Terraform Project Server 1</h1>
<p>Instance ID: $INSTANCE_ID</p>
EOF
systemctl start apache2
systemctl enable apache2
Note169.254.169.254 is the instance metadata address. From inside any EC2 instance you can call it to learn the instance's ID, IP, region and more. Newer instances may require IMDSv2, which needs a session token first. If the ID shows up blank, that's why.
TipUser data errors are silent: the script runs in the background and you won't see the error in Terraform. Test the script on a Linux machine first. You can check what an instance received under Actions → Instance settings → Edit user data.

Step 4: the load balancer

In the console, one wizard creates the load balancer, target group and listener together. In Terraform each is a separate resource, and you have to connect them yourself:

resource "aws_lb" "myalb" {
  name               = "myalb"
  internal           = false              # internet-facing
  load_balancer_type = "application"
  security_groups    = [aws_security_group.webSg.id]
  subnets            = [aws_subnet.sub1.id, aws_subnet.sub2.id]
  tags = {
    Name = "web"
  }
}

resource "aws_lb_target_group" "tg" {
  name     = "myTG"
  port     = 80
  protocol = "HTTP"
  vpc_id   = aws_vpc.myvpc.id
  health_check {
    path = "/"
    port = "traffic-port"
  }
}

resource "aws_lb_target_group_attachment" "attach1" {
  target_group_arn = aws_lb_target_group.tg.arn
  target_id        = aws_instance.webserver1.id
  port             = 80
}

resource "aws_lb_target_group_attachment" "attach2" {
  target_group_arn = aws_lb_target_group.tg.arn
  target_id        = aws_instance.webserver2.id
  port             = 80
}

resource "aws_lb_listener" "listener" {
  load_balancer_arn = aws_lb.myalb.arn
  port              = 80
  protocol          = "HTTP"
  default_action {
    type             = "forward"
    target_group_arn = aws_lb_target_group.tg.arn
  }
}

output "loadbalancerdns" {
  value = aws_lb.myalb.dns_name
}
  • The target group holds the servers and health-checks them on /. Unhealthy servers get no traffic.
  • The attachments put each instance into the target group. With many servers you'd use count or for_each instead of copying the block.
  • Without the listener, the load balancer and target group exist but aren't connected, and you get no response.
  • The output prints the DNS name at the end of apply. Open it in a browser and refresh: the page switches between server 1 and server 2.
  • Wait until the load balancer is Active and both targets are Healthy. This can take a few minutes.
Better securityFor simplicity, the load balancer and instances share one security group here. In real work, give the load balancer its own group and let the instances accept port 80 only from that group.

Common errors (and how to fix them)

ErrorCause
Duplicate resource … already declaredYou copied a block and forgot to change its local name (e.g. two rta1 or two attach1).
Reference to undeclared resourceA reference points to a name that doesn't exist, often left over from code pasted from an older project.
Unsupported block type "tags"tags is an argument, so it needs an equals sign: tags = { … }.
Plan doesn't show your changeThe file wasn't saved. Terraform reads the files on disk.
Access denied on applyThe IAM user lacks permissions for that service.

Errors are normal, even for engineers with years of experience. Read the message, find the line, check the docs. Fixing them yourself teaches you more than copying a working repo.

Finishing up

  • Add a .gitignore with .terraform/, *.tfstate and *.tfstate.backup before pushing code to GitHub.
  • Run terraform destroy when done. The load balancer costs money even when idle.
  • Challenge: add an IAM role and instance profile so the servers can read from the S3 bucket (roles are covered in Lesson 3).
  • Next steps: modules and remote state in S3 with DynamoDB locking are covered in Lesson 34.
Interview angle"Walk me through a Terraform project" is common. Explain the order: provider → network (VPC, subnets, IGW, route table, associations) → security group → compute (EC2 + user data) → load balancer (LB, target group, attachments, listener) → output. Then mention init/plan/apply, state hygiene (not in Git, remote backend) and how references create dependencies.

Check yourself

What does terraform plan do?
plan is a dry run. init downloads providers, apply makes changes, destroy deletes.
You wrote subnet_id = aws_subnet.sub1.id in an EC2 resource. What else does this do?
A reference creates an implicit dependency. Terraform builds a graph from them and creates resources in the right order.
Your ALB and target group were created, but the browser gets no response from the ALB. What is most likely missing?
The listener connects the load balancer to the target group. Also check that both targets show as healthy.

Key takeaways

  • Terraform describes infrastructure in .tf files: a provider (AWS) plus resources, variables and outputs.
  • The workflow is init → validate/fmt → plan → apply, and destroy to clean up.
  • The state file is Terraform's memory of what exists. Keep it out of Git.
  • References like aws_vpc.myvpc.id wire resources together and set the build order.
  • Things the console does for you in one wizard (route table associations, target groups, listeners) are separate resources in code.
  • Know how to build it in the console first, keep the docs open, and treat errors as part of learning.
