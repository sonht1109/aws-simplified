AWS Config: Compliance Checks

Companies have rules about how cloud resources must be set up. AWS Config watches your resources and flags which ones follow those rules and which don't. You'll learn the idea of compliance, managed vs custom rules, and how to write a custom rule backed by a Lambda function.

Start with a story

Your company has a rule: every EC2 instance must have detailed monitoring turned on. Detailed monitoring sends metrics every minute instead of every five, which helps the team spot security or application problems quickly.

Now picture an account with thousands of instances, created by many developers and DevOps engineers. Some will forget the checkbox. Who notices? Checking by hand doesn't scale. That's the problem AWS Config solves.

What is compliance?

Compliance means your resources follow your organisation's rules. A resource that follows them is compliant; one that breaks them is non-compliant.

Every organisation has different rules, depending on its industry. A bank, a government project and a startup will care about very different things. Some examples:

  • Every EC2 instance must have detailed monitoring enabled.
  • No S3 bucket may allow public access.
  • Every S3 bucket must have a lifecycle policy.
  • Every resource must carry an owner tag.

As a DevOps engineer, you don't invent these rules. Ask your manager or security team for the list of mandatory checks, then turn each one into a Config rule. Compliance is part of security, so companies treat it as a high priority.

What AWS Config does

In the console, Config is described as "track resource inventory and changes". It does three things:

  1. Records the configuration of your resources (what exists and how it's set up), and each time that configuration changes.
  2. Evaluates each resource against your rules.
  3. Shows a dashboard of compliant and non-compliant resources, per rule and per resource.
NoteConfig has to be switched on first: you set up a recorder (which resource types to track) and a place, usually an S3 bucket, where it delivers configuration history. Config also has its own charges per item recorded and per rule check, so watch the bill on large accounts.

Two kinds of rules

AWS managed rules

Ready-made rules written by AWS: pick one from the list, fill in a few settings, done. Examples: s3-bucket-public-read-prohibited, required-tags, ec2-instance-detailed-monitoring-enabled. Always check this list first.

Custom rules

For checks AWS doesn't provide. You write the logic yourself, most often as a Lambda function (a "custom Lambda rule"). The console also offers custom rules written in Guard, a policy language. This lesson focuses on Lambda.

A rule runs on one of two kinds of trigger:

  • Configuration changes: runs whenever a matching resource is created, changed or deleted. Results update within minutes.
  • Periodic: runs on a schedule, like a cron job (for example every 24 hours).

How a custom Lambda rule works

Lambda functions are event-driven: something has to invoke them. Here, Config is the caller. It passes the function a JSON event describing the resource that changed. The function checks that resource and sends back a verdict. See Lesson 19: Lambda for the basics.

Build it step by step

  1. Create the Lambda function first (Python runtime, default execution role is fine). You need its ARN before you can create the rule.
  2. Give the function's IAM role permissions to read EC2 (ec2:DescribeInstances), report to Config (config:PutEvaluations) and write CloudWatch logs. For a first demo, broad policies such as EC2 full access, CloudWatch full access and the AWS_ConfigRole managed policy get you going. Then trim them down to least privilege (Lesson 3).
  3. Paste the code below and deploy.
  4. In Config → Rules → Add rule, choose Create custom Lambda rule, give it a name (e.g. test-demo) and paste the Lambda ARN.
  5. Set the trigger to When configuration changes, scope = resources, resource type = AWS::EC2::Instance. Leave the resource ID blank to watch all instances.
  6. Save. Config runs the first check and fills in the dashboard.

The Lambda code

The function is written in Python with boto3, the AWS SDK for Python. It talks to EC2 and Config. The entry point is lambda_handler, which is like main in other languages.

import json
import boto3

ec2 = boto3.client("ec2")
config = boto3.client("config")

def lambda_handler(event, context):
    # Config sends the changed resource as a JSON string inside the event
    invoking_event = json.loads(event["invokingEvent"])
    item = invoking_event["configurationItem"]
    instance_id = item["resourceId"]

    compliance = "COMPLIANT"            # assume good until proven otherwise

    if item["configurationItemStatus"] == "ResourceDeleted":
        compliance = "NOT_APPLICABLE"
    else:
        resp = ec2.describe_instances(InstanceIds=[instance_id])
        instance = resp["Reservations"][0]["Instances"][0]
        if instance["Monitoring"]["State"] != "enabled":
            compliance = "NON_COMPLIANT"

    # Report the verdict back to AWS Config
    config.put_evaluations(
        Evaluations=[{
            "ComplianceResourceType": item["resourceType"],
            "ComplianceResourceId": instance_id,
            "ComplianceType": compliance,
            "OrderingTimestamp": item["configurationItemCaptureTime"],
        }],
        ResultToken=event["resultToken"],
    )
    return {"compliance": compliance}
  • invokingEvent holds the resource's configuration. resultToken tells Config which evaluation run this answer belongs to.
  • The function assumes "compliant", then flips to "non-compliant" if monitoring isn't enabled.
  • You don't need to memorise boto3. Everyone, experienced engineers included, writes this kind of code with the boto3 documentation open.
Try it: compliance checker

Choose which rules are active, then change the resources' settings. Each resource is checked against every active rule that applies to its type, the same way Config evaluates them.

Troubleshooting: when the dashboard doesn't update

Config, Lambda and EC2 are separate services, so results can take a few minutes. If nothing changes:

  1. Check the rule's last successful evaluation time. If it's old, the rule hasn't run yet.
  2. Open CloudWatch → Log groups and find the function's log group (/aws/lambda/<name>). Read the latest log stream. See Lesson 18.
  3. A common error is "Task timed out after 3.0 seconds". Lambda's default timeout is 3 seconds, and a cold start plus two API calls can exceed it. Raise it under Configuration → General configuration (10 seconds is plenty).
  4. Back in Config, choose Actions → Re-evaluate to run the rule again right away.
TipBe patient. Even when everything is correct, a change can take 2–3 minutes or more to appear on the dashboard.

Practice: do the same for S3

Once the EC2 rule works, create a second rule with resource type AWS::S3::Bucket. Write a function that marks a bucket non-compliant if public access isn't blocked. Bucket settings are explained in Lesson 11: S3.

Interview angle"How do you make sure resources follow company policy?" Answer: collect the mandatory rules from security/management, use AWS Config managed rules where they exist, write custom Lambda rules for the rest, trigger on configuration change, and review the compliance dashboard (and alert on it). Mentioning a concrete example like EC2 detailed monitoring makes the answer sound real.

Check yourself

Your rule needs a check that no AWS managed rule offers. What do you create?
Custom Lambda rules let you write any check you need. Config invokes the function and the function reports the result with put_evaluations.
Your rule never updates and the Lambda log says "Task timed out after 3.0 seconds". What's the fix?
Lambda's default timeout is 3 seconds. Raise it, then use Re-evaluate on the rule.
Which trigger updates compliance soon after someone edits an instance?
Change-triggered rules run when a matching resource is created, modified or deleted. Periodic rules wait for the schedule.

Key takeaways

  • Compliance = resources follow your organisation's rules. Config labels each resource COMPLIANT or NON_COMPLIANT.
  • AWS Config records resource configurations and their changes, and evaluates them against rules.
  • Use managed rules when AWS already has the check; write custom Lambda rules for everything else.
  • A rule triggers on configuration changes or periodically.
  • The Lambda reads the event, checks the resource with boto3, and reports back with put_evaluations. Its role needs the matching permissions.
  • Debug with CloudWatch Logs; watch the 3-second default Lambda timeout.
