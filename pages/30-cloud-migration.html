Migrating Applications to AWS

Many companies, especially banks and large enterprises, still run on their own servers and are moving to the cloud gradually. This lesson covers how a real migration project runs (five phases), the "7 Rs" of migration strategy, how databases are moved safely, and how to talk about all of it in an interview.

On-premises vs cloud, and why companies move, is covered in Lesson 2: Introduction to AWS.

Don't start with the 7 Rs

Ask most candidates "how did you migrate to AWS?" and they'll reply "we used lift and shift". Anyone can read that in a blog. Interviewers want to hear how the project actually ran: the phases, how apps were grouped, how you checked things were working and what you improved afterwards. The 7 Rs are just one decision inside that process.

The five phases of a migration project

1. Prepare

Look at the current architecture. Is the application one big monolith (everything in one codebase and one deployment), or already split into microservices (small, independently deployable services)?

  • If it's a monolith and the company wants to be cloud native, developers and DevOps engineers may first split it into microservices.
  • Microservices fit containers well: each service becomes its own container, deployed on an orchestrator like EKS or ECS. See Lesson 22 for containers and Lesson 23 for orchestration.

2. Plan

Two big decisions:

  1. Waves (phases). Don't move 200 services at once. Group them, for example:
    • Wave 1: ~50 low-risk, less user-facing apps. Use them as a proof of concept.
    • Middle waves: slightly more critical, then critical apps.
    • Last wave: the ~20 most critical apps, once the process is proven.
  2. Strategy per app: which of the 7 Rs fits each group (below).

Preparation and planning are done once. After that, you don't go back to them.

3. Migrate

Move one wave at a time. As a DevOps engineer you'll typically:

  • Write Terraform or CloudFormation to create the target infrastructure (Lesson 26).
  • Write shell scripts for start-up and setup tasks, and cron jobs for recurring work.
  • Set up CloudWatch dashboards and alarms (Lesson 18).
  • Schedule the test team's automation suites, e.g. a daily Jenkins job against the new environment.

4. Monitor

After a wave goes live, watch it for weeks or months, depending on how critical it is. Compare performance before and after with dashboards, and collect feedback from internal users or beta customers. Only when the wave looks healthy do you start the next one. Migrate + monitor repeat for every wave, so a project with 10 waves runs this loop 10 times.

5. Optimize

When everything has moved, evaluate: what did the migration achieve? Lower cost? Less maintenance? Better availability? Then improve on it. For example, "we cut costs by 40%; with rightsizing and reserved capacity we can reach 50% within six months". Each improvement becomes a ticket in the backlog.

The 7 Rs of migration

For each application you choose one strategy. In practice, most companies rely on the first three.

StrategyWhat it meansExample
Rehost
"lift and shift"		Move as-is, with minimal or no changes. Fastest and most popular. Works well when the app doesn't depend much on specific hardware or OS. Gains in cost and scaling are small until you optimise later.On-prem Kubernetes with 3 namespaces → the same cluster layout built on EC2 in AWS.
Replatform
"lift, tinker and shift"		Mostly as-is, plus a few changes to use AWS features for availability, scaling or cost. No change to the core code.Move a self-managed MySQL to Amazon RDS; spread nodes across several AZs.
Refactor / re-architectRedesign the app to be cloud native. Most effort, most long-term benefit.Break a monolith into containerised microservices on EKS or serverless.
RelocateMove a whole platform to its AWS-hosted equivalent, without buying new hardware or rewriting apps.VMware vSphere → VMware Cloud on AWS. On-prem OpenShift → Red Hat OpenShift Service on AWS (ROSA).
Repurchase
"drop and shop"		Replace the app with a different product, usually SaaS.A self-hosted CRM → a SaaS CRM. Less common today.
RetainKeep it on-premises for now, often for security, compliance or because it's not worth moving yet. Cloud apps connect to it securely.A bank keeps its mainframe payment systems on-prem; the other apps on AWS reach them through a secure gateway.
RetireSwitch it off. Nobody uses it, so migrating it would waste effort.10 of 200 apps have zero active users.
Think of it like…Moving house. Rehost: pack everything and unpack it the same way. Replatform: same furniture, but you use the new building's laundry room instead of your own machine. Refactor: redesign the furniture to fit the new place. Repurchase: sell the old sofa, buy a new one. Retain: leave some things in storage. Retire: throw out what you never use. Relocate: move a whole furnished room in one piece.
TipYou don't need hands-on experience with all seven. A company typically picks one main approach, so knowing one well and understanding the rest is enough. Retain and retire are less "migration methods" and more team decisions about what not to move.

Migrating databases safely

Apps usually depend on databases, and data is the riskiest part to move. Two rules:

  1. Find the right managed fit. Running your own database takes a lot of effort. If AWS has a managed equivalent, like Amazon RDS for MySQL or PostgreSQL, moving to it hands patching, backups and failover to AWS. This is a classic replatform.
  2. Always have a way back. Large databases can lose data or become unreachable mid-migration. Take backups and keep a copy running (on-prem prod or a pre-prod/staging database). If the cloud database has problems, point the application's connection URL back to that copy right away.
Tools worth knowingAWS offers dedicated services: AWS Application Migration Service for rehosting servers, AWS Database Migration Service (DMS) for copying databases with minimal downtime (it can keep source and target in sync until cutover), and AWS Migration Hub for tracking progress across tools.
Interview angleStructure your answer: "We prepared by assessing the architecture (and split the monolith), planned waves from least to most critical and chose a strategy per group, mostly rehost with some replatform to RDS. Each wave we migrated with Terraform and scripts, then monitored for a month with CloudWatch dashboards before the next. At the end we measured cost savings and opened optimisation tasks." If you didn't experience something, say so: "I was on the project for six months and didn't handle that part, but I'd approach it like this…"

You move an app unchanged, but swap its self-managed MySQL server for Amazon RDS. Which R is that?
A small change to use a managed AWS service, without redesigning the app, is replatforming.

Keeping an application where it is, on purpose, is "retain".

Key takeaways

  • A migration is a project: prepare → plan → (migrate → monitor) per wave → optimize.
  • Move apps in waves, from least to most critical, and monitor each wave before the next.
  • The 7 Rs: rehost, replatform, refactor, relocate, repurchase, retain, retire. Rehost, replatform and refactor are the most common.
  • Databases need extra care: prefer managed services like RDS, and always keep a backup and a fallback copy.
  • In interviews, describe the process and your part in it, not only "lift and shift".
