Three-Tier Architecture on AWS

Most apps you use every day are split into three layers: the screen you see, the logic behind it, and the database that stores the data. This lesson explains that split and how a classic EC2-based version is built on AWS.

What is a "tier"?

A tier is a separate layer of an application that has one job and usually runs on its own servers. Follow a shopper on an online store:

  1. The user opens the site in a browser and sees a web page: the user interface (UI), also called the front end. They log in, search, and click a product.
  2. The UI does not hold product details. It sends a request to the back end, an application written in Java, Python, Go, etc. The back end checks the request and decides what data is needed.
  3. The back end asks the database, which stores the product name, price, description and images.
  4. The database answers the back end, and the back end sends the result to the front end, which shows it to the user.

Tier 1: Presentation

The front end / UI. Runs in the browser and on web servers. Shows pages and collects input.

Tier 2: Application (logic)

The back end. Business rules: login checks, pricing, cart, orders. Sits between the UI and the data.

Tier 3: Data

The database. Stores users, products, orders. Only the logic tier talks to it.

Think of it like…A restaurant. The dining room (presentation) is where guests order. The kitchen (logic) does the work. The pantry (data) holds the ingredients. Guests never walk into the pantry; the kitchen fetches what's needed.

One, two or three tiers?

TypeLayersExample
One-tierEverything in one placeA static website: just HTML pages, no back end or database
Two-tierFront end + back end, no databaseA web calculator (the UI sends "2 + 2", the back end returns 4), or the 2048 game deployed in Lesson 24: EKS
Three-tierFront end + back end + databaseOnline shops, social media, banking apps: almost every real app

Why split an app into tiers?

  • Security: the database is never reachable from the internet. Each tier only accepts traffic from the tier in front of it.
  • Independent scaling: if the web tier is busy but the app tier isn't, add web servers only.
  • Availability: each tier runs in at least two Availability Zones, so one data-center failure doesn't take the app down.
  • Separate teams and changes: front-end developers can ship a UI change without touching the database.

Building it on AWS (EC2 version)

Here is the classic layout, from the outside in.

  1. A VPC for the project. One AWS account may host many projects, so give this app its own isolated network, e.g. 172.16.0.0/16. (VPCs and CIDR)
  2. Subnets per tier, in two AZs. A public subnet for the internet-facing load balancer, and private subnets for the web tier, the app tier and the database. Spreading across two Availability Zones (e.g. us-east-1a and us-east-1b) keeps the app alive if one zone fails.
  3. Web tier: EC2 instances in an Auto Scaling Group, which keeps the right number of servers running, adds more under load, removes them when quiet, and spreads them across AZs. (Auto Scaling Groups)
  4. App tier: a second Auto Scaling Group for the back-end servers, with an internal load balancer in front of it that only the web tier can reach.
  5. Data tier: Amazon RDS, a managed database service (MySQL, PostgreSQL…). Run it as Multi-AZ: a primary database plus a standby copy in another AZ that takes over automatically if the primary fails.
  6. The front door: users reach the app through Route 53 (DNS), optionally CloudFront (a CDN that caches content near users), and then a public Application Load Balancer.

How a request flows

User → Route 53 resolves the domain → CloudFront (cached content served from the edge) → public ALB → one web server → internal ALB → one app server → RDS primary. The response travels back the same way.

Locking it down with security groups

The usual trick is security-group chaining: instead of allowing IP ranges, each tier's security group allows traffic only from the security group of the tier in front of it.

Security groupAllows inbound from
Public ALBInternet (0.0.0.0/0) on 80/443
Web serversPublic ALB's security group only
Internal ALBWeb servers' security group only
App serversInternal ALB's security group only
RDSApp servers' security group only, on the DB port (e.g. 3306)
How security groups work (inbound rules, stateful replies) is covered in Lesson 7: Security Groups & NACLs. Private servers still reach the internet for updates through a NAT gateway.

Going further: disaster recovery

Larger setups copy the whole stack into a second region. If an entire region has an outage, Route 53 can send users to the backup region. Multi-AZ protects against a data-center failure; multi-region protects against a regional one.

TipBuild a one-tier app (a static site) and a two-tier app before this one. A full three-tier build has many parts: VPC, subnets, two ALBs, two ASGs, RDS, Route 53 and CloudFront. It's much less scary when you've already built the smaller pieces.

When to talk about this in an interview

This EC2-based design is a classic, but many companies now run apps on containers (Kubernetes / EKS) or serverless instead of fleets of EC2 instances. Match your story to the job:

JD mentions EC2, ASG, VMs

Describe this architecture: the VPC, subnets per tier, ASGs in two AZs, internal and public ALBs, Multi-AZ RDS.

JD mentions containers / Kubernetes

Describe the three tiers running as microservices on EKS instead. See Lesson 33.

Interview angleDon't mix the two stories. Saying "we ran everything on Kubernetes" and then describing fleets of EC2 web servers in Auto Scaling Groups makes it sound like you haven't worked on either for real.

Check yourself

A web calculator has a front end and a back end that does the math, but no database. What is it?
Front end + back end without a data layer is a two-tier application.
Which tier should be allowed to connect to the RDS database?
The data tier's security group allows only the app tier's security group. The front end never talks to the database directly.
What does running RDS as Multi-AZ give you?
Multi-AZ keeps a synchronized standby in a second Availability Zone for automatic failover. It's about availability, not speed or public access.

Key takeaways

  • Three tiers = presentation (UI) + application (logic) + data (database). No database means two-tier.
  • On AWS: a dedicated VPC, a public ALB in public subnets, web and app tiers in private subnets with Auto Scaling Groups, and RDS in its own subnets.
  • Spread every tier across at least two AZs; use Multi-AZ RDS. For disaster recovery, copy the stack to a second region.
  • Each tier only accepts traffic from the tier in front of it (security-group chaining). The database is never internet-facing.
  • In interviews, use this EC2 design for VM-focused roles and an EKS/container design for Kubernetes roles.
