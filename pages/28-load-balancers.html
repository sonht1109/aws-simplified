Load Balancers: ALB vs NLB vs GWLB

A load balancer spreads incoming traffic across several servers so no single server gets overwhelmed. AWS has three modern types. Picking the right one depends on which network "layer" it works at, so we'll cover just enough of the OSI model first, then compare ALB, NLB and GWLB with real use cases.

Why you need a load balancer

Say you build a game and run it on one EC2 instance. Five players, no problem. The game goes viral and now hundreds of people play at once. One server can't keep up: some players see slowness, others see downtime. Either way, it's a bad experience.

The fix: run the game on several identical instances and put a load balancer in front. Users connect to the load balancer, never to a server directly, and it decides which server handles each request.

  • Spreads the load: 100 requests across 3 servers ≈ 33 each.
  • Scales out: still too slow? Add more instances behind it, for example with an Auto Scaling Group (Lesson 9).
  • Keeps the app up: it checks each server's health and stops sending traffic to broken ones. This is what makes an app highly available.

Load-balancing algorithms

An algorithm here just means the rule for choosing a server:

  • Round robin: take turns, 1 → 2 → 3 → 1… The simplest option, good when all servers are identical (same CPU, RAM, OS).
  • Weighted / ratio-based: a bigger server gets a bigger share, e.g. 50% to the powerful one and 25% each to the other two.
  • Least outstanding requests: send the next request to the server that is least busy right now (an ALB option).

Load balancers aren't unique to AWS. NGINX, F5, Envoy, Traefik and Ambassador are popular ones, each with its own set of algorithms.

Just enough OSI model

When you open linkedin.com/in/someone in a browser, the request passes through seven layers on its way to the server. Each layer adds one job. You only need a rough idea of each, because different load balancers work at different layers.

#LayerWhat happens there (simplified)
7ApplicationThe protocol you speak: HTTP, FTP… Your browser builds the HTTP request for you. ALB works here.
6PresentationEncoding and encryption, e.g. TLS (the successor to SSL) for HTTPS.
5SessionOpens and tracks the session between client and server.
4TransportSplits data into small segments and delivers them reliably (TCP) or quickly (UDP), using ports. NLB works here.
3NetworkIP addresses; packets hop across routers toward the destination. GWLB works here.
2Data linkSwitches move frames inside the local network or data centre.
1PhysicalCables and signals that finally reach the server.
Think of it like…A Layer 7 balancer is a receptionist who opens your letter, reads it, and walks it to the right department. A Layer 4 balancer is a mail sorter who only reads the address and port on the envelope, which makes it much faster, but it can't route by what's inside.

Application Load Balancer (ALB): Layer 7

The ALB reads each HTTP(S) request: the path, the host name, the headers, query strings. Then it decides where to send it. That allows content-based routing:

  • Path-based: /payments → payment service, /login → login service.
  • Host-based: shop.example.in and shop.example.com go to different servers.
  • Header/query-based and weighted routing, e.g. send 10% of traffic to a new version.
  • TLS termination (SSL offloading): the ALB decrypts HTTPS so your servers don't have to; it can also re-encrypt toward the servers.
  • Built for websites, APIs and microservices. It's also what Kubernetes ingress uses on EKS (Lesson 24).

Trade-off: reading every request costs time and money. The ALB adds a little latency (an extra "hop" that inspects the request) and costs more per unit of traffic than an NLB.

Network Load Balancer (NLB): Layer 4

The NLB doesn't look inside the request. It forwards TCP and UDP traffic based on IP address and port, which makes it very fast:

  • Ultra-low latency and huge throughput (millions of requests per second).
  • Handles non-HTTP protocols: game servers, video streaming, IoT, databases, any custom TCP/UDP protocol.
  • Can have a static IP per Availability Zone, which helps when clients or firewalls need to allow-list fixed IPs.
  • A TCP connection stays on the same target for as long as it lasts, which suits long streams. NLB can also pin a client to one target by source IP (stickiness).
  • Cheaper than an ALB for the same volume of traffic.

Typical users: online games and live/video streaming platforms, where even a small delay is not acceptable and HTTP-level routing isn't needed.

Clearing up a common mythYou'll sometimes hear "only NLB has sticky sessions". Not quite: an ALB supports sticky sessions too, using cookies, so a user's requests keep going to the same target. The real difference is the layer: ALB sticks at HTTP level with a cookie; NLB keeps each TCP connection on one target and can stick by client IP.

Gateway Load Balancer (GWLB): Layer 3

GWLB is a different tool for a different job. It sits in front of virtual appliances: third-party firewalls, intrusion detection/prevention systems (IDS/IPS) and deep packet inspection tools, usually running on EC2.

  • It works at Layer 3 (IP packets) and is transparent: it passes the original packets unchanged to the appliance fleet, wrapped in a tunnel (the GENEVE protocol), and gets them back after inspection.
  • It spreads load across the appliances and scales them, while keeping each traffic flow on the same appliance.
  • ALB and NLB aren't designed for this. They terminate or forward connections to an application rather than passing every packet through a security appliance and back.

Typical users: companies that build or run firewall/VPN-style security appliances, or that must route all traffic through a central inspection layer.

NoteThere's also the Classic Load Balancer, the older previous-generation option. New designs use ALB, NLB or GWLB.

The pieces of every AWS load balancer

Listener

A port and protocol the load balancer listens on (e.g. HTTPS :443), plus rules saying what to do with matching traffic: forward, redirect (HTTP→HTTPS) or return a fixed response.

Target group

The set of destinations: EC2 instances, IP addresses, Lambda functions (ALB) or containers. Each group has its own port and protocol.

Health check

The load balancer regularly calls each target (e.g. GET /). Targets that fail are marked unhealthy and get no traffic until they recover.

Subnets / AZs

You enable the load balancer in subnets in two or more Availability Zones, so losing one AZ doesn't take the app down.

Key takeaways

  • A load balancer spreads traffic across healthy targets so apps stay fast and available.
  • Round robin takes turns; weighted sends more to stronger servers; health checks remove broken ones.
  • ALB = Layer 7: reads HTTP, routes by path/host/header, terminates TLS. Smart but slightly slower and pricier.
  • NLB = Layer 4: TCP/UDP by IP and port, ultra-low latency, static IPs. For games, streaming and non-HTTP traffic.
  • GWLB = Layer 3: transparently feeds traffic through firewalls and other security appliances.
  • Every load balancer is built from listeners, rules, target groups and health checks, spread across multiple AZs.
