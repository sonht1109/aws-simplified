S3: Object Storage

Amazon S3 is where companies keep files they can't afford to lose: backups, logs, reports, website files. You'll learn how buckets and objects work, how to keep old versions, how to pay less with storage classes, how to lock a bucket down, and how to host a website from one.

The problem S3 solves

When your laptop runs out of space, you buy a bigger disk or a USB drive. A company has the same problem, only much bigger:

  • Database backups and dumps: one backup of a big shopping site can be several terabytes.
  • Application logs: for example, "keep the last 30 days of logs".
  • Reports, CSV/Excel files, dashboard data, config files, images, videos.

S3 (Simple Storage Service) is AWS's answer: you put in as much data as you like, pay only for what you store, and AWS takes care of the disks. It was one of the very first AWS services, and it's often the first one people learn because the idea is easy to follow.

Think of it like…A huge, never-full online drive. A bucket is a top-level folder you create, and every file you drop into it is an object.

Buckets, objects and keys

  • Object storage stores each file as a whole object (data + some metadata) that you read or write in one go through a web request. It's not a disk you mount and edit block by block (that's EBS, attached to an EC2 instance).
  • Bucket: a container for objects. You create it, name it and pick a region.
  • Object: anything you upload, such as index.html, a video or a 3 TB database dump. S3 doesn't care what type of file it is, so it calls them all "objects".
  • Key: the object's full name inside the bucket, e.g. logs/2024/06/app.log. The slashes look like folders, but they're really just part of the name.

Limits worth remembering

  • There's no limit on how much data a bucket can hold.
  • A single object can be at most 5 TB. A bigger file must be split up.
  • For large files, use multipart upload: the file goes up in chunks (say 100 MB each). If your network drops, only the failed chunk is retried instead of starting over. AWS recommends it for anything over about 100 MB, and you must use it above 5 GB.

Bucket names are globally unique

Every object can be reached over HTTPS with a URL, so a bucket name must be unique across all AWS accounts in the world, not just yours. If someone already took abhishek, you can't have it. Teams use a naming convention so names stay unique and meaningful:

<app>-<feature>-<environment>-<company domain>
app1-payments-prod-example.com

Names must be 3–63 characters, using lowercase letters, numbers, dots and hyphens.

Global names, regional buckets

This trips people up: the name is global and the data can be reached from anywhere, but each bucket lives in one region that you choose. Pick a region close to your users so requests travel a shorter distance. That delay is called latency. (Regions and availability zones are covered in Lesson 2.)

Why S3 is so popular

Durability: "11 nines"

S3 is designed for 99.999999999% durability. Put another way, if you store 10 million objects, you can expect to lose one about every 10,000 years. That's possible because S3 copies every object across several data centers.

Availability

Your data can be read when you need it. S3 Standard is designed for 99.99% availability.

Scalability

Start with one 100-byte file and grow to petabytes. You don't have to buy or resize any disks.

Security

Encryption, bucket policies, Block Public Access, access logging and object lock. More on these below.

Cost efficiency

You pay per GB per month, and old or rarely used data can move to much cheaper storage classes.

Performance

Choosing a nearby region gives fast transfers, and multipart upload makes huge uploads reliable.

Interview angle"Why S3?" A strong short answer: it's simple object storage with 11 nines of durability, high availability, practically unlimited scale, strong security controls, and low cost thanks to storage classes.

Creating a bucket and uploading

  1. In the console, search for S3, open Buckets, then click Create bucket.
  2. Enter a globally unique name and pick a region.
  3. Leave Block all public access turned on. That's the safe default.
  4. Leave versioning at its default for now. Server-side encryption is on by default: since January 2023, every new object is encrypted with S3-managed keys.
  5. Click Create bucket, open it, click Upload, add a file and upload. Your file is now an object, and it stays safe even if your laptop dies.

Versioning: keep every old copy

Say you upload app.log today and a changed app.log tomorrow. Without versioning, S3 simply replaces the old file, and yesterday's copy is gone. With versioning turned on (Bucket → Properties → Bucket Versioning → Enable), S3 keeps every version, a bit like Git keeps the history of a file. If someone says "yesterday's file was wrong, give me the one from the day before", you can download that exact version.

  • Each version gets its own version ID.
  • Deleting a file in a versioned bucket doesn't destroy the data. S3 adds a delete marker on top, so the file looks gone but older versions are still there. Remove the marker and the file comes back.
  • Once enabled, versioning can only be suspended, not fully turned off.
  • S3 can keep versions, but it isn't a replacement for Git: there are no code reviews, branches or pull requests.

Storage classes: pay for what you need

Storage is a trade-off. Data you read often has to come back instantly, which costs more. Data you almost never read can sit somewhere slower and much cheaper. S3 lets you pick a storage class for each object. Durability stays at 11 nines for all of them. What changes is price, how fast you get the data back, and the minimum time you pay for.

Lifecycle rules: automate the savings

You don't have to move objects by hand. A lifecycle rule (Bucket → Management) does it on a schedule. This pairs nicely with versioning, which would otherwise keep paying for every old copy:

  • Move objects to Standard-IA after 30 days, and to Glacier after 90.
  • Move previous versions to Glacier Deep Archive, or delete them after 5 or 10 days.
  • Delete logs older than 30 days.

Other bucket properties at a glance

  • Tags: key/value labels like project=app1. They make it easy to answer "which buckets belong to this project?" and to split costs by team.
  • Default encryption: on by default. S3 supports encryption at rest (on AWS's disks) and in transit (over HTTPS).
  • Server access logging: records who accessed which object, which helps you spot suspicious activity. It's off by default.
  • Event notifications: when an object is uploaded or deleted, S3 can trigger something else, such as a Lambda function (see Lesson 19).
  • Object Lock: makes objects write-once-read-many, so nobody can overwrite or delete them for a set period. Useful for sensitive or regulated data.
  • Static website hosting: covered in demo 2 below.

Demo 1: lock a bucket with a bucket policy

The scenario: someone in your company has an IAM policy like AmazonS3FullAccess, which means they can open every bucket, including the one holding sensitive data. As the bucket owner, you can block them anyway with a bucket policy. That's a JSON policy attached to the bucket itself rather than to a user.

  1. Create an IAM user with no permissions and log in as them in a private browser window. Opening S3 shows "you don't have permissions to list buckets", as expected.
  2. Attach AmazonS3FullAccess to that user. Now they can open your bucket and download files. That's the problem.
  3. In your bucket, go to Permissions → Bucket policy → Edit and add a statement that denies everyone except you. The policy generator (Add statement) helps you build the JSON.
  4. Refresh the other user's window. They now get "Insufficient permissions to list objects".
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyEveryoneExceptOwner",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::app1-payments-prod-example.com",
        "arn:aws:s3:::app1-payments-prod-example.com/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "aws:PrincipalArn": "arn:aws:iam::111122223333:root"
        }
      }
    }
  ]
}
  • Principal "*": applies to everyone.
  • Effect Deny + Action s3:*: block every S3 action.
  • Resource: list both the bucket ARN and bucket/* (the objects inside). Forgetting one of the two is a classic mistake.
  • Condition: "unless the caller is this ARN", so you don't lock yourself out. Replace 111122223333 with your account ID.
Watch outAn explicit Deny always beats an Allow. A careless deny-all policy can lock out your own admins. The account's root user can still delete the bucket policy to recover.

Demo 2: host a static website

A static website is plain HTML, CSS, JavaScript and images, with no server-side code. S3 can serve one cheaply to the whole world. In real jobs, developers usually set this up once, but you should know the steps.

  1. Create a bucket and upload your index.html.
  2. Go to Properties → Static website hosting → Edit, choose Host a static website, set the index document to index.html, then save. You get a website endpoint URL like http://<bucket>.s3-website-us-east-1.amazonaws.com.
  3. Open the URL and you get 403 Forbidden, because public access is still blocked.
  4. Go to Permissions → Block public access → Edit, untick Block all public access and confirm. If the box can't be changed, Block Public Access is also switched on at the account level and must be turned off there too. Also remove any deny-all policy from demo 1.
  5. Still "Access denied"? Turning off the block only allows public policies. You still need a policy that grants public read:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::app1-payments-prod-example.com/*"
    }
  ]
}

Refresh the page and your site loads.

TipIf your page's JavaScript calls APIs on other domains, the browser may block those calls unless CORS (Cross-Origin Resource Sharing) is configured. For real sites, you'd usually put a CDN in front of the bucket and keep the bucket private. See Lesson 21: CloudFront. A custom domain comes from Route 53.

Check yourself

Your bucket has versioning enabled and someone deletes report.csv. What happens?
In a versioned bucket, a normal delete only places a delete marker on top. Remove the marker (or download an older version ID) to get the file back.
A user has AmazonS3FullAccess in IAM, but you want them out of one sensitive bucket. What's the simplest fix?
Bucket policies are attached to the bucket, and an explicit Deny overrides any Allow in the user's IAM policy.
You must keep audit files for 7 years and will probably never read them. Waiting 2 days is fine if you ever do. Which class is cheapest?
Deep Archive is the cheapest class. Retrieval takes 12–48 hours, which fits rarely read compliance data.

Key takeaways

  • S3 stores objects (any file, up to 5 TB each) in buckets. Bucket names are globally unique, but each bucket lives in one region.
  • 11 nines of durability come from automatic copies across multiple AZs.
  • Versioning keeps old copies, and deletes become delete markers. Use lifecycle rules so old versions don't pile up costs.
  • Pick a storage class by how often you read the data and how fast you need it back. Standard costs the most, Deep Archive the least.
  • Keep Block Public Access on. Use bucket policies to restrict access even for users with broad IAM rights.
  • Static website = upload files + enable website hosting + allow public access + a public-read s3:GetObject policy.
