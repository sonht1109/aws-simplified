Project: EKS + VPC with Terraform

Use community Terraform modules to build a production-style VPC and an EKS cluster with auto-scaling worker nodes in about 55 resources and one command. You'll also learn how teams store Terraform state safely so two people can't break it at the same time.

New to Terraform? Providers, resources, variables, state and plan/apply are explained in Lesson 26: Terraform. EKS itself is covered in Lesson 24.

What we're building

Step 1–3: Install and connect

  1. Install the AWS CLI (from the AWS "Install or update the AWS CLI" page for your OS), then check: aws --version.
  2. Install Terraform (HashiCorp's install page: package manager on Linux, Homebrew on Mac, Chocolatey or a zip on Windows), then check: terraform version.
  3. Connect Terraform to AWS by running aws configure and entering an access key, secret key, default region and output format (json). This saves the keys in ~/.aws/credentials. Terraform's AWS provider reads that same file, so configuring the CLI also configures Terraform.
Watch outUse an IAM user or role with the right permissions, not root access keys, in any real account. Delete demo access keys when you're done. (IAM, AWS CLI & access keys)

How to structure the Terraform files

You could put everything in one main.tf, but a 500-line file is hard to read and fix. Split by purpose, so the person fixing a security-group rule opens security-groups.tf and nothing else:

FileWhat's inside
versions.tfRequired Terraform version and providers (aws, random, …)
variables.tfInputs: AWS region, Kubernetes version, VPC CIDR
vpc.tfThe aws provider, a random suffix for the cluster name, and the VPC module
eks-cluster.tfThe EKS module and its managed node group
security-groups.tfExtra security group with inbound/outbound rules for the nodes
outputs.tfValues printed after apply (cluster name, endpoint, region…)

Terraform modules

A module is a reusable package of Terraform code. You call it, pass in a few inputs, and it creates all the resources inside. Think of it as a function: you don't rewrite the code for a VPC (subnets, route tables, internet gateway, NAT…) every time; you call the VPC module with your settings.

Think of it like…A flat-pack furniture kit. You don't cut wood and design joints yourself; you pick the "wardrobe" kit and choose the size and colour. A module is the kit; the inputs are your choices.

Why modules are a best practice:

  • No duplicate code. If project X and project Y both need "S3 bucket + EC2", write it once as a module and call it twice.
  • Fix once, fix everywhere. When a security update changes how something should be built, you update the module and every caller benefits. Callers only pass variables, so they don't break.
  • Battle-tested code. Common building blocks like VPC and EKS already exist as community modules.

Where to look for a module, in order:

  1. The Terraform Registry (registry.terraform.io), e.g. the community-maintained terraform-aws-modules collection, which has VPC, EKS, S3, RDS and more.
  2. Your organisation's own modules (often in a Git repo), written by another team for the same need.
  3. If neither exists, write the code yourself, then consider turning it into a module for the next person.

The VPC module

Every module call has a source (where the module comes from) and a version. Always pin the version. Without it you get whatever is newest, and a breaking change could hit you without warning. For a new project, start with the latest version.

provider "aws" {
  region = var.aws_region
}

locals {
  cluster_name = "abhi-eks-${random_string.suffix.result}"
}

resource "random_string" "suffix" {
  length  = 8
  special = false
}

module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "5.7.0"

  name = "abhi-eks-vpc"
  cidr = var.vpc_cidr
  azs  = data.aws_availability_zones.available.names

  private_subnets = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
  public_subnets  = ["10.0.4.0/24", "10.0.5.0/24", "10.0.6.0/24"]

  enable_nat_gateway   = true
  single_nat_gateway   = true
  enable_dns_hostnames = true
  enable_dns_support   = true

  tags = {
    "kubernetes.io/cluster/${local.cluster_name}" = "shared"
  }
}

data "aws_availability_zones" "available" {}

How do you know which inputs exist? Open the module's page in the registry and read its Inputs, Outputs and Examples. Some inputs are required (like name and cidr), most are optional. With practice you'll know which ones matter. The random_string adds an 8-character suffix so every cluster name is unique.

The EKS module

module "eks" {
  source  = "terraform-aws-modules/eks/aws"
  version = "~> 20.0"

  cluster_name    = local.cluster_name
  cluster_version = var.kubernetes_version
  vpc_id          = module.vpc.vpc_id
  subnet_ids      = module.vpc.private_subnets

  eks_managed_node_group_defaults = {
    ami_type               = "AL2_x86_64"
    instance_types         = ["t3.medium"]
    vpc_security_group_ids = [aws_security_group.all_worker_mgmt.id]
  }

  eks_managed_node_groups = {
    node_group = {
      min_size     = 2
      desired_size = 2
      max_size     = 6
    }
  }
}

Note how modules plug together: module.vpc.vpc_id and module.vpc.private_subnets are outputs of the VPC module fed into the EKS module. Terraform works out the order: VPC first, then EKS. An EKS managed node group means AWS creates an Auto Scaling Group and launch template for the worker nodes; you set min/desired/max. (The module's examples also show Fargate profiles, Karpenter and self-managed node groups.)

Variables and outputs

# variables.tf
variable "aws_region" {
  default = "us-east-1"
}
variable "kubernetes_version" {
  default = "1.29"
}
variable "vpc_cidr" {
  default = "10.0.0.0/16"
}

# outputs.tf
output "cluster_name"     { value = module.eks.cluster_name }
output "cluster_endpoint" { value = module.eks.cluster_endpoint }
output "region"           { value = var.aws_region }

Outputs are printed at the end of apply, so you don't have to dig through the console to find the cluster name or endpoint.

Step 4: Run it

terraform init      # downloads providers and modules into .terraform/
terraform plan      # preview: about 55 resources to add
terraform apply     # type "yes" (or add -auto-approve); takes roughly 10-15 min
  • Read the init output. It says which backend it's using (local here), downloads each module into .terraform/modules/ (you'll find eks and vpc), and downloads every provider listed in versions.tf into .terraform/providers/. Unused providers left in versions.tf still get downloaded, so remove them.
  • Read the plan. You'll see the VPC, subnets, route tables, internet gateway, NAT gateway, security groups, IAM roles, the cluster and the node group. Reading a plan line by line is one of the best ways to learn what a module actually builds.

Getting access to the cluster

When you open the new cluster in the console, the Compute and Resources tabs may say you have no access, even as root. EKS uses access entries to decide who can see inside the cluster. Under the cluster's Access tab:

  1. Click Create access entry and choose your IAM principal (user or role ARN).
  2. Attach the AmazonEKSClusterAdminPolicy access policy.
  3. Refresh: the nodes (2 by default) and resources now appear.

You can also do this in Terraform (e.g. enable_cluster_creator_admin_permissions = true or an access_entries block in EKS module v20). Then connect kubectl:

aws eks update-kubeconfig --name <cluster-name> --region us-east-1
kubectl get nodes
Watch outNAT gateways, EKS control planes and EC2 nodes are not free. When you're done, run terraform destroy.

Remote state and locking

This demo uses the local backend: terraform.tfstate sits on your laptop. That's fine for learning, but in a team it causes two problems:

  • Nobody else has the state. A teammate running apply from their machine has an empty state, so Terraform thinks nothing exists and tries to create everything again.
  • Simultaneous applies. Even with a shared state file, two people running apply at the same time can corrupt it or overwrite each other's changes.

The usual fix is a remote backend: keep the state in an S3 bucket (shared, versioned, encrypted) and use a lock so only one apply can run at a time. Traditionally the lock is a row in a DynamoDB table:

terraform {
  backend "s3" {
    bucket         = "my-company-terraform-state"
    key            = "eks/terraform.tfstate"
    region         = "us-east-1"
    encrypt        = true
    dynamodb_table = "terraform-locks"   # table with a string partition key "LockID"
  }
}
NoteTerraform 1.10+ can also lock using S3 itself (use_lockfile = true), and newer versions mark the DynamoDB option as deprecated. You'll still see S3 + DynamoDB in most existing projects and interviews, and the idea is the same: one writer at a time.

Interview angle"How do you manage Terraform state in a team?" Remote backend in S3 (versioning + encryption on, public access blocked), state locking (DynamoDB or S3 native lockfile), access limited with IAM, and applies run from a CI/CD pipeline rather than laptops. Also: "Why use modules?" Reuse, consistency, and fixing things in one place.

Check yourself

Why should you always set version when calling a registry module?
Pinning keeps builds repeatable. You upgrade on purpose, after reading the changelog, not by accident.
Two engineers run terraform apply at the same moment against an S3 backend with a DynamoDB lock table. What happens?
The first apply takes the lock (a LockID row in DynamoDB). The second can't get it and stops. The state lives in S3; DynamoDB only holds the lock.
The cluster was created, but the console says you can't see its nodes. What's the fix?
EKS access entries control who can see Kubernetes objects. Even root needs one. You can also set this in Terraform.

Key takeaways

  • aws configure stores credentials that Terraform's AWS provider also uses.
  • Split Terraform into files by purpose (vpc, eks, security groups, variables, outputs, versions) for readability.
  • Modules are reusable packages. Use registry or company modules, always pin version, and wire them together via outputs like module.vpc.private_subnets.
  • init → plan (≈55 resources) → apply; then add an EKS access entry and run aws eks update-kubeconfig; finish with terraform destroy.
  • In teams, store state remotely in S3 with locking (DynamoDB or S3 lockfile) so only one apply runs at a time.
