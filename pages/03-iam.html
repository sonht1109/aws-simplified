IAM: Who Can Do What

IAM (Identity and Access Management) decides who can get into your AWS account and what they are allowed to do once inside. It's the first service every DevOps engineer sets up, and one you'll use constantly.

A bank, two checks

Picture a bank. It has a service desk, an employee area, and a vault full of documents and cash. To keep it safe, the bank runs two separate checks:

  1. Can you come in at all? Only known people (customers, staff) may enter the building.
  2. Once inside, where can you go and what can you do? A customer can use the service desk. An employee can use their laptop. Only a few senior staff can open the vault.

Without these checks, anyone could walk straight into the vault. These two checks have names:

Authentication

"Who are you?" Proving your identity, for example with a username and password. Getting through the front door.

Authorization

"What are you allowed to do?" The permissions you have after you're in. Which rooms you can enter and what you can touch.

IAM is the AWS service that handles both for your AWS account.

The root user: the master key

When you created your account in Lesson 2, you signed up with an email address. That login is the root user. It can do everything: delete any server, wipe any database, close the account.

Now imagine a company with 1,000 employees sharing that one root login. Someone, by mistake or on purpose, opens the database service and deletes production data. The data may be gone for good, and because everyone used the same login, nobody can even tell who did it.

Rule #1: protect and don't use the root userNever share root credentials. Turn on MFA for root right away, and use it only for the few tasks that truly need it (such as some billing and account settings). For daily work, create IAM users. While you're learning in your own practice account, using root briefly is tolerable, but build the habit early.

The four building blocks

IAM has four main parts. Each solves a specific problem.

1. Users (authentication)

An IAM user is an identity for one person (or one tool) inside your account, with its own login. When employee #501 joins and needs AWS access, the DevOps engineer creates an IAM user for them. Now every action can be traced to a specific person.

A user with no permissions can sign in but can't do anything useful, like being let into the bank lobby and then stopped at every door.

2. Policies (authorization)

A policy is a document that lists permissions: which actions are allowed (or denied) on which resources. You attach policies to users, groups or roles. Example: "user 501 can read the database but not delete anything from it."

  • AWS managed policies: ready-made by AWS, such as AmazonS3ReadOnlyAccess or AmazonS3FullAccess. Great for common cases.
  • Customer managed (custom) policies: written by you when you need something more specific, such as access to one particular storage bucket only.

3. Groups (less repetitive work)

People join and leave companies all the time. Attaching the same five policies to every new developer is slow and easy to get wrong. Instead you create groups (for example Developers, QA, DB-Admins, Others), attach policies to the group once, and drop each new user into the right group.

Even better: if all developers later need a new permission (say, to list servers), you add it to the group once and every member gets it, instead of editing four, forty or four hundred users.

4. Roles (temporary access for services and outsiders)

Sometimes the thing that needs access isn't a person. An application running on a server needs to read files from storage. A tool in another AWS account needs to deploy into yours. For these cases you use a role.

  • A role has policies like a user does, but no permanent password or keys.
  • Someone or something trusted "assumes" the role and receives temporary credentials that expire automatically (typically within an hour or a few hours).
  • If those credentials leak, they soon stop working. That's much safer than baking a permanent password into an app.

Typical uses: an EC2 server reading from S3, a Lambda function writing logs, a CI/CD pipeline deploying code, or access between two AWS accounts. You'll use roles in practice in the CI/CD lessons (Lesson 17).

Think of it like…A user is an employee ID card with your name on it. A role is a visitor badge from the front desk: it grants specific access and stops working at the end of the day.

What a policy looks like

Policies are written in JSON (a simple text format of keys and values). Here is the core of AWS's managed AmazonS3FullAccess policy, simplified:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:*",
      "Resource": "*"
    }
  ]
}
FieldMeaning
VersionThe policy language version. Always "2012-10-17" (it's a fixed value, not today's date).
StatementA list of rules. Each rule has the three fields below.
EffectAllow or Deny.
ActionWhich API actions, written service:Action. s3:* means every S3 action; s3:List* means every S3 action starting with "List".
ResourceWhich things it applies to. * means all; an ARN (Amazon Resource Name, a unique ID for one resource) narrows it down.

A custom policy that only lets someone read files from one bucket might look like this:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetObject"],
      "Resource": [
        "arn:aws:s3:::my-app-bucket",
        "arn:aws:s3:::my-app-bucket/*"
      ]
    }
  ]
}

How AWS decides: allow or deny?

  1. Everything starts as denied. If no policy says "Allow", the answer is no (an "implicit deny").
  2. An explicit "Deny" always wins. If any attached policy denies the action, it's blocked, even if another policy allows it.
  3. Otherwise, an "Allow" lets it through. Permissions from the user's own policies and from all their groups add up.

Hands-on: users, policies and groups

This is the practical flow you'd follow in the console. Do it yourself in your account.

Step A: create a user (authentication only)

  1. Sign in, search for IAM in the console, open Users → Create user.
  2. Name it, e.g. test-user-501. Tick Provide user access to the AWS Management Console and choose I want to create an IAM user. (The other option, IAM Identity Center, is AWS's recommended way to manage many people across many accounts; you can ignore it for now.)
  3. Choose an auto-generated password and tick Users must create a new password at next sign-in. You don't invent passwords for people, and they set their own on first login.
  4. Skip permissions for now and create the user. AWS automatically attaches one policy, IAMUserChangePassword, so the user can set their new password.
  5. Copy or download the .csv with the username, password and the console sign-in URL, which contains your 12-digit account ID: https://<account-id>.signin.aws.amazon.com/console.

Sign out, then sign in as an IAM user using the account ID, username and password. Set a new password. Now open S3 and try to list buckets: you get an access denied error saying you need s3:ListAllMyBuckets. Launching an EC2 server fails too. You're authenticated, but not authorized.

Step B: add a policy (authorization)

  1. Sign back in as an admin, open the user, choose Add permissions → Attach policies directly.
  2. Search "S3" and pick AmazonS3ReadOnlyAccess (view only) or AmazonS3FullAccess (view, create, delete).
  3. Sign in as the test user again. Now listing buckets works, and with full access, so does creating one. (Bucket names must be unique across all of AWS, so pick something unusual.)

Step C: use a group instead

  1. Go to User groups → Create group, name it development, attach AmazonS3FullAccess.
  2. Add your test users to the group.
  3. Later, when the team asks for server access, open the group and attach AmazonEC2FullAccess. Every member gets it at once.
Clean upWhen you finish practising, delete test users and groups you don't need. Unused logins are a security risk even when they cost nothing.

Best practices

  • Least privilege. Give each person or app only the permissions they need for their job, nothing more. Start small and add when needed. A new junior engineer might not get delete rights at all.
  • Turn on MFA (multi-factor authentication). After the password, the user must also enter a short code from an authenticator app or tap a security key. A stolen password alone is then not enough. Enable it for root first, then for every human user.
  • One identity per person. Never share logins, so you always know who did what.
  • Manage permissions through groups, not user by user.
  • Use roles for applications and AWS services instead of storing long-lived passwords or access keys in code. (Access keys for the command line are covered in Lesson 12.)
Interview angle"Do you use the root user?" Good answer: "No. Root is locked down with MFA. Our DevOps team members each have their own IAM identity with admin-level access; developers and QA get IAM users placed in groups with least-privilege policies; applications use IAM roles. That way every action is traceable to a person."

Check yourself

A new IAM user can sign in but sees "access denied" everywhere. What's missing?
Signing in proves who they are (authentication). They still need policies, directly or through a group, that allow actions (authorization).
An app on an EC2 server needs to read files from S3. What's the best way to give it access?
Roles give temporary credentials that rotate automatically, so nothing permanent is stored in the code.
A user's group allows s3:*, but a policy on the user says Deny s3:DeleteBucket. Can they delete a bucket?
IAM checks for any explicit Deny first. If one matches, the action is blocked no matter how many Allows exist.

Key takeaways

  • Authentication = who you are; authorization = what you may do. IAM handles both.
  • The root user can do everything: protect it with MFA, never share it, don't use it day to day.
  • Users are identities, policies (JSON with Effect / Action / Resource) are permissions, groups save repeated work, roles give temporary access to apps and services.
  • Default is deny; an explicit Deny beats any Allow.
  • Follow least privilege and enable MFA for every human.
