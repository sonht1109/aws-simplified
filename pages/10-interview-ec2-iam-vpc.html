Scenario Questions: EC2, IAM, VPC

Interviewers today rarely ask "What is EC2?" — they describe a situation and ask how you'd handle it. Here are 10 scenario questions on everything so far, with model answers and links back to the lessons that explain each idea.

How to answer scenario questions

  1. Break the question into parts. "Highly available and scalable two-tier app" is really three questions.
  2. Name the AWS building block for each part (AZs for availability, Auto Scaling for scale, subnets for layout…).
  3. Say why, in one sentence each. Mention security when it fits.
  4. If several answers work, give them, then say which is simplest or best and why.

Networking and VPC

1. Design a VPC for a two-tier application that must be highly available and scalable.

Split it into its parts:

  • Layout: a public subnet holding an internet-facing load balancer, and a private subnet holding the application servers. The load balancer must be reachable from the internet, otherwise nobody can reach the app.
  • High availability: repeat the public and private subnets in at least two Availability Zones, so if one AZ goes down the other keeps serving.
  • Scalability: run the app servers in an Auto Scaling Group that adds instances when load rises.

This is exactly the build in Lesson 9. (Adding a database tier makes it three-tier.)

2. Your VPC has several subnets. Block outbound internet access for one subnet but keep it for another.

You could tighten outbound security group rules on every instance, but the cleanest answer is routing:

  • Find the route table associated with the subnet you want to restrict.
  • Remove the default route 0.0.0.0/0 that points to the internet gateway (or NAT gateway).
  • With no route out, nothing in that subnet can reach the internet. The other subnet keeps its own route table and stays connected.

Route tables: Lesson 6.

3. Instances in a private subnet need internet access for software updates. How?
  • Put a NAT gateway (or an older-style NAT instance) in a public subnet.
  • In the private subnet's route table, send 0.0.0.0/0 to the NAT gateway.
  • Bonus point: NAT (network address translation) replaces the instance's private IP with the NAT gateway's public IP, so outside sites never learn your server's address, and nobody outside can start a connection back in.

NAT gateway: Lesson 6.

4. Two EC2 instances, "foo" and "bar", must talk to each other using private IPs. What do you need?

Sometimes scenarios are simple:

  • Put them in the same VPC. Every route table has a built-in local route, so subnets in one VPC can reach each other — same subnet or different subnets.
  • Make sure their security groups (and NACLs, if customised) allow the port they use. A neat trick: allow traffic whose source is the other instance's security group.
  • If they are in different VPCs, connect the VPCs with VPC peering and add routes in both route tables pointing to the peering connection.
5. You must enforce strict network access control for your VPC. How?
  • Use network ACLs at the subnet level for broad, fine-grained rules: allow only specific IP ranges and ports, and explicitly deny bad ones. They apply to every instance in the subnet.
  • Use security groups at the instance level to open only the ports each app needs.
  • Using both is defense in depth.

Details and a simulator: Lesson 7.

6. Your organisation needs an isolated environment inside the VPC for sensitive workloads. How do you set it up?

This checks that you understand subnets as a unit of isolation:

  • Create a dedicated private subnet — a slice of the VPC's range (e.g. a few thousand of its 65,536 addresses).
  • Give it a route table with no route to an internet gateway or NAT gateway — only the local route.
  • Lock it down further with a strict NACL and security groups, and limit who can reach it (not even via the general bastion if not needed).
7. An application in your VPC needs to reach AWS services like S3 privately and securely. How?
  • Use a VPC endpoint. It lets resources in your VPC reach services such as S3 or DynamoDB over AWS's private network, without going through an internet gateway or NAT gateway.
  • For S3 and DynamoDB there is a free gateway endpoint; you add it to the subnet's route table. (It's the "S3 gateway" option you see in VPC and more.)
  • Combine it with an IAM role on the instance so the app has permission to use the bucket.

8. What's the difference between a security group and a NACL?
Security groupNACL
LevelInstanceSubnet
RulesAllow onlyAllow and deny, numbered order
StateStateful — replies allowed automaticallyStateless — replies need their own rule

Example of "stateful": your app calls google.com. With a security group, the response comes back in without any inbound rule because the group remembers the outgoing request. A NACL doesn't remember, so you must allow both directions.

Good practice: use both. More in Lesson 7.

IAM

9. Explain IAM users, groups, roles and policies.
  • User — an identity for a person (or tool) who needs to log in. Handles authentication: who are you?
  • Policy — a JSON document listing permissions (e.g. read S3, manage EC2). Handles authorization: what may you do? A user without policies can sign in but do nothing.
  • Group — a set of users sharing policies. If 500 developers all need EKS access, update the developers group once instead of 500 users.
  • Role — permissions that a service (or person, temporarily) can assume. Example: attach a role to an EC2 instance so the Python app on it can read a database or S3 bucket — no stored passwords.

Full explanation: Lesson 3.

Access to private servers

10. Instances in a private subnet must have no direct internet access, but admins still need to log in. How do you set this up?
  • Launch a bastion host (jump server) in a public subnet of the same VPC.
  • Admins SSH to the bastion, then from it to the private instances' private IPs. Use SSH for Linux and RDP for Windows.
  • Allow SSH on the bastion only from trusted IPs, and on private instances only from the bastion's security group.
  • Why it's secure: there is one door to guard, and you can log and audit every login and command there.

Check yourself

The quickest way to stop one subnet from reaching the internet, without touching each instance, is to…
Deleting the IGW would cut off every subnet. Editing that one subnet's route table affects only it.
An app on EC2 needs to read from S3. What's the right way to give it permission?
Roles give services temporary credentials without storing secrets on the machine.
Which pair gives a two-tier app high availability and scalability?
AZs keep the app up if one location fails; an Auto Scaling Group adds servers as load grows.

Key takeaways

  • Break scenario questions into parts and map each to a building block.
  • Availability → multiple AZs. Scalability → Auto Scaling Groups.
  • Most subnet questions are answered by the route table: IGW, NAT, or nothing.
  • Security: NACLs at the subnet, security groups at the instance — stateless vs stateful.
  • Give apps permissions with IAM roles; reach private servers through a bastion host.
