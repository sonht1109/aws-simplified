Shell Scripting: AWS Resource Report

Write a beginner-friendly shell script that lists the active resources in your AWS account for any region and service, run it on a schedule with cron, and pick up the scripting and security habits interviewers look for.

Why this project?

Interviewers rarely ask "what's the command to list processes?" anymore. They ask "What do you use shell scripts for in your job?" This project gives you a real answer.

Companies care about cost. Forgotten EC2 instances, unattached EBS volumes and old load balancers all cost money. So DevOps engineers often write a script that reports what's running, schedule it with cron to run every day, and (optionally) email the report to managers. Many teams write these in shell; others use Python with boto3.

The script works like this:

./aws_resource_list.sh <region> <service>

./aws_resource_list.sh us-east-1 ec2    # running EC2 instances in us-east-1
./aws_resource_list.sh us-east-1 s3     # S3 buckets
./aws_resource_list.sh us-east-1 ebs    # EBS volumes
TipAWS has 200+ services, and no company uses all of them. First find out which services your organisation actually uses and support only those. Anything else should get a clear "invalid service" message.

The full script

#!/bin/bash
###############################################################################
# Author:  DevOps Team
# Version: v0.0.1
#
# Lists active AWS resources in a given region for a given service.
#
# Supported services: ec2, s3, rds, dynamodb, lambda, ebs, elb, cloudfront,
#                     cloudwatch, sns, sqs, route53, cloudformation, iam, vpc
#
# Usage:   ./aws_resource_list.sh <region> <service>
# Example: ./aws_resource_list.sh us-east-1 ec2
###############################################################################

# 1. Check that exactly two arguments were passed
if [ $# -ne 2 ]; then
    echo "Usage: $0 <region> <service>"
    echo "Example: $0 us-east-1 ec2"
    exit 1
fi

region=$1
service=$2

# 2. Check that the AWS CLI is installed
if ! command -v aws &> /dev/null; then
    echo "AWS CLI is not installed. Please install it and try again."
    exit 1
fi

# 3. Check that the AWS CLI is configured
if [ ! -d ~/.aws ]; then
    echo "AWS CLI is not configured. Run 'aws configure' and try again."
    exit 1
fi

# 4. Run the right AWS CLI command for the chosen service
case $service in
    ec2)
        aws ec2 describe-instances --region "$region" \
            --filters "Name=instance-state-name,Values=running" ;;
    s3)             aws s3api list-buckets ;;
    rds)            aws rds describe-db-instances --region "$region" ;;
    dynamodb)       aws dynamodb list-tables --region "$region" ;;
    lambda)         aws lambda list-functions --region "$region" ;;
    ebs)            aws ec2 describe-volumes --region "$region" ;;
    elb)            aws elbv2 describe-load-balancers --region "$region" ;;
    cloudfront)     aws cloudfront list-distributions ;;
    cloudwatch)     aws cloudwatch describe-alarms --region "$region" ;;
    sns)            aws sns list-topics --region "$region" ;;
    sqs)            aws sqs list-queues --region "$region" ;;
    route53)        aws route53 list-hosted-zones ;;
    cloudformation) aws cloudformation describe-stacks --region "$region" ;;
    iam)            aws iam list-users ;;
    vpc)            aws ec2 describe-vpcs --region "$region" ;;
    *)
        echo "Invalid service: $service"
        echo "Supported: ec2 s3 rds dynamodb lambda ebs elb cloudfront cloudwatch sns sqs route53 cloudformation iam vpc"
        exit 1
        ;;
esac

Walking through it

  1. Header comments first. Before any code: what the script does, the author (or team) so people know who to ask, a version, supported services, and usage with an example. Start at a low version like v0.0.1, bump it on every change, and move to 1.0.0 once it's stable. In an interview, start by writing this header; it shows good habits.
  2. Validate the arguments. If someone runs ./aws_resource_list.sh ec2 and forgets the region, print the usage and exit. Using $0 in the message means it stays correct even if the file is renamed. Whenever a script takes arguments, validate them first.
  3. Check the AWS CLI is installed. You could call the AWS APIs directly with curl, but then you'd have to handle request signing, headers and JSON yourself. The AWS CLI makes those API calls for you. (In Python you'd use boto3 instead.) If the CLI is missing on this machine, say so clearly instead of failing with a confusing error.
  4. Check it's configured. aws configure creates the ~/.aws folder with your credentials and default region. [ ! -d ~/.aws ] means "if this directory does not exist".
  5. Pick the command with case. The region stays the same and only the command changes per service. A case statement is cleaner than a long if / elif chain: one readable line per service, and a *) catch-all for invalid input.
TipChecking for ~/.aws is a quick heuristic. A stronger check is aws sts get-caller-identity, which actually confirms the credentials work. Also note: S3, IAM, CloudFront and Route 53 are global, so the region doesn't change their results.
Interview angle"How do you remember all those CLI commands?" It's fine to say: "I remember the common ones like ec2 describe-instances and s3api list-buckets. For the rest I check the AWS CLI reference." That's what working engineers do.

Running it on EC2

If you're on Windows, the easiest place to run Bash is a small Ubuntu EC2 instance (launch one, then SSH in).

# Install the AWS CLI v2 on Ubuntu
sudo apt update
sudo apt install -y unzip
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install
aws --version

# Configure it (use an IAM user's access keys, not root)
aws configure

# Make the script executable and run it
chmod +x aws_resource_list.sh
./aws_resource_list.sh us-east-1 ec2

Test the failure paths too: run it with one argument (you should see the usage message), and before installing the CLI (you should see "AWS CLI is not installed"). Checking that your error handling works is part of testing a script.

Scheduling it with cron

cron is the Linux scheduler. It runs commands at set times. Each line in your crontab has five time fields followed by the command:

┌──────── minute       (0-59)
│ ┌────── hour         (0-23)
│ │ ┌──── day of month (1-31)
│ │ │ ┌── month        (1-12)
│ │ │ │ ┌ day of week  (0-7, 0 and 7 = Sunday)
│ │ │ │ │
0 21 * * * /home/ubuntu/aws_resource_list.sh us-east-1 ec2 >> /home/ubuntu/ec2_report.log 2>&1

That line runs the report every day at 9 PM and appends the output (and any errors, via 2>&1) to a log file. Edit your crontab with crontab -e and list it with crontab -l.

Watch outcron runs with a very short PATH (usually just /usr/bin:/bin). The AWS CLI lives in /usr/local/bin, so the script may say "AWS CLI is not installed" under cron even though it works in your terminal. Add PATH=/usr/local/bin:/usr/bin:/bin at the top of the crontab or the script, and always use full paths in cron lines.
Try it: cron expression explainer

Edit the five fields or pick a preset. Supports *, numbers, lists (1,15), ranges (1-5) and steps (*/15).

Securing the script

Other people (developers, managers) may need to run the report, but they shouldn't edit it. Use file permissions. Each digit of chmod is a sum of 4 = read, 2 = write, 1 = execute, given for owner, group and others in that order:

CommandOwnerGroupOthersUse when
chmod 750rwx (7)r-x (5)none (0)Your team can run it; nobody else can
chmod 770rwx (7)rwx (7)none (0)Your whole DevOps team maintains it
chmod 755rwx (7)r-x (5)r-x (5)Everyone can run it, only you can edit
Watch outYou may see advice to use chmod 711 ("others may only execute"). That works for compiled programs, but not for shell scripts: Bash must read a script in order to run it, so execute-only users get "Permission denied". Give read + execute (5) to anyone who should run it. Either way, never put secrets (access keys, passwords) in a script. Rely on aws configure, IAM roles, or a secrets manager.

Check yourself

You run ./aws_resource_list.sh us-east-1 ec2. What is $0?
$0 is the script's own name; $1 is the region and $2 is the service.
Which crontab schedule runs at 9 PM every day?
Minute 0, hour 21. 21 0 means 00:21 (just after midnight), and * 21 runs every minute from 21:00 to 21:59.
The script works in your terminal but cron logs "AWS CLI is not installed". Most likely cause?
cron uses a minimal PATH. Set PATH in the crontab or script, or call /usr/local/bin/aws directly.

Key takeaways

  • A resource-report script (region + service arguments) is a realistic, interview-friendly DevOps automation that helps control cost.
  • Start with a header (author, version, usage), then validate: argument count, CLI installed, CLI configured. Fail early with exit 1.
  • Use the AWS CLI rather than raw API calls, and a case statement to map each service to its command, with a *) catch-all.
  • Schedule with cron (0 21 * * * = daily 9 PM), using full paths and a proper PATH.
  • Lock it down with chmod (e.g. 750 or 755; scripts need read + execute), and never hard-code secrets.
