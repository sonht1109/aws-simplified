AWS Interview Q&A Collection

You've done the theory and the hands-on work. Before an interview you also need a quick-reference you can skim the night before. This lesson covers how to use a large bank of AWS DevOps interview questions well, and gives you a representative set of questions by service, each linked to the lesson that explains it.

Why a question bank?

Courses and projects build real skill, but interviews test recall under pressure. A well-organised question bank, roughly 500 questions across about 30 AWS services, gives you:

  • One place to revise. One file per service (e.g. an ecs.md), each a list of questions with short answers.
  • A fast gap check. Read a question, try to answer it, then compare. If you couldn't answer it, that's a topic to revisit.
  • Job-description targeting. If the posting says "strong ECS experience", go straight to the ECS questions.

Questions in such a bank come in three levels:

Basic / theory

"What is…?", "What's the difference between…?" These check that you know the vocabulary.

Advanced

How things work inside, limits, trade-offs, best practices.

Scenario-based

"Your app is slow / insecure / expensive. What do you do?" Interviewers increasingly focus on these, because they show real experience.

Keep it growing

Add questions you meet in real interviews or at work. A shared repo that others can contribute to stays up to date.

How to prepare

  1. Balance your time. With four hours, spend about two on theory and hands-on work and two on interview prep. Learning ECS today? One hour theory, one hour practical, one hour on ECS questions.
  2. Answer out loud before reading the answer. Rehearse how you would put it to an interviewer, not the book's wording.
  3. Tie answers to something you built. "In my project I put the ALB in public subnets and the app in private ones…" sounds more convincing than a definition.
  4. Interview tomorrow? Skip new labs. Skim the bank for the services in the job description and revise the scenario questions.
  5. Be honest about gaps. "I haven't hit that scenario yet; here's how I'd approach it" is better than bluffing.
TipA strong answer has three parts: a one-line definition, how you'd use it (or did use it), and one trade-off or gotcha. Scenario answers add the steps you'd take, in order.

Representative questions by service

A sample of the kind of questions you'll face. Each answer is short on purpose; the linked lesson has the full explanation.

Compute, identity and networking

EC2: what's the difference between stopping and terminating an instance?

Stopping shuts it down but keeps the root EBS volume, so you can start it again (you stop paying for compute, but still pay for storage). Terminating deletes the instance, and by default its root volume too. → Lesson 4

IAM: role vs user. When do you use a role?

A user is a long-lived identity for a person or tool with its own credentials. A role has no permanent credentials; it's assumed and hands out temporary ones. Use roles for EC2/Lambda/other services and for cross-account access, so access keys never sit on a server. → Lesson 3

VPC: what makes a subnet "public"?

Its route table has a route 0.0.0.0/0 to an internet gateway. Private subnets reach the internet outbound through a NAT gateway instead. → Lesson 6

Security groups vs NACLs?

Security groups are attached to instances (ENIs), are stateful and only have allow rules. NACLs are attached to subnets, are stateless (return traffic needs its own rule), support allow and deny, and are evaluated in rule-number order. → Lesson 7

Scenario: users report the site is down after one AZ failed. How do you prevent this next time?

Run instances in at least two AZs with an Auto Scaling Group, put a load balancer in front with health checks, and use Multi-AZ for the database. → Lesson 9, Lesson 28

Storage, DNS and content delivery

S3: how do you protect against accidental deletes?

Turn on versioning (deleted objects can be restored), optionally MFA Delete, restrict delete permissions in bucket policies, and replicate critical data. → Lesson 11

Route 53: CNAME vs alias record?

A CNAME points a name to another name and can't be used at the zone apex (example.com). An alias is Route 53-specific, works at the apex, points directly to AWS resources such as an ALB or CloudFront, and alias queries to AWS resources are free. → Lesson 8

CloudFront: users in Asia see slow downloads from a US bucket. Fix?

Put CloudFront in front of the bucket so content is cached at edge locations near users, and lock the bucket to CloudFront with origin access control. → Lesson 21

Infrastructure as Code and tooling

CloudFormation vs Terraform?

Both are declarative IaC. CloudFormation is AWS-only and AWS manages its state for you. Terraform is multi-cloud, uses HCL, and keeps its own state file, which you must store safely (e.g. S3 + DynamoDB lock). → Lesson 13, Lesson 26

Terraform: why must the state file never go to Git?

It can contain secrets in plain text, and if two people apply from different copies they overwrite each other. Use a remote backend with locking instead. → Lesson 34

AWS CLI: how do you work with several accounts from one laptop?

Use named profiles (aws configure --profile dev) and pick one with --profile or the AWS_PROFILE variable. → Lesson 12

CI/CD, monitoring and serverless

What are buildspec.yml and appspec.yml?

buildspec.yml tells CodeBuild how to build and test (phases and commands). appspec.yml tells CodeDeploy how to deploy: which files go where, and which hook scripts to run. → Lesson 16, Lesson 17

CloudWatch: how do you get alerted when CPU goes above 80%?

Create a CloudWatch alarm on the CPUUtilization metric with an 80% threshold and an SNS topic as the action. Memory and disk need the CloudWatch agent (custom metrics). → Lesson 18

Lambda: when would you not use it?

For jobs longer than the 15-minute limit, steady high-traffic workloads where EC2/containers cost less, or apps that need special OS-level control. → Lesson 19

Scenario: the bill doubled because of old EBS snapshots. How do you stop it happening again?

Automate cleanup: a scheduled Lambda (boto3) finds snapshots not linked to any active volume or instance and deletes them, plus budgets and alerts. → Lesson 20

Containers, security and compliance

ECS vs EKS?

ECS is AWS's own simpler orchestrator; EKS is managed Kubernetes, which is portable and has a huge ecosystem but is more complex. Both can run on Fargate. → Lesson 23

Where should database passwords live?

Not in code or environment files. Use Secrets Manager (built-in rotation) or Systems Manager Parameter Store (SecureString, cheaper), with IAM controlling who can read them. → Lesson 25

How do you find EC2 instances that break a company rule?

AWS Config: use a managed rule if one exists, or write a custom Lambda rule, and review the compliance dashboard. → Lesson 27

ALB or NLB for a UDP game server?

NLB: it handles UDP at Layer 4 with very low latency. ALB only understands HTTP(S). → Lesson 28

Scenario: "How did you migrate an app to AWS?"

Walk through the phases (prepare, plan, migrate, monitor, optimize) and name the strategy you used for each group of apps, instead of only saying "lift and shift". → Lesson 30

Interview angleInterviewers can tell memorised definitions from experience. After a definition, add "and here's where I used it…" with a detail from one of your projects. Even a lab project counts if you can explain the decisions you made.

Key takeaways

  • A question bank is a revision tool, not a replacement for theory and hands-on practice.
  • Split study time between theory, practicals and interview prep; let unanswered questions show you what to study next.
  • Expect basic, advanced and especially scenario-based questions.
  • Answer with definition → how you used it → a trade-off; for scenarios, give ordered steps.
  • Target the services in the job description, and be honest about gaps.
