Lambda: Serverless Functions

AWS Lambda runs your code only when something happens: a schedule, a file upload, an API call. You don't create or manage any servers, and you pay only for the milliseconds your code runs. That makes it a favourite DevOps tool for automation jobs.

What problem Lambda solves

When you think of S3 you think storage. Lambda belongs to two ideas at once:

  • Compute: like EC2, it gives you a place to run code (Python, Node.js, Java…).
  • Serverless: unlike EC2, you never pick, start, patch or stop a server.

With EC2 you tell AWS the image, instance type (CPU and memory), network and security settings, and you get a virtual server that runs until you stop it. With Lambda you hand AWS just your code. When an event arrives, AWS creates the compute it needs, runs the code, scales out if many events come at once, and then removes it all again.

What "serverless" means

Serverless doesn't mean there are no servers. It means the servers aren't your problem. AWS provisions, scales, patches and tears them down, and you don't even see an IP address or subnet. You only care about your code and what triggers it.

Think of it like…The checkout in a food-delivery app. A customer taps Pay, the payment code runs for a moment, the order is placed, and the customer is gone. On a serverless design, compute for that checkout exists only while the payment is being processed and disappears once it's done. On a server design, a checkout server sits running (and costing money) all night, whether anyone orders or not.

Who decides: server or serverless?

For the company's applications, the architects and developers decide. A food app can be built either way, and it depends on how the code is written. As a DevOps engineer you build the infrastructure they choose. Where you choose Lambda is in your own automation work.

Event-driven: triggers

Lambda functions are event-driven: they run in response to an event. The thing that delivers the event is the function's trigger. You can also run a function by hand with a test event, but a function with no trigger loses most of the benefit.

  • Schedule: an EventBridge rule (formerly "CloudWatch Events") like "every day at 10:00" works like a cron job in the cloud.
  • Resource events: "an EBS volume was created", "an EC2 instance changed state", delivered through EventBridge.
  • S3 events: "a new object was uploaded to this bucket".
  • HTTP requests: through a function URL or API Gateway.

How DevOps engineers use Lambda

Cost optimization

Find stale resources (an EBS volume nobody has used for 30 days, old snapshots, an idle instance holding an Elastic IP) and report or delete them. This is built step by step in Lesson 20.

Security & compliance

Enforce company rules automatically. Examples: "all EBS volumes must be gp3, not gp2" (gp3 is cheaper and faster), or "no S3 bucket may be public". The function checks daily and sends an SNS alert, or fixes the problem itself.

Routine checks

Daily audits, such as listing IAM users or roles that were given extra permissions, and sending a summary to the team.

Why Lambda rather than EC2 for these? Say a cleanup script runs for 5 minutes every morning at 10:00. On EC2 you'd have to start a server, run the script and stop the server every day, or leave it running and pay for 23 hours 55 minutes of nothing. If you forget to stop it, you pay even more. With Lambda you set "every day at 10:00" as the trigger and AWS handles the rest.

Creating a function in the console

  1. Open Lambda → Create function. Choose one of:
    • Author from scratch: you write the code (what DevOps engineers usually do).
    • Use a blueprint: AWS samples, e.g. "process an object uploaded to S3".
    • Container image: package your code as a Docker image stored in ECR.
  2. Runtime: the language. AWS provides managed runtimes for Python, Node.js, Java, .NET and Ruby. Other languages (e.g. Go, or even shell) run on an OS-only "custom runtime", which is more work. Python is the most popular choice for DevOps scripts.
  3. Execution role: by default Lambda creates an IAM role for the function that can only write logs. If your function needs to read EC2 or publish to SNS, add permissions to that role (or choose an existing role). As always, services get permissions through roles. See IAM.
  4. Advanced settings → Enable function URL (optional) gives the function its own HTTPS address. Auth type NONE means anyone can call it, which is fine for a hello-world demo. AWS_IAM restricts it to authorised callers. Without a URL, AWS services and triggers can still invoke the function. DevOps automation rarely needs a URL.

The handler

The new function comes with sample code:

import json

def lambda_handler(event, context):
    # event:   the data from the trigger (the S3 object, the schedule, the HTTP request...)
    # context: info about this run (request id, time remaining...)
    return {
        'statusCode': 200,
        'body': json.dumps('Hello from Lambda!')
    }

The handler is the function Lambda calls first, like main() in Java or C. The handler setting lambda_function.lambda_handler means "file lambda_function.py, function lambda_handler". You can write as many other functions as you like, but they run only if the handler calls them. You can rename the handler, but then you must also update it under Runtime settings.

You can edit code in the browser, add files and folders, or write it in VS Code on your laptop and upload a .zip. Click Deploy to save, then Test with a test event to run it by hand. Open the function URL and you'll see "Hello from Lambda!".

Pricing model

You pay for two things, and nothing while the function is idle:

  • Requests: about $0.20 per million invocations.
  • Duration × memory, measured in GB-seconds: run time (billed per millisecond) × memory size. About $0.0000167 per GB-second on x86.

The free tier includes 1 million requests and 400,000 GB-seconds per month, so most DevOps automation costs nothing. (Prices are approximate us-east-1 list prices; check the AWS pricing page for current numbers.)

Check yourself

A Python script must run for 4 minutes every night. What's the most cost-effective way to run it on AWS?
Lambda with a schedule trigger runs only those 4 minutes and bills only for them. EC2 would bill all day.
Your function times out after 3 seconds even though the code is correct. Why?
The default timeout is 3 seconds. You can raise it up to 15 minutes.
What does the handler setting lambda_function.lambda_handler mean?
It's file.function, the entry point Lambda calls with (event, context).

Key takeaways

  • Lambda is serverless compute: you give AWS code, and it creates, scales and removes the servers.
  • Functions are event-driven: schedules, S3 uploads, resource events or HTTP requests trigger them.
  • The handler (lambda_handler(event, context)) is the entry point. Permissions come from the function's execution role.
  • Default timeout is 3 s (max 15 min). You pay per request + GB-seconds, with a generous free tier and nothing while idle.
  • DevOps engineers use Lambda for cost optimization, compliance checks and routine automation.
