CloudWatch: Metrics, Logs, Alarms

CloudWatch is AWS's built-in monitoring service. It collects numbers (metrics) and text records (logs) from your resources, shows them on graphs and dashboards, and alerts you when something goes wrong. That way nobody has to watch servers 24/7.

What CloudWatch is

Think of it like…A security guard for a property. When you come back you can ask, "What happened while I was away?" The guard can also be told, "If you see smoke, call me right away." CloudWatch does both for your AWS account: it keeps a record of what happened and raises the alarm when a rule is broken.

In one sentence for an interview: CloudWatch is the AWS service for monitoring, alerting, reporting and logging of your resources and applications. Its main features:

  • Metrics: numbers measured over time, like CPU %, network bytes, request count. Many are collected automatically.
  • Alarms: rules on a metric ("if CPU ≥ 80%…") that trigger an action such as an email or scaling out.
  • Logs (plus Logs Insights for searching them): text output from services and apps.
  • Custom metrics: your own numbers, for things AWS doesn't measure by default.
  • Dashboards: your chosen graphs on one screen.

CloudWatch doesn't scale servers or cut costs by itself, but it's what triggers those actions. For example, an alarm can tell an Auto Scaling group to add a server, or a schedule can start a Lambda function that cleans up waste (see Lesson 20).

Monitoring vs logging

Monitoring (metrics)

Watching numbers over time to answer "how healthy is it right now?" Example: CPU was 35% at 10:00, 92% at 10:05. Small, regular data points that are easy to graph and alert on.

Logging

Keeping text records of events to answer "what exactly happened?" Example: ERROR: Could not open requirements.txt. Detailed, used for debugging and audits.

You need both. A metric tells you that something is wrong ("CPU at 100%"), and logs help you find out why.

NoteThe record of who called which AWS API (e.g. "user X deleted bucket Y at 14:02") is kept by a sister service, AWS CloudTrail. CloudTrail can also deliver those records into CloudWatch Logs so you can search and alarm on them there.

Logs: log groups and streams

Many AWS services send their logs to CloudWatch Logs automatically, with no setup. Logs are organised in two levels:

  • Log group: one per source, e.g. one per CodeBuild project (/aws/codebuild/sample-python-flask-service) or one per Lambda function. This stops 100 projects' logs from mixing together.
  • Log stream: one sequence of events inside a group, e.g. one build run.

Example: open the log group of the CodeBuild project from Lesson 16. Every build is there: the successful ones with the full Docker build output, and the early failed one with Could not open requirements file. The logs stay there even if you delete the CodeBuild project. By default log groups keep data forever, so set a retention period to control storage cost.

Logs Insights lets you query logs with a small query language, for example to find the latest errors:

fields @timestamp, @message
| filter @message like /ERROR/
| sort @timestamp desc
| limit 20

Metrics

Out of the box, CloudWatch tracks over a thousand metrics across the services in an account, grouped by service (namespace, e.g. AWS/EC2). For EC2 you'll find CPUUtilization, NetworkIn/NetworkOut, disk I/O, CPU credit usage and more, either per instance or across all instances. You only need the few that matter for your project.

You can see the same data on the EC2 console's Monitoring tab. That view is CloudWatch underneath.

How often: basic vs detailed monitoring

  • Basic monitoring (free): EC2 sends metrics every 5 minutes.
  • Detailed monitoring (paid): every 1 minute. Enable it from the instance's Monitoring tab → Manage detailed monitoring.

Statistic and period: Average vs Maximum

A graph point is a statistic (Average, Maximum, Minimum, Sum…) over a period (1 min, 5 min…). This choice matters:

  • Maximum catches every brief spike. Good for demos, but noisy: CPU touching 100% for one second isn't a real problem.
  • Average over e.g. 5 minutes shows sustained pressure. Production alarms usually use Average, so CPU stuck above 70% for 5+ minutes pages someone and a one-second blip doesn't.

Custom metrics

Some things are not collected by default. The classic example is memory usage on EC2: AWS can see the CPU from outside your instance, but not how much RAM your programs use inside it. To track that, or any application number like "orders per minute", something has to send it to CloudWatch. That's a custom metric. You can send one with the CloudWatch agent installed on the server, or from your own code or the CLI:

aws cloudwatch put-metric-data \
  --namespace "MyApp" \
  --metric-name MemoryUsedPercent \
  --unit Percent \
  --value 63

Once it's in CloudWatch, a custom metric works like any built-in one: graphs, dashboards, alarms.

Alarms and SNS notifications

Collecting metrics is only half the job. Engineers can't stare at graphs all day, so an alarm watches a metric for you and acts when it crosses a threshold. An alarm is always in one of three states:

StateMeaning
OKMetric is within the threshold.
ALARMMetric crossed the threshold for the required number of periods, so actions fire.
INSUFFICIENT_DATANot enough data yet (just created, instance stopped, metric not arriving).

The usual action is to send a message through Amazon SNS (Simple Notification Service). You create an SNS topic, which is a named channel, and add subscriptions: who gets messages and how (email, SMS, Slack via a webhook or chat integration, a Lambda function…). The alarm publishes to the topic, and SNS delivers the message to every subscriber.

Hands-on: alert when EC2 CPU spikes

  1. Launch an instance. Ubuntu, t2.micro, public IP. Turn on detailed monitoring so metrics arrive every minute instead of every five.
  2. Look at the metric. CloudWatch → Metrics → All metrics → EC2 → Per-Instance Metrics → your instance ID → CPUUtilization. It's flat near 0% for now.
  3. Create the alarm. Alarms → Create alarm → select that metric. Statistic Maximum, period 1 minute (just for a quick demo; use Average over 5 minutes in real life). Condition: Greater/Equal than 50.
  4. Add the notification. Action: "In alarm" → Create new topic (e.g. cloudwatch-topic) → your email address. Give the alarm a clear name and description, e.g. "Priority: EC2 CPU ≥ 50%. Automated notification from CloudWatch, please take action."
  5. Confirm the subscription. AWS emails a confirmation link. Until you click it, nothing is delivered. Check spam and promotions folders. You can see the status under SNS → Topics → Subscriptions ("Confirmed").
  6. Generate load. SSH in and burn some CPU, then stop it: 
    yes > /dev/null &     # start a CPU-hungry process
top                    # watch CPU climb (q to quit)
pkill yes              # stop it
  7. Watch it fire. Within a minute or two the alarm goes red (ALARM) and the email arrives with the metric, threshold and time.
Watch outNever run CPU-burning scripts on a production server or your work laptop. At 100% CPU the machine becomes unresponsive. Use a throwaway demo instance and terminate it afterwards.

Dashboards

A dashboard puts the graphs you care about on one page: a line chart of CPU for all web servers, a number widget for error count, an alarm status widget. Each widget can show one metric or several, as lines, stacked areas, bars or pie charts. Teams often put one on a TV in the office or use it as the first page they check during an incident.

Interview angleInterviewers like real problems you've run into. Good examples from this lab: metrics showing up a few minutes late (basic monitoring is every 5 minutes); an alarm stuck in INSUFFICIENT_DATA; alert emails never arriving because the SNS subscription wasn't confirmed or they landed in spam; choosing Average over Maximum to avoid false alarms; and memory not being a default EC2 metric, so it needs a custom metric.

Check yourself

You want to alert on EC2 memory usage, but there's no memory metric in CloudWatch. Why?
AWS can't see RAM usage from outside the instance. Use the CloudWatch agent (or put-metric-data) to publish it as a custom metric.
Your alarm is created but no email ever arrives, even in ALARM state. What do you check first?
SNS won't deliver to an email address until the subscription is confirmed via the link AWS sends (check spam and promotions too).
For a production CPU alarm, which setting avoids paging people for one-second spikes?
Average over a few minutes only fires on sustained load. Maximum fires on every brief spike.

Key takeaways

  • CloudWatch handles monitoring, alerting, reporting and logging for AWS resources and apps.
  • Metrics are numbers over time (monitoring); logs are text records of events (debugging). Logs live in log groups → log streams.
  • EC2 sends metrics every 5 minutes by default, or every 1 minute with detailed monitoring. Memory needs a custom metric.
  • Alarms watch a metric against a threshold (OK / ALARM / INSUFFICIENT_DATA) and act, usually by publishing to an SNS topic that emails subscribers.
  • Use Average over several minutes in production, confirm SNS subscriptions, and use dashboards to see everything at a glance.
