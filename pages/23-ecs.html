ECS: Running Containers

Running one container is easy. Keeping hundreds of them healthy, scaled and reachable is the hard part. This lesson explains why container orchestration exists, how Amazon ECS works (clusters, task definitions, tasks, services), Fargate vs EC2, and the popular interview question: ECS vs EKS vs Kubernetes.

New to containers and images? Start with the quick primer in Lesson 22: ECR. This lesson also pulls its image from ECR.

Why isn't Docker alone enough?

Say you install Docker on a virtual machine and run your app as container c1. It works, but in production you quickly hit three problems:

1. No auto-healing

Containers are ephemeral (short-lived): they can die from a crash, running out of memory, a bad deploy, or someone deleting them by mistake. Plain Docker won't bring them back, so users see downtime.

2. No auto-scaling

On a normal day you get 100 requests. During a festival sale you get 10,000. One container can't cope, and plain Docker won't add more copies for you.

3. Changing addresses

Even if you restart a container by hand, it usually comes back with a new IP address (e.g. 172.16.3.4 becomes 172.16.3.9). Anything calling the old IP breaks.

A container orchestrator solves these. It watches your containers and restarts failed ones (auto-healing), adds or removes copies with demand (auto-scaling), and gives a stable address in front of changing containers (service discovery and load balancing). Orchestration is what took containers from "works in dev" to "safe in production".

Think of it like…A restaurant manager. Cooks (containers) may go home sick or get overwhelmed at dinner rush. The manager notices, calls in replacements, adds extra cooks at peak time, and customers always order at the same counter no matter which cook is working.

The orchestration landscape

  • Kubernetes is the open-source leader. Many companies sell their own "distribution" of it, just as Ubuntu and Fedora are distributions of Linux: Red Hat OpenShift (enterprise support and security), Rancher, and managed cloud versions like AWS EKS, Azure AKS and Google GKE.
  • Non-Kubernetes orchestrators also exist: Docker Swarm, Apache Mesos, and AWS's own ECS.

AWS built ECS (Elastic Container Service) to be simpler than Kubernetes. It doesn't use Kubernetes concepts like pods or deployments. It has its own: clusters, task definitions, tasks and services. It's also proprietary: it only runs on AWS.

How ECS is organised

Kubernetes objects (pods, deployments, services, ingress) are explained in Lesson 24: EKS.

Tip"Run task" starts a one-off task. If it dies, nothing replaces it. For a real app, create a service. That's where auto-healing and scaling come from.

Fargate vs EC2 launch type

When you create a cluster or task, you choose where the containers physically run:

Fargate (serverless)

You only say "this task needs 0.5 vCPU and 1 GB". AWS finds the compute. There are no servers to patch, scale or monitor. Like Lambda, but built for long-running containers. You pay per task for the CPU/memory it uses while running. Most teams start here.

EC2 (servers you manage)

ECS places tasks on EC2 instances in your cluster. You choose instance types, configure an Auto Scaling group, patch the OS and watch server health. In return you get more control: special instance types, GPUs, custom AMIs, and possibly lower cost at steady high usage.

ECS vs EKS vs Kubernetes: the interview question

On AWS you have three main ways to orchestrate containers: ECS, EKS (managed Kubernetes), or Kubernetes you install yourself on EC2 (with tools like kubeadm or kops).

Where ECS shines

  • Simple: no control plane with many components to learn and run. Create a cluster, a task definition and a service, and you're live. Cluster creation with Fargate takes about a minute.
  • Fully managed, and with Fargate there are no servers at all.
  • Cost-effective: no Kubernetes system workloads eating resources, and no control-plane fee.
  • Deep AWS integration: IAM roles per task, CloudWatch logs and metrics built in, load balancers, ECR.

Where ECS falls short

  • Lock-in: ECS task definitions and services only work on AWS. Move to Azure, and you rebuild from scratch. Kubernetes manifests (pods, services, deployments, ingress) carry over to any cloud with mostly small changes. In a multi-cloud or hybrid world, that matters. (Lock-in is good for AWS, not for you.)
  • Smaller ecosystem: Kubernetes is open source with a huge community adding features constantly. It can be extended with custom resources (CRDs) and controllers, which is how tools like Argo CD, Flux and Istio work. None of those run on ECS.
  • Fewer advanced options: Kubernetes has hundreds of ingress controllers and many security and secret-management add-ons. ECS mainly relies on AWS's load balancers and services.

Hands-on: deploy a Flask app on ECS Fargate

Watch out: costFargate tasks, public IPs and log storage are billed while running. Stop tasks and delete the cluster as soon as you finish.
  1. Create a cluster. ECS → Clusters → Create. Name it demo-ecs-cluster, keep the default VPC and subnets, and choose AWS Fargate as infrastructure. (Choosing EC2 would also ask you for instance types and an Auto Scaling group.) CloudWatch monitoring is on by default.
  2. Prepare the image. The sample is a small Python Flask app listening on port 3000. Build it and push it to a private ECR repository, using the login/build/tag/push flow from Lesson 22. A handy shortcut builds and tags in one go: 
    aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin 123456789012.dkr.ecr.us-east-1.amazonaws.com
docker build -t 123456789012.dkr.ecr.us-east-1.amazonaws.com/demo-app-repo:latest .
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/demo-app-repo:latest
  3. Create a task definition. Task definitions → Create new. Name it, keep launch type Fargate, OS Linux, and choose the smallest CPU/memory that fits.
  4. Pick the two IAM roles (see below). Let the console create a new task execution role so logs can go to CloudWatch. Leave the task role empty unless your code calls AWS services.
  5. Container details: name example, image URI …/demo-app-repo:latest, container port 3000 (HTTP). Optionally set memory soft/hard limits, similar to Kubernetes resource requests/limits. Keep "Use log collection" on with CloudWatch.
  6. Run it. Open the task definition → Deploy → Run task → choose your cluster → Create. The task goes from Provisioning to Running.
  7. Check logs. Open the task → Logs tab. These come from CloudWatch, and you'll see Flask reporting it's running on port 3000. To open the app in a browser, the task needs a public IP, and its security group must allow inbound port 3000 (see Lesson 7).

Task role vs task execution role

These two names confuse almost everyone, and interviewers know it.

Task execution role

Used by ECS itself (the agent) to start your task: pull the image from ECR, send logs to CloudWatch, read secrets for environment variables.

Task role

Used by your application code inside the container to call AWS APIs, e.g. read from S3 or write to DynamoDB. Optional: only if your app talks to AWS.

TipGood habit to mention in interviews: "I always send ECS container logs to CloudWatch. When something breaks, CloudWatch is my first stop." Logging and alarms are covered in Lesson 18.

Check yourself

Your ECS container crashes at 2 a.m. Which setup automatically starts a replacement?
A service constantly compares running tasks with the desired count and replaces any that stop. A one-off task or plain Docker won't.
Your container needs to upload files to S3. Which IAM role gets the S3 permission?
The task role is for your application code's AWS calls. The execution role is for ECS itself: pulling images and shipping logs.
Your company may move to another cloud next year. Why might that favour EKS over ECS?
ECS is proprietary to AWS. Kubernetes resources carry over to AKS, GKE or self-managed clusters with mostly small changes.

Key takeaways

  • Orchestrators add what plain Docker lacks: auto-healing, auto-scaling and stable networking.
  • ECS building blocks: cluster → task definition (blueprint) → task (running) → service (keeps N tasks alive, LB).
  • Fargate = serverless, nothing to manage. EC2 = more control, but you manage the servers.
  • ECS is simple, cheap and AWS-integrated, but proprietary with a smaller ecosystem. Most organisations choose EKS.
  • Execution role = ECS pulls images and writes logs. Task role = your app calls AWS.
