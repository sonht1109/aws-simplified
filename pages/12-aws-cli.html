AWS CLI

Clicking through the console is fine for learning, but it doesn't scale. The AWS Command Line Interface (CLI) lets you list, create and delete AWS resources from your terminal in seconds. In this lesson you'll install it, connect it to your account with access keys, and learn how to work out any command from the docs.

Why not just use the console?

So far we've built everything in the AWS console, the web UI. That's great for learning, but it's not automation-friendly. Picture a busy DevOps week:

  • "We need 10 VPCs for new projects by this afternoon."
  • "Create 20 S3 buckets with this exact configuration."
  • "Spin up 15 EC2 instances."

Doing that by clicking means repeating the same screens over and over, which is slow, boring and easy to get wrong. Every serious tool, whether AWS, Jenkins or GitHub, solves this the same way: with an API.

What is an API?

API stands for Application Programming Interface: a set of URLs that a program, rather than a person, can send requests to. You send a request like "create a bucket named X with versioning on", along with your credentials, and AWS sends back the result, usually as JSON.

  • Console (UI): you reach AWS manually by clicking.
  • API: you reach AWS programmatically, from a script, a tool or code.

Calling raw APIs yourself is hard work. You'd have to build HTTP requests, sign them with your keys and parse JSON. So AWS and others built tools that sit on top of the API and do that work for you:

ToolWhat you writeBest for
AWS CLIShort commands in a terminalQuick tasks, checks and simple scripts
SDKs (e.g. boto3 for Python)Code in your programming languageApps and automation that talk to AWS (see Lesson 20)
CloudFormation, Terraform, CDKTemplates/code describing the whole setupBuilding and managing large stacks of resources (Lesson 13, Lesson 26)
Think of it like…A translator. You say aws s3 ls in plain shorthand, and the CLI translates it into the exact API request AWS understands (here, ListBuckets), then translates the answer back for you.

CLI or CloudFormation/Terraform?

If they all call the same API, why learn more than one? Because they suit different jobs:

  • CLI = quick actions. Your manager asks "which S3 buckets do we have?" Running aws s3 ls answers in seconds, with no need to log in, switch regions and click around.
  • IaC tools = big, repeatable setups. A VPC, subnets, EC2 instances and a load balancer as one unit is far easier to describe in a template that can be reviewed and reused. A very long CLI command is hard to remember and share.
Interview angle"When do you use the CLI vs CloudFormation/Terraform?" Say: CLI for quick, short tasks and small scripts; CFT/Terraform when creating or managing a full stack of resources that should be version-controlled and reviewed. Every DevOps engineer uses the CLI daily, whatever IaC tool they pick.

Step 1: install the CLI (version 2)

Only install from the official AWS documentation (search "AWS CLI install", then User Guide → Get started → Install/update). Make sure you get version 2. Version 1 is old. Version 2 comes with everything it needs bundled in, so you don't have to install Python separately.

# Linux (x86_64)
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip
sudo ./aws/install

# macOS (command-line installer)
curl "https://awscli.amazonaws.com/AWSCLIV2.pkg" -o "AWSCLIV2.pkg"
sudo installer -pkg AWSCLIV2.pkg -target /

# Windows (PowerShell or cmd)
msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi

# Verify — should print aws-cli/2.x.y ...
aws --version
TipOn Windows, a Linux environment makes DevOps practice easier: a VirtualBox Ubuntu VM, WSL, or at least Git Bash for a Unix-like terminal.

Step 2: create access keys

The CLI is installed, but it doesn't know which of the millions of AWS accounts to talk to, or who you are. For programs, AWS uses access keys instead of a username and password:

  • Access key ID: like a username (e.g. AKIA…).
  • Secret access key: like a password. It's shown only once when you create it.

Create them under your name (top right) → Security credentials → Access keys → Create access key. Each user can have at most two access keys, which lets you rotate them.

Watch outAnyone with your secret key can use your account. Never share it, paste it in chats or commit it to Git. Use an IAM user, not the root user. AWS warns you if you try to create root access keys, and in a real company you won't have root access anyway (see Lesson 3: IAM). Delete keys you no longer need.

Step 3: aws configure

$ aws configure
AWS Access Key ID [None]: AKIAIOSFODNN7EXAMPLE
AWS Secret Access Key [None]: wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
Default region name [None]: us-east-1
Default output format [None]: json
  • Default region: where commands run unless you pass --region.
  • Output format: json (most common and script-friendly), table (easy to read) or text.
  • The values are saved in ~/.aws/credentials (keys) and ~/.aws/config (region, output).

Profiles: more than one account

Most engineers work with several accounts or roles (dev, prod…). A profile is a named set of credentials:

aws configure --profile dev          # save a second set of keys as "dev"
aws s3 ls --profile dev              # run one command as "dev"
export AWS_PROFILE=dev               # use "dev" for the whole terminal session
aws sts get-caller-identity          # "who am I?" — shows account and user ARN

Step 4: run commands

Every command has the same shape:

aws <service> <action> [--option value ...]
# Verify the setup: list your buckets
aws s3 ls
2024-06-06 10:12:33 demo-abhishek-bucket

# Create an EC2 instance (replace IDs with ones from YOUR account)
aws ec2 run-instances \
  --image-id ami-0abcdef1234567890 \
  --instance-type t2.micro \
  --key-name my-key \
  --security-group-ids sg-0123456789abcdef0 \
  --subnet-id subnet-0123456789abcdef0 \
  --count 1

The run-instances command is long because launching an instance in the console also asks for many details: the AMI, instance type, key pair, network and so on (Lesson 4). The JSON reply includes the new instance ID and private IP, and you'll see the same instance in the console if you're looking at the same region.

Reading the CLI reference (how to work out any command)

Nobody memorizes these commands. Search "AWS CLI reference <service>", e.g. "aws cli reference s3":

  1. Open the service page. Its Available Commands list shows actions like cp, ls, mb (make bucket), mv, rb, rm, sync.
  2. Click a command to see its description, every option and examples.
  3. For EC2, search the list for what you want to do (e.g. run-instances) and copy only the options you need.
  4. You can also run aws ec2 run-instances help right in the terminal.

Error messages tell you what's missing. Leave out --image-id and AWS replies: "An error occurred (MissingParameter) when calling the RunInstances operation: The request must contain the parameter ImageId". Leaving out optional ones like --key-name still works, though without a key pair you can't SSH in.

Try it: command builder

Pick a service and an action, fill in the options, and see the command plus the API call the CLI makes for you. Empty a required field to see the kind of error you'd get.

Check yourself

What does the AWS CLI actually do when you run aws s3 ls?
The CLI is a layer between you and the AWS API. It signs the request with your access keys, calls the API and formats the reply.
Your manager wants a 3-tier setup (VPC, subnets, EC2, load balancer) that the team can review and recreate. Best tool?
For whole stacks that need review and repeatability, use IaC. Keep the CLI for quick tasks.
Which pair of values does aws configure need to authenticate?
Access keys are the programmatic equivalent of username and password. Region and output format are just defaults.

Key takeaways

  • The console doesn't scale for repeated work. APIs let programs manage AWS, and the CLI wraps those APIs in simple commands.
  • Install CLI v2 from the official docs and check it with aws --version.
  • Authenticate with an IAM user's access keys through aws configure. Keep the secret key secret and use profiles for multiple accounts.
  • Command shape: aws <service> <action> --options. Look up options in the CLI reference or with help.
  • CLI for quick, short tasks. CloudFormation/Terraform for full, reviewable stacks.
