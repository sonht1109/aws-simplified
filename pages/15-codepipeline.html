CodePipeline vs Jenkins

AWS CodePipeline is AWS's managed pipeline orchestrator. The quickest way to understand it is to compare it with a Jenkins setup you may already know. You'll see how CodeCommit, CodePipeline, CodeBuild and CodeDeploy fit together, and how to explain in an interview when to choose CodePipeline and when to choose Jenkins.

New to CI/CD? Continuous integration, delivery and pipeline stages are explained in Lesson 14: CI/CD Basics & CodeCommit.

The classic Jenkins flow

  1. A developer commits a change (e.g. to a .java or .html file) and pushes it to a Git host such as GitHub, GitLab or Bitbucket.
  2. A webhook, an automatic "something happened" message from GitHub, triggers the Jenkins pipeline. The pipeline is written in Groovy, as a declarative or scripted pipeline.
  3. Jenkins implements CI itself: checkout → build and unit tests → static code analysis (SonarQube) → Docker image build → image scan → image push.
  4. Jenkins then invokes CD, handing the deployment to another tool: Argo CD or Flux (GitOps, the modern way), Spinnaker, or older approaches like Ansible or shell scripts running kubectl/helm.
  5. The app lands on Kubernetes or virtual machines.
NoteGitOps means Git is the single source of truth for what should be running. A tool like Argo CD keeps checking the cluster against Git and puts back anything someone changed by hand. Similar in spirit to CloudFormation's drift detection, except Argo CD fixes the drift automatically.

The same flow with AWS managed services

  1. The developer pushes code to CodeCommit, or, more commonly, to GitHub connected to AWS.
  2. The change triggers CodePipeline, which takes Jenkins's place as the orchestrator.
  3. CodePipeline invokes CI by calling CodeBuild, which runs the build, tests, scans and image push (Lesson 16).
  4. CodePipeline invokes CD by calling CodeDeploy, which rolls the app out to EC2 instances, on-prem servers, ECS or Lambda (Lesson 17).
Interview angleNote the wording: Jenkins usually implements CI (the stages run inside Jenkins) and invokes CD. CodePipeline usually invokes both: it does very little work itself and calls CodeBuild and CodeDeploy. You can skip CodeBuild and run scripts in other ways, but CodePipeline + CodeBuild + CodeDeploy is the standard pattern.

How a CodePipeline is put together

  • Pipeline: the whole workflow for one app.
  • Stages: run in order, e.g. Source → Build → Approval → Deploy. If a stage fails, the pipeline stops there.
  • Actions: the tasks inside a stage, each run by a provider: GitHub/CodeCommit/S3 for source, CodeBuild for build/test, CodeDeploy/ECS/CloudFormation for deploy, a manual approval, or a Lambda invoke.
  • Artifacts: the files passed from one stage to the next (source code, build output). CodePipeline stores them in an S3 artifact bucket.
  • Trigger: usually a push to a branch, received through a connection to your Git host.
Watch outCodeDeploy deploys to EC2/on-prem servers, ECS and Lambda, not to EKS. For Kubernetes on AWS, teams typically run kubectl/helm from a CodeBuild step, or use a GitOps tool like Argo CD (see Lesson 24: EKS).

If Jenkins is free, why pay for CodePipeline?

Jenkins software is free, but running it isn't. A typical Jenkins setup has a main server plus worker nodes (agents) that run the builds. As teams add pipelines, two agents become 4, 8, 16, 20 virtual machines, and someone has to:

  • scale them up and down,
  • apply security patches and upgrade plugins,
  • watch their health, clean up disks and replace broken nodes.

Often that needs a dedicated engineer. AWS spotted this management burden, as it did with compute (EC2) and storage (S3), and offers CodePipeline as a managed, pay-as-you-go service. Startups and small teams that don't want to babysit CI servers find that very appealing.

…and why Jenkins is still more popular

  • Managing it isn't always hard. With Docker agents, each build runs in a container that's created on demand and deleted afterwards, so a couple of servers can handle a lot. You can also run Jenkins on EC2 with Auto Scaling and CloudWatch alarms.
  • No lock-in. A Jenkinsfile kept in Git works on AWS, Azure, GCP or on-prem. If your company moves clouds or goes hybrid, you move Jenkins and keep your pipelines. CodePipeline definitions only work on AWS.
  • Huge ecosystem. Thousands of plugins and integrations with almost any tool.
  • Cost control. Pay-as-you-go services can get expensive if they're used carelessly.

Key takeaways

  • CodePipeline ↔ Jenkins, CodeCommit ↔ GitHub, CodeBuild ↔ CI build stages, CodeDeploy ↔ Argo CD/Ansible.
  • A pipeline is made of stages (Source, Build, Approval, Deploy…) containing actions. Artifacts pass between them through S3.
  • Jenkins usually implements CI and invokes CD. CodePipeline invokes both, via CodeBuild and CodeDeploy.
  • Pick CodePipeline for an AWS-only shop that doesn't want to run CI servers. Pick Jenkins for portability, plugins and full control.
  • In real setups, CodePipeline is usually paired with GitHub rather than CodeCommit.
